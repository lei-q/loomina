# ADR-0095：导出前合规预检与内容安全规则扫描

- 状态：已采纳
- 日期：2026-11-11
- 关联：H6、G8、H5、H7、G1、R3、R29、ADR-0008、ADR-0086、ADR-0090、ADR-0091

## 背景

`PUBLISHING.md` 要求四个检查点（剧本 / 关键帧 / 成片 / 发布文案）与三级处置（pass / review / block），并规定「预检不通过，不进入渲染」。`FEATURES.md` 的 G8 仍是「待设计」，H6 只有一句「文本 / 图像 / 视频三级」。

现实约束：

- 当前网关只有生成接口，没有内容审核接口；接第三方审核需要额外账号、计费与网络条件，不是这一轮能验证的。
- 成片页已经有五种导出（MP4 / 预览 HTML / OTIO / SRT / 发布包），但导出前只检查了画面与配音缺口，没有任何合规闸门。
- 用户要求「一个功能一个功能地实现，每实现一个都能在 UI 上操作验证」，所以这一轮必须给出可点的检查面板与真实拦截，而不是只写文档。

## 决策

### 1. 规则扫描放在共享的纯函数里

新增 `apps/web/lib/compliance.ts`，不依赖 Node 或浏览器 API，客户端与服务端共用：

- 17 条规则，覆盖涉政、涉黄、暴力、低俗、歧视、未成年人、拜金炫富、封建迷信、诱导消费、违法等分类。
- 两种级别：
  - `block`：危害国家安全、分裂 / 民族仇恨、恐怖袭击与制作爆炸物、未成年人性内容、性暴力、制毒贩毒；
  - `review`：剧情里的自杀 / 血腥 / 杀人、裸露与性暗示、侮辱性粗口、歧视称呼、未成年人亲密关系、暴富承诺、迷信、导流与消费诱导、烟酒赌博。
- 每条规则在一段文本里只报第一次命中，同时给命中词、前后各 14 字上下文与人话位置（`第 2 场 · 第 3 镜 · 描述`、`台词 · 林昭`）。

扫描对象是项目里所有会进入成片或发布文案的用户文本：标题、故事 logline / 梗概 / 类型 / 受众 / 调性 / 钩子、人物弧光与关系张力、角色外观与监工要点、场景与道具描述、分镜描述与补充指令、台词，以及成片页当前填的发布标题 / 简介 / 话题。`provenance.prompt` 不扫：它是生成记录，不是观众会看到的内容。

### 2. 预检四项，导出统一过闸

`preflightProject(project, { title, description, topics, durationMs })` 返回 `checks[]`、`findings[]`、`blocked`、`review`、`ok`、`signature`、`checkedAt`：

| 检查 | 结论怎么来 |
| --- | --- |
| AI 标识 | 导出链路固定写显式 + 隐式标识；通过 |
| 内容安全 | 规则命中：有 block 即 block；只有 review 即 review |
| 素材授权 | 有 `upload` / `imported` 资产即 review（授权台账 H7 未做）；剧本导入的 provenance 以「导入剧本」开头视为已声明原创或已获授权 |
| 平台规格 | 1080×1920 / 30fps；全长为 0 或超过 180 秒即 block |

成片页在导出区上方显示检查面板：四项检查逐条列出状态与说明，命中项列出位置、命中词、上下文与处理建议。`ok === false` 时五个导出按钮全部禁用；只有 review 时必须勾选「我确认以上内容属于剧情需要…」才放行。五个按钮的处理函数入口也再判一次，避免快捷键或旧状态绕过。

### 3. 确认绑定内容指纹

`signature` 是「全部被扫描文本 + 四项检查结论 + 命中项」的 FNV-1a 短指纹。勾选确认时记住当前指纹；标题、简介、话题、项目文本或时长任何一处改动都会让指纹变化，确认自动失效，页面回到未确认状态。这样不会出现「改了文案但确认还留着」。

### 4. MP4 清单携带证据，服务端再扫一遍

`RenderManifest` 增加必填的 `compliance`：

```ts
type RenderCompliance = {
  ok: true;
  checkedAt: string;
  signature: string;          // 8 位十六进制
  reviewAcknowledged: boolean;
  findings: number;
};
```

- 清单校验要求字段齐全、`signature` 形状正确；缺证据直接 400，不能塞空对象蒙混。
- 服务端用同一套 `scanText` 再扫标题与占位文案（`SH-xx`）。命中 block 直接拒绝；命中 review 但 `reviewAcknowledged !== true` 也拒绝。
- 发布包 JSON 也带同一份 `compliance`，便于事后追溯这条片子导出时检查过什么。

### 5. 这一轮不做的部分

- 不接图像 / 视频内容审核：没有可用的审核接口，也不该拿生成模型冒充审核模型。画面安全仍靠人工与关键帧检查点。
- 不做四个检查点各自的独立记录：目前只在成片导出前统一检查，剧本阶段与关键帧阶段没有单独闸门。
- 不做授权台账 H7：上传素材只能标 review 让作者确认，不能验证授权文件。
- 服务端只能重扫清单里出现的文本，无法复算整份项目的扫描结果；它不是防篡改边界，只是纵深防御。

## 理由

- 关键词规则不完美，但能在零额外依赖、零额外费用的前提下把明显违规挡在导出前，并把擦边内容显式交给作者确认。
- 共享纯函数让「客户端预检」与「服务端复检」用同一口径，不会出现两边结论不一致。
- 指纹绑定确认，解决的是最容易出错的场景：确认之后又改了文案。
- 把证据写进清单与发布包，先留下可追溯的字段；以后接真正的审核服务时，只需替换规则来源，闸门形状不用改。

## 后果

**正面**

- 成片页可以实际操作验证：把标题改成「一夜暴富」出现 1 处待确认、五个按钮全灰；勾选后恢复；再改一个字确认失效；改成「如何制造炸弹」出现 1 处阻断且没有确认框。
- 渲染路由即使收到手工构造的清单，也会因缺证据或标题命中阻断而返回 400。
- 发布包可回溯：里面带着导出时的检查指纹、确认状态与命中数量。

**负面**

- 关键词规则会误报（剧情需要的历史称谓、片名里的反讽）与漏报（同义改写、拼音、图片里的文字）；这是当前方案的已知边界。
- 扫描范围包含故事与人物设定，作者可能觉得「我写人物创伤也要被提示」；目前只标 review，不阻断。
- review 很多时面板会变长（最多列 8 条，其余只报数量），需要作者先处理再重看。
- 预览 HTML / OTIO / SRT 也被同一闸门挡住：合规要求覆盖所有对外文件，但这会让只想导字幕的用户也必须先过确认。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 只在服务端检查 | 页面无法在导出前告诉用户哪一句有问题，体验是点一次失败一次 |
| 只在客户端检查 | 服务端可被直接调用，等于没有闸门 |
| 接第三方内容审核 API | 当前没有可用接口与计费口径；先做可验证的本地规则，接口到位后替换规则来源 |
| 所有命中都阻断 | 短剧本身就有冲突、暴力与犯罪情节，全阻断会让正常剧本无法导出 |
| 只有一个总「通过 / 不通过」 | 作者不知道该改哪里；四项检查与命中位置是可用性的下限 |
| 确认状态只存布尔值 | 改文案后确认仍然有效，闸门形同虚设；必须绑定内容指纹 |
| 把规则写进 IR 或事件日志 | 规则会随法规与平台口径变化，不属于作品数据；指纹与确认状态只进导出物 |
