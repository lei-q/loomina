# ADR-0001 统一项目文档（Project IR）作为唯一事实来源

- 状态：已接受
- 日期：2026-11-09
- 决策者：产品 / 工程（单人）
- 关联：P2、P7、F1、E1

## 背景

AI 短剧的生产会同时产生：剧本、分镜、提示词、关键帧、视频片段、配音、配乐、字幕、发布包。若按传统方式存储（文件夹 + 零散 json + 成品 mp4），会出现：

- 无法回答"这个镜头是哪个模型、什么提示词、什么 seed 生成的"；
- 改一句台词后，下游分镜/字幕/配音无法同步；
- 剪辑、发布、模板复用各自维护一套数据，长期不可维护。

## 决策

定义一份**结构化项目文档 Project IR**（见 [DATA-MODEL.md](../DATA-MODEL.md)），作为整个系统的唯一事实来源：

1. 所有实体（故事圣经、场、镜、Take、资产、音频、字幕、发布包）都在同一棵树里。
2. 所有派生物（预览、成片、SRT、发布包）都从 IR 生成，不反向成为真相。
3. 每个生成物带 provenance（模型、seed、提示词、参考图、时间）。
4. 项目版本化，支持快照与事件日志回放。
5. 时间线通过 **OpenTimelineIO** 与外部工具交换。

## 理由

- 自动剪辑、多人协作、模板复用、发布适配，全都依赖统一数据模型；晚做要重构全部。
- provenance 是质量回溯与成本核算的前提。
- 结构化数据才能让人与 AI 同时编辑，并做"改动影响下游"的同步。

## 后果

**正面**
- 功能有统一挂载点，避免数据孤岛。
- 自动 QA、成本记账、A/B 对比都变简单。

**负面 / 代价**
- 前期建模成本高；schemal 变更需要迁移。
- 需要约束：所有功能必须先落到 IR，不能绕过。

**跟进**
- 破坏性 schema 变更写迁移脚本。
- 事件日志 vs 全量快照的取舍在实现期决定。

## 替代方案

- **文件夹 + 配置 json**：简单，但无法支撑一致性与自动化，否决。
- **只用 OTIO 作为项目模型**：OTIO 面向时间线，不承载叙事与一致性信息，否决（仅作交换格式）。
- **每类资产独立数据库**：边界清晰但一致性成本极高，单人开发不可维护，否决。
