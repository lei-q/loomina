# ADR-0006 发布策略：官方 API + 移动端分享扩展，不做逆向自动化

- 状态：已接受
- 日期：2026-11-09
- 决策者：产品 / 工程
- 关联：P9、G3、G4、R8、R9、R10

## 背景

需求是"扫码登录后一键发布到抖音、TikTok、小红书、B 站、X"。但现实是：

- **TikTok**：有官方 Content Posting API，需应用审核与权限。
- **抖音**：开放平台提供发布能力，通常需企业资质与审核。
- **B 站**：有开放平台投稿能力，需申请。
- **小红书**：**无公开发布 API**。
- **X**：有官方 API，按档位付费。

若通过逆向 Web/App 协议模拟登录与发布，属于违反平台协议，风险包括封号、接口失效、法律责任。

## 决策

采用三层发布策略：

1. **有官方 API 的平台**：OAuth 授权 + 一键发布（Phase 2）。
2. **无 API 的平台**：提供**移动端伴侣 / 分享扩展**——生成标准发布包，用户在系统分享面板选择目标 App 发布（Phase 1）。
3. **兜底**：导出成片与发布物料，手动发布。

**明确禁止**：逆向登录、模拟点击、批量养号、绕过平台风控。

## 理由

- 合规是产品能长期存在的前提（准则 P9）。
- 移动端分享是平台官方支持的路径，体验接近"一键"。
- 用户本来就更习惯在手机端发布。
- 与"桌面创作、手机发布"的分工一致。

## 后果

**正面**
- 零封号/法律风险。
- 不依赖平台开放生态的审核周期。
- 移动端 App 还可承载通知、预览、数据查看。

**负面 / 代价**
- 分享扩展的体验不如真·一键（需用户在系统面板再点一次）。
- 官方 API 的资质门槛可能长期拿不到。

**跟进**
- 发布包需内置平台规格校验（G2）。
- 记录各平台 API 申请条件与进展。
- 移动端形态（PWA / 原生壳 / 独立 App）待定。

## 替代方案

- **逆向自动化发布**：否决（R10）。
- **只做手动导出**：体验差，作为兜底而非方案。
