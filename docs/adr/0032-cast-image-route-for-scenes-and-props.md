# ADR-0032 场景主镜与道具参考图复用同一条出图路由

- 状态：已接受
- 日期：2026-11-10
- 决策者：用户 + Claude
- 关联：ADR-0028（资产层与定妆闸门）、ADR-0030（道具进镜头）、ADR-0031（服务端出图）、B8、[UX.md](../UX.md) 第九节

## 背景

ADR-0031 只通了人物三视图。定妆台另外两类必锁资产仍然停在剪影：

- **场景主镜**（`Location.masterShotId`）：`castReadiness` 已经把它算成必锁项，没锁完"进分镜"不开；但界面只有一张 `Scene` 占位图，"锁定主镜"锁的是一张不存在的图。
- **道具参考图**（`Prop.referenceImages[0]`）：被镜头引用（`Shot.propIds`）的道具同样必锁，同样没有像素。

闸门放行的是"有资产 id"，而这几类资产的 id 一直没有内容。ADR-0031 留了一句"复用同一条路由"，这一条把它做掉。

## 决策

1. **路由改为 `POST /api/asset`**，用一个判别的 `kind` 决定生成什么：

   ```json
   { "kind": "sheet",  "character": { "name", "appearance", "mustNotChange" }, "angle": "front" }
   { "kind": "master", "location": { "name" } }
   { "kind": "prop",   "prop": { "name", "description" } }
   ```

   回包统一是 `{ uri, model, prompt }`。旧的 `/api/sheet` 删除，不做兼容层——还没有外部调用方。

2. **提示词都在 `packages/pipeline`**：新增 `buildMasterPrompt(location)` 与 `buildPropPrompt(prop)`，与 `buildSheetPrompt` 并列。主镜是空镜（"无人入画"），道具是单件静物（正面、纯浅灰背景），两者都不带人物串。
3. **服务端只认业务字段，不认资产 id**：路由不接收 `assetId`。资产 id 由客户端在落事件时决定（`Location.masterShotId` / `Prop.referenceImages[0]`），服务端不知道也不需要知道项目结构。
4. **store 拆成三个入口，共用一条出图路径**：`generateSheet` / `generateMaster` / `generateProp`，内部都走 `generateOne`——发请求、校验、写一条 `asset.updated`、清进度；失败写一句人话并返回 false。三视图靠它实现"一格没成就不再往下烧钱"。
5. **进度记录从 `sheetJobs` 泛化为 `jobs`**：`Record<targetId, GenerateJob>`，`GenerateJob = {kind:"sheet",angle} | {kind:"master"} | {kind:"prop"}`。三类资产在同一块界面里各自显示"生成中…"，互不干扰。
6. **锁定即拒绝**，三类一致（准则 P14）。要重做先解锁。
7. **资产位缺失时先说话**：场景没有 `masterShotId`、道具没有 `referenceImages[0]` 时不发请求，直接在标题下写"还没有主镜的资产位"。

## 理由

- **一条路由三个 kind** 比三条路由更接近事实：它们做的事完全一样——编译提示词、调同一个图片适配器、返回一张图；差别只在提示词与展示语义。
- **服务端不懂项目**：路由只吃"描述这段东西的字段"，不吃 IR。以后换成队列或独立服务时，这个接口不用重写。
- **复用 `generateOne`** 而不是复制三遍：`asset.updated` 的形状、错误文案、进度清理只有一处，改一次三处都对。
- **主镜不写 `description`**：`Location` 目前只有 `name` 与 `templateId`，没有描述字段。与其为了提示词改 IR，不如先接受"主镜只靠场景名"，等真有需要再加字段（改数据结构要单独一条 ADR）。

## 后果

**正面**
- 定妆闸门第一次覆盖全部三类资产：人物四格、场景主镜、道具参考图都能出真图，锁定的东西终于有内容。
- 实测：走廊主镜 32 秒、搪瓷杯参考图 24 秒（`gpt-image-2`，1024×1536）。主镜出的是空走廊，道具出的是白底蓝边马克杯，与描述一致。
- 路由校验按 kind 分开：缺名字 / 未知角度 / 未知 kind 各自 400，不会把错误混成 502。
- 测试补齐：pipeline 三条（主镜空镜、道具带描述、空描述不留空句）、store 两条（主镜与道具各写一条事件、锁定的不重生成）。

**负面**
- **主镜只有场景名**：提示词里没有任何空间描述，"走廊"就只是一个走廊。同一部片里两个"走廊"会生成得几乎一样，靠的是名字不同。
- 仍然是**一次一张、同步两分钟**：没有取消、没有重试，三个场景串行点完要好几分钟。
- data URI 的体积问题照旧，主镜与道具每张约 2.4MB，进内存不落盘。
- 出图费用仍未进账本（H12 跟进项）。

**跟进**
- `Location` 加空间描述字段（或从 `templateId` 编译固定串），让主镜提示词有内容可写。
- 出图记账、对象存储、取消/重试三条与 ADR-0031 的跟进合并做。
- 参考图接口可用后，主镜与道具也改走"参考图 + 约束"路径。

## 替代方案

| 方案 | 未采用的原因 |
| --- | --- |
| 保留 `/api/sheet`，再加 `/api/master`、`/api/prop` | 三条路由做同一件事，校验与错误映射要抄三遍 |
| 路由接收 `assetId` 并自己写状态 | 服务端就要懂 IR 与事件日志；密钥边界之外不该再引入结构耦合 |
| 在主镜提示词里塞进首镜描述 | 一场多条镜头，拿哪一条都是猜；反而让主镜跟着镜头漂移 |
| 三类资产各写一套进度字段 | 界面要同时看三处状态，错误处理也要三份 |
