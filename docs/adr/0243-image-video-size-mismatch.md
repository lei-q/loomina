# ADR-0243：图像模型能用了，但首帧塞不进视频请求（诊断记录）

- 状态：已废弃（被 ADR-0245 取代：结论只在 `minimax-h3` 成立，`wan3.0` 是「收下首帧但不用」）
- 日期：2026-11-15
- 决策者：用户 + Claude
- 关联：B2、B3、P4、ADR-0162、ADR-0242

## 背景

ADR-0242 修好了视频通路（轮询到终态 + content 端点取片），纯文生视频能出片。
但「关键帧 → 图生视频」这条主路径（P4 准则）仍失败，报
`400 Part exceeded maximum size of 1024KB.`

这次把整条链路逐段拆开验证，结论如下。

## 诊断结果

### 1. 图像模型：配置问题，已解决

当前配置用的是 `gpt-image-2-c`（带 `-c` 后缀），**上游 503**：
`The upstream image response could not be validated`。

同目录下不带后缀的 `gpt-image-2` **正常出图**（实测 1.2 MB PNG，看图确认是正常画面）。
`gemini-2.5-flash-image` 也能出图。

已改：`IMAGE_MODEL=gpt-image-2`、`SEED_MODELS.image`、价目表补上可用模型。

### 2. 首帧塞不进视频请求：**供应商两侧的尺寸不匹配**

| 环节 | 实测 |
| --- | --- |
| `gpt-image-2` 出 1024×1536 PNG | **2232 KB**，base64 后 **2976 KB** |
| 代理对 `POST /v1/videos` 的单 part 限制 | **1024 KB** |
| 压到 768px PNG（773 KB / 请求体 1031 KB） | 仍 400 part 超限 |
| 压到 512px PNG（360 KB / 请求体 480 KB） | 400 `content or prompt is required` |
| 压成 JPEG（50–134 KB） | 400 `content or prompt is required` |
| 纯 prompt、不带图 | **200**（任务正常建立） |

**关键发现**：压到限值以内之后，`minimax-h3` **不再接受这张图**——
报的不是尺寸问题，而是「没有 content」。也就是说：

- 大图 → 被代理的 part 限制挡住；
- 小图 → 被视频模型拒收。

**这是两个供应商能力之间的尺寸窗口不存在**，不是代码能绕过的。

## 决定

1. **保留首帧压缩的实现**（`fitVideoFrameBytes` + `runShot` 的 `compressFrame` 钩子）：
   换一个对输入尺寸宽容的视频模型时，这条路立刻可用。
2. **如实记录这个不匹配**，不假装能修：界面与文档都说「关键帧 → 视频」当前不通，
   纯文生视频可用。
3. **探测脚本保留 `--text-only`**：那是当前唯一能跑通的路径。

## 理由

- **继续试下去收益递减**：已经排除了图片格式、尺寸、prompt 字段、体积这些变量，
  剩下的可能性都在供应商内部（模型要求的输入规格），用户侧无法观测。
- **保留压缩代码是对的**：它不是死代码——换模型或供应商修好之后就是现成能力，
  而且它已经让「大图被 part 限制挡住」这个错误不再出现。
- **诚实标注比假装修好重要**：如果把这个不匹配说成「已解决」，作者会在
  关键帧页反复点生成、每次都失败。

## 后果

**正面**

- 图像模型从「全部 503」变成「可用」，这是本轮最大的实际进展。
- 视频通路可用（ADR-0242），纯文生视频能出片。
- 首帧压缩能力就位，换模型即可用。

**负面 / 代价**

- **「关键帧 → 图生视频」主路径仍不通**，违反 P4「先图后视频」的默认路径。
  当前只能：纯文生视频（质量与一致性差），或贴视频地址导入。
- 需要向供应商确认 `minimax-h3` 要求的首帧规格（尺寸 / 格式 / 体积）。
- TTS / ASR 的 403 未变。
- 只验证了 `gpt-image-2` + `minimax-h3` 这一对组合；换 `gemini-2.5-flash-image`
  或 `wan3.0-video` 是否匹配未测。
