# ADR-0176：桶里孤儿对象的清理界面（H3 收尾）

- 状态：已采纳
- 日期：2026-11-13
- 决策者：用户 + Claude
- 关联：H3、F4、H9、ADR-0128、ADR-0129、ADR-0158、ADR-0175、R59、ADR-0034

## 背景

ADR-0158 把本机资产库的孤儿清理做安全了：白名单取所有能回放项目的地址并集，
有日志段回放不了时只列不删。但它明确把**对象存储那一半**留在「不做」里，R59 的第 ②
条也照实写着「桶里的素材不会被『清理没人引用的文件』碰到，只能手工清」。

实际状态是：`removeS3Object` 早就有了，`listS3Objects` 也能按前缀翻页列桶，
缺的只是「**列出来 → 作者看见 → 确认 → 删**」这条界面路径。作者接了对象存储之后，
`assets/` 前缀下的对象只增不减——换掉的 take、改过的参考图、删掉的项目留下的素材，
全都还在桶里，账单上看得见、界面上看不见。

H3 的收尾就从这条开始：不新增存储能力，把已经有的删除能力接到同一套白名单与两步确认上。

## 决定

1. **新路由 `apps/web/app/api/asset/remote`**
   - `GET`：按 `assets/` 前缀列桶（`listS3Objects`，内部按 continuation token 翻页），
     回 `{ configured: true, count, bytes, files: [{ uri, bytes }] }`。
     没配对象存储回 409，列桶失败回 502 并带上游的报错文本。
   - `DELETE { keep: string[], dryRun?: boolean }`：
     列桶 → 过滤掉地址在 `keep` 里的对象 → `dryRun` 时只回 `{ wouldRemove, bytes }`；
     否则逐个 `removeS3Object`，回 `{ removed, bytes, failed }`。
     没有 `keep` 数组回 400。**没有 `keep` 就不删任何东西**，不做「空清单等于全删」。
   - 凭据只在服务端。回给浏览器的只有对象地址与字节数，没有 AK / SK / 预签名 URL。

2. **前缀写死 `assets/`，不列整个桶**
   - 桶可能是和别人共用的，也可能存着本项目之外的东西。
   - `assets/` 是本项目自己的命名空间（`s3KeyOf(hash, ext)` 的默认前缀），
     只在这个范围里谈「孤儿」才说得通。

3. **白名单沿用 ADR-0158 的那一份**
   - 浏览器算：当前项目 + 所有能回放 `projectSegments` 的资产地址并集。
   - 有日志段回放不了 → 只列孤儿，清理按钮与确认按钮都停用，界面写明原因。
     这条不是重新考虑，而是同一条规则在远端生效。

4. **界面挂在「本机资产库」区里，只在配了对象存储时出现**
   - 它是同一个概念的另一半（「这台机器 / 这个桶里谁没人用」），不该另开一页。
   - 显示 `assets/` 前缀的对象数、孤儿个数与总字节、前 5 个地址（去掉 `s3://`
     以便一眼认出）、两步确认。确认句里的数字来自服务端 `dryRun`，
     不是浏览器本地数出来的——两边算的必须是同一份桶清单。
   - 清完自动重列一次，回执写「从桶里清掉 N 个没人引用的对象（约 X）」。

5. **不碰别的东西**
   - 只删 `assets/` 前缀下、且不在白名单里的对象。
   - 不删缓存目录 `.loomina/assets/cache/`（那是本机的事，归本机库那一块）。
   - 不动配置，不动 `s3://` 之外的对象，不动别的项目（无从判断，所以不猜）。

## 理由

- **删除能力已经有了，缺的是让人看见**：没有清单的删除按钮没人敢点，
  有了清单、有了字节数、有了「所有能回放的项目都没引用」这一句，作者才能自己判断。
- **同一个白名单**：本机库与桶里的对象是按同一套 `s3://` / `loomina://` 地址被引用的，
  白名单只能有一份；让两处各算一次，迟早会有一处算错。
- **`dryRun` 由服务端算**：桶是外部状态，浏览器手上那份清单是几秒前的。
  确认句里的数字必须是「此刻要删的」。
- **前缀写死**：桶的命名空间不由我们独占；列整个桶再按白名单筛，等于把别人的对象
  也当成候选，错一次就找不回来。
- **不引依赖**：`listS3Objects` / `removeS3Object` 都是 ADR-0129 自写 SigV4 的一部分，
  这次只调它们；`package.json` 一个包都没加。

## 后果

**正面**

- R59 第 ② 条的核心缺口关闭：桶里的孤儿第一次能在界面上看见、被确认后清掉。
- 清理路径和本机库对称：同一份白名单、同一个「回放不了就不删」的保守规则、
  同样由服务端给出真实删除数量。作者学一次就够了。
- 只读的 `GET` 可以随时打开看，不会删任何东西；清完立刻能重列复核。
- 凭据没有离开服务端一步；浏览器只拿到地址和大小。

**负面 / 代价**

- **只看 `assets/` 前缀**：早期手工传进桶里别的路径的对象，这个界面永远看不见，
  得去对象存储控制台处理。
- **没有分页交互**：一次全列（`listS3Objects` 内部翻页，最多 `MAX_LIST_PAGES` 页）。
  对象上十万时设置页打开会慢，而且可能列不全——列不全时删的安全边界仍然成立
  （白名单是全的），只是「该删的」会分几次才删完。
- **桶开了版本控制时，删除不会释放容量**：删掉的是当前版本，旧版本还在计费。
  这一版不处理删除标记与历史版本。
- **失败只报个数**：`failed` 给的是几个没删掉，没给是哪些。要重试就再点一次，
  白名单与桶清单会重新算。
- 缓存目录不跟着清；`.loomina/assets/cache/` 大小仍然要手动看一眼。

**不做**

- 多项目分桶（按项目前缀隔离）、分片上传。
- 日志压缩与旧事件里 data URI 的清理（下一件 H3 的事）。
- 回收站、定时清理、按容量淘汰、删除撤销。
- 桶内其他前缀的清理、跨桶清理、删除版本与删除标记。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 让本机库的 `DELETE /api/asset/store` 顺带清桶 | 一个是本机盘、一个是外部桶；删错了修法完全不同，混在一个按钮里说不清楚 |
| 列整个桶，让白名单决定一切 | 桶不是我们独占的命名空间；`assets/` 之外的对象不该出现在候选里 |
| 确认句的数字用浏览器本地算的 | 桶清单是几秒前拉的；要删多少必须由服务端此刻算 |
| 空 `keep` 就当「全删」 | 一次请求体出错就是清空桶，代价不可逆 |
| 自动清理孤儿 | 刚生成还没挂上的素材、正在换的 take 看起来都像没人用 |
| 把桶清单缓存到服务端 | 多机 / 多人共用一个桶时缓存只会过期出错；每次现列更便宜也更准 |
| 这一版顺手做多项目分桶 | 分桶要改 `s3KeyOf` 的 key 布局与旧对象的迁移，是另一件事 |
