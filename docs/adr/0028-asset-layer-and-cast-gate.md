# ADR-0028 资产层先于生成：三视图、主镜与定妆闸门

- 状态：已接受
- 日期：2026-11-10
- 决策者：用户 + Claude
- 关联：ADR-0014（多层一致性）、ADR-0026（审片台）、A9、B1、B8、[CONSISTENCY.md](../CONSISTENCY.md)、[DATA-MODEL.md](../DATA-MODEL.md) §2

## 背景

审片台能审、能写回之后，暴露出一个更靠前的缺口：**IR 里没有"资产"这层。**

- `Character` 只有 `appearance` 一段文字，没有三视图的位置；
- `Location` 没有主镜，场景锚只能靠文字描述；
- 没有 `Approval`，准则 P14"经确认锁定的资产不得被覆盖"在数据上无处安放；
- 示例项目里镜头带的参考图直接是 `characterIds`（`packages/pipeline/src/index.ts`），即"把人本身当参考图"，这在生成阶段是讲不通的。

结果是：跨镜头一致性的第一层（资产锚定）只写在文档里，代码无法引用，也无法验证。

## 决策

1. **定妆是独立阶段**，排在"剧本"与"分镜"之间，对应四道闸门里的第一道（A9）。分镜之前，脸和空间必须先钉住。
2. **新增 `Asset` 实体**：一切被生成或上传的东西（图 / 视频 / 音频）。语义不放在资产上——"这是某人的侧面"由引用它的一侧决定，同一张图可以既是侧面又是场景参考。
3. **角色三视图是四个有角度语义的槽位**：`Character.sheet = { front, threeQuarter, side, back }`，每格指向一个 `Asset`。`Character.referenceImages` 留给不带角度语义的图（表情表、服装变体）。
4. **不是所有角色都强制三视图**：有近景 / 特写镜头的角色，四格齐全才能锁；其余角色不强制，避免为群演付三视图的钱。判定看镜头数据（`shotSize`），不看用户勾选。
5. **场景的锚是主镜一张**：`Location.masterShotId`。同一空间只需要一个空间与光线的基准，多机位/细节图放 `referenceImages`。场景不做三视图——场景不是"人"，变量是机位。
6. **锁定产生 `Approval`**：`targetType`（character / location / prop）+ `targetId`，事件 `approval.updated` 按这一对 upsert；`lockedAssetIds` 是确认那一刻的资产快照，之后新增的资产不在锁内。解锁改回 `pending` 并保留同一条记录，不删除。
7. **闸门由数据决定，界面不做假放行**：`lockedCount === totalRequired` 才出现"进分镜"；`lockCast` 对 `incomplete` 的目标直接返回，UI 与 store 各守一道。
8. **示例数据不伪造真图**：`Asset.uri` 允许为空，界面用占位剪影渲染。格子的语义是真的（四张独立的图、锁的是这四个 id），像素是真的没有。

## 理由

- **一致性最强的防线最便宜，也最该先做。** 三视图和主镜是一次性成本，锁住之后每个镜头都受益；把它们放进 IR，下游（关键帧、视频、QA）才有东西可引用，`pipeline` 里"拿人当参考图"的错误才有地方改。
- **槽位化而不是数组化**：`sheet.front` 比 `referenceImages[0..3]` 多一个不可省的保证——插一张表情图不会让侧面变成正面。改角度是改字段，不是改顺序。
- **按景别决定是否必经**：近景占画面大，身份漂移最刺眼；全景里观众看不清痣。规则与 CONSISTENCY.md 的"特写严、全景松"一致。
- **场景用主镜不用三视图**：场景的一致性是"布局、家具、窗外、光位不变"，一个固定机位的主镜已经编码了这些；三视图会给出模型没见过的视角，反而增加想象空间。
- **锁定即快照**：记 `lockedAssetIds` 而不是一个布尔值，才能回答"当时锁的是哪几张""后来又加了什么"。

## 后果

**正面**
- 准则 P14 在数据与事件里都落地了；`approval.updated` 可重放。
- 定妆闸门在 store 与界面双保险；未补齐三视图的角色，锁按钮是禁用的，且有 `title` 说明原因。
- `Prop` 与 `ApprovalTargetType` 已进 schema，道具闸门只差界面。

**负面**
- 图片接口未通，三视图只能验证"语义与闸门"，验证不了"生成出来的四格像不像同一个人"。
- 三视图自身的内部一致性（同一角色的四张图两两比对）还没有验收，目前只保证"都填了"。
- 示例资产没有 `uri`，将来做导出时会缺文件；这是示例数据，不是产品行为。
- 缺格的入口只有"待生成"三个字，还不能点它去生成——生成链路没通，做一个假的排队过程不诚实。
- `lockedAssetIds` 只是数组，没有版本号；同一角色解锁再锁，历史靠事件日志，`project.approvals` 里只剩最后一次。

**跟进**
- 接通图片接口后补"生成三视图"动作；生成结果先过 intra-sheet 检查（脸 embedding 两两相似度）再允许锁定。
- 道具闸门 UI；`castReadiness` 已把 props 算进 `totalRequired`，示例项目 `props: []`。
- 解锁时提示下游影响（有多少已生成镜头引用了这批资产）。
- `pipeline` 的参考图来源改为 `assetIds`，先取 `sheet` 与 `masterShotId`。

## 替代方案

| 方案 | 未采用的原因 |
| --- | --- |
| 把四张图塞进 `Character.referenceImages`，按顺序约定 | 语义靠约定，插一张图就错位；改角度要重排 |
| 场景也做三视图 | 场景的变量是机位不是朝向；主镜 + 机位参数更省也更准 |
| 所有角色一律强制三视图 | 群演、背影、一次性的路人不需要，成本白花 |
| 锁定记成 `Character.approved: boolean` | 答不了"锁的是哪批资产"，没有时间，解锁不留痕 |
| 定妆放进分镜里做成一步弹窗 | 闸门会被顺手点掉；它是独立阶段，才有"没锁完不进分镜"的约束 |
| 先接生成、后建资产层 | 生成结果无处存放，参考图只能继续拿人凑；顺序反了 |
