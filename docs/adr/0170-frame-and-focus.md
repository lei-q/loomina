# ADR-0170：多比例适配与裁切焦点（E5）

- 状态：已采纳
- 日期：2026-11-13
- 决策者：用户 + Claude
- 关联：E5、G7、G9、H13、E4、B7 / I5、准则 P5 / P20

## 背景

到这一刻，成片只有一个形状：`buildCommand` 把每段素材
`scale=W:H:force_original_aspect_ratio=decrease,pad=W:H:(ow-iw)/2:(oh-ih)/2`
塞进 `RENDER_PROFILES` 写死的 540×960 或 1080×1920。竖屏是短剧的主场，
但同一集要发到横屏平台（B 站、YouTube、X）或方形位（小红书、朋友圈）时，
唯一的办法是导完再拿别的软件裁——那一步在 Loomina 之外，裁剪的位置、
字幕的位置、角标的位置全都要重来一遍。

`Project.look.aspect` 帮不上忙：它写进的是**生成提示词**（让模型按竖构图作画），
改它要重出全部图。分发时真正要改的是**导出**这一层。

另外，裁切会切掉画面：竖屏 9:16 裁成横屏 16:9，画面只剩中间 56% 的高度。
人站在画面上三分之一时，居中裁就把头裁掉了。没有「留住哪一块」的表达，
裁切这个选项在短剧里就没法用。

## 决定

1. **`Project.frame` 管导出，`Look.aspect` 管生成**
   ```ts
   Project.frame = { aspect: "9:16" | "16:9" | "1:1", fit: "pad" | "crop" | "blur" }
   ```
   - 与 E4 的 `grade` / `look` 同一套分工：改 `frame` 只重渲一遍，不花钱、不重出图。
   - 旧项目没有这个字段，zod 默认 `{ aspect: "9:16", fit: "pad" }`，`LOG_VERSION` 不动。

2. **`fit` 默认是 `pad`，不是 `crop`**
   - `pad` 正是以前写死的 `scale + pad` 那一条链：默认档**不改变任何滤镜**，
     旧项目重渲与以前逐字节同构。
   - 想铺满再选 `crop`；想保住构图又不留黑边选 `blur`。默认值选了最不容易出错的那个。

3. **成片尺寸按画幅推，短边固定**
   ```
   草稿 540×960 / 960×540 / 540×540
   定稿 1080×1920 / 1920×1080 / 1080×1080
   ```
   - 短边固定而不是长边固定：换画幅只换形状、不降清晰度；G7 对短边有 720 下限。
   - `FRAME_SIZES` 一张表同时给客户端（排版字幕 / 角标 / 占位图）与服务端（校验），
     清单里的 `width` / `height` 必须与画幅对得上，对不上就拒收。

4. **三种适配各是一条滤镜链，出口统一**
   - `pad`：`scale=…:decrease` + `pad=…:(ow-iw)/2:(oh-ih)/2:color=<底色>` + `setsar=1`
   - `crop`：`scale=…:increase,crop=W:H:(iw-W)*fx:(ih-H)*fy,setsar=1`
   - `blur`：`split=2` → 底路 `scale:increase,crop,gblur=sigma` / 前景 `scale:decrease` → `overlay` 居中
   - `setsar=1` 挪进取景链的出口：像素形状在这里定死，后面的 fps / trim / 淡变不再管它。
     这一条让 `frameChain` 成为**唯一**知道「素材怎么变成成片尺寸」的地方。

5. **裁切焦点是 `Shot.focus?: { x, y }`，不是主体追踪**
   - 0–1 的比例，缺省居中；只对 `crop` 有意义，`fit` 换回 `pad` 时设置先留着。
   - 不做自动识别：认人脸 / 人体要跑模型，短剧里人物位置是作者最清楚的事，
     点一下九宫格比等一个可能认错的框更可靠。ADR 标题里的「智能」在这里落到
     「点一次，之后换画幅、重渲都跟着走」。
   - 走既有 `shot.updated { focus }`，回放、撤销、历史全部免费。

6. **校验在两头都做**
   - `shot.updated` 按 `ShotFocusSchema` 解析，越界不进日志。
   - `validateRenderManifest` 校验 `frame` 与每段的 `focus`，画幅与尺寸对不上就拒收；
     不合法**拒收**而不是悄悄丢掉——作者选了横屏、成片却是竖屏，
     「看着成功其实不一样」比一次失败更难发现。
   - 预检与平台规格按**实际画幅**校验：选 16:9 发抖音时，画幅这一项当场变红。

7. **界面：顶栏「画幅」抽屉 + 时间线下的一行摘要**
   - 抽屉上半：三个形状（带小图形与定稿尺寸）、三种适配方式、导出尺寸与一句说明、
     「存画幅 / 恢复竖屏留边」。
   - 抽屉下半：每一镜一行——缩略图、焦点标记、3×3 九宫格。点一下就是这一镜的取景。
   - 时间线下：`画幅 16:9 · 裁切 · 2 镜设过焦点 · 当前 SH-03 偏上`，点开抽屉。
   - 播放器按画幅摆形状：`crop` 用 `object-fit:cover` + `object-position` 近似焦点，
     `blur` 在下面垫一层同帧模糊；预览 HTML 用同一套。**不是逐像素等价**，以导出为准。
   - 发布包记下这一版 `frame: { aspect, fit, width, height }`，ASS 的 `PlayRes` 跟着画幅走。

## 理由

- **分发时改的是导出，不是提示词**：用竖屏生成、再裁成横屏，是短剧分发最省钱的路径；
  为横屏重出全部图是另一笔钱，而且构图上常常还不如竖版。
- **默认 `pad`**：任何「默认就切画面」的改动都会让旧项目的重渲结果变样；
  默认不切，想要满屏的人自己选。
- **短边固定**：平台对短边有硬要求（720），长边跟着形状走才对得上；反过来会让
  方形与横屏的短边掉到 540 以下。
- **焦点是比例而不是像素**：素材可能换、可能重出，比例在任何尺寸下都对得上；
  像素坐标一换图就错位。
- **不做主体追踪**：识别会错，错了作者还不知道错在哪；点一下九宫格的结果是确定的。
- **两头校验**：清单里画幅与尺寸对不上时，服务端若「以尺寸为准」地渲，
  作者看到的是横屏设置、拿到的是竖屏片子。

## 后果

**正面**

- 一条片子可以按平台各出一版：竖屏发抖音、横屏发 B 站、方形发小红书，
  字幕、角标、调色都跟着走，不用离开 Loomina。
- 裁切第一次可用：每一镜能说「留住哪一块」，竖屏裁横屏不再必然切头。
- 预检当场发现「16:9 不在抖音接受的画幅里」，而不是导完才看见。
- 预览、预览 HTML、渲染三处共用 `FRAME_SIZES` / `frameChain` 与同一个焦点，
  不会各说各话。

**负面 / 代价**

- 没有自动追踪：镜头多时要点很多次（九宫格一步到位，但仍是手工）。
- 裁切会损失画面：竖屏裁横屏只留 56% 高度，这是几何事实，`blur` 是唯一的补救。
- 播放器里的焦点是 CSS 近似（`object-position` 与 ffmpeg 的 `crop` 偏移在极端比例下
  略有差别），界面写明「以导出为准」。
- 模糊填充多一路 `gblur`，草稿档长片会慢一些。
- 每一镜的焦点是镜头级，不是逐帧：镜头内主体大幅移动时只能选一个折中位置。

**不做**

- 自动主体追踪 / 人脸识别取景。
- 逐帧或关键帧级焦点动画（需要 E8）。
- 按平台一次出多版（G9，下一步）。
- 自定义画幅比例（只做 9:16 / 16:9 / 1:1 三个分发常用形状）。
- 字幕重排：横屏时字幕仍是同一套 cqw 规则，不做竖屏 / 横屏两套版式。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 复用 `Look.aspect` | 它进提示词，改它要重出全部图；分发时改的是导出 |
| 默认 `crop` | 会让旧项目重渲结果变样，且默认切画面是不可逆的损失 |
| 长边固定（横屏 1920×1080、竖屏 1080×1920） | 方形与横屏的短边会掉到 540 以下，过不了平台下限 |
| 自动主体追踪取景 | 识别会错且错得没有提示；作者点一下是确定的 |
| 焦点存像素坐标 | 换图、重出、换分辨率都会错位 |
| 清单里画幅与尺寸对不上时以尺寸为准 | 作者看到横屏设置、拿到竖屏片子，比一次失败更难发现 |
| 用 `scale=…:force_original_aspect_ratio=increase` 再 `crop` 居中 | 不能选位置，竖屏裁横屏必切头 |
| 单独做一套横屏字幕版式 | 竖屏 / 横屏各一套规则，预览、ASS、渲染三处都要分叉；先用同一套 |
