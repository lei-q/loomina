# ADR-0011 Project IR 以 JSONB 文档 + 事件日志存储

- 状态：已接受
- 日期：2026-11-09
- 决策者：工程
- 关联：P2、P7、F1、F2

## 背景

Project IR（[DATA-MODEL.md](../DATA-MODEL.md)）是一棵深层嵌套的树：项目 → 故事圣经 → 分集 → 场 → 镜 → Take → 资产。它有三个特点：

1. **频繁演进**：早期字段会不断增删；
2. **整体读写**：编辑器通常一次加载整棵树；
3. **需要版本与撤销**：多 Take、非破坏、回滚。

传统关系表建模（每类实体一张表）在这种场景下：

- 每次 schema 变化都要写迁移；
- 读取整棵树要多次 join；
- 历史版本难以表达。

## 决策

采用 **JSONB 文档 + 追加式事件日志 + 周期快照**：

1. 项目文档整体存为 `projects.doc jsonb`，用 Zod 在边界校验。
2. 每次修改写入 `project_events`（append-only），记录 patch、时间、操作者。
3. 每 N 条事件或每日生成一次全量快照 `project_snapshots`。
4. 撤销 = 回放/反向 patch；回滚 = 载入快照 + 重放到目标版本。
5. 需要查询的字段（owner、status、updated_at、episode 数）做**投影列**并建索引。
6. 资产本体存对象存储，DB 只存元数据与引用。

## 理由

- 与 IR 的"文档"本质一致，读写简单。
- 事件日志天然支持撤销、审计、协作（未来 CRDT 的过渡形态）。
- 迁移成本低：新增字段只需改 Zod 与默认值。
- Postgres 足够，无需引入文档数据库。

## 后果

**正面**
- 数据结构演进快，返工少。
- 撤销/历史/审计是"免费"的。
- 单库即可，运维简单。

**负面 / 代价**
- 文档可能变大（多 Take、长项目），需要分片或懒加载。
- 跨项目查询能力弱，需要投影表。
- 事件日志需要压缩/归档策略。

**跟进**
- 定义事件格式与版本号；事件不可变。
- 大资产（视频）绝不进 JSONB。
- 若单文档超过阈值（如 5MB），把 `takes`、`assets` 拆为子文档并引用。
- 破坏性 schema 变更写迁移脚本，并记录在 ADR。

## 替代方案

- **全关系表**：查询强，但演进与整树读取成本高，否决。
- **MongoDB 等文档库**：多一个基础设施，Postgres JSONB 已够，否决。
- **完整事件溯源 + CQRS**：能力过剩，复杂度高，只取"事件日志"部分。
