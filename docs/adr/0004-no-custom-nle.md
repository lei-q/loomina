# ADR-0004 不自研 NLE：OTIO + WebCodecs/WebGPU + ffmpeg 组合

- 状态：已接受
- 日期：2026-11-09
- 决策者：工程
- 关联：P1、P10、E1、E6、E7

## 背景

"内置剪辑工具"是需求核心之一。选项：

A. 从零自研专业 NLE（时间线、轨道、转场、调色、特效、字幕动画……）
B. 直接嵌入开源 NLE（如 Shotcut/Kdenlive 的 MLT 后端，或 Web 编辑器组件）
C. 组合开源组件：结构化时间线 + 浏览器预览 + 服务端渲染

## 决策

采用 **C**：

- **数据层**：OpenTimelineIO 作为时间线交换格式。
- **预览层**：WebCodecs + WebGPU 在浏览器内实时预览（低分辨率代理）。
- **渲染层**：服务端 ffmpeg（必要时 GPU）出定稿。
- **交互层**：只做短剧需要的时间线操作，不追求专业 NLE 全功能。

## 理由

- 自研 NLE 是数人年投入，且很难超过剪映；对单人开发不可行。
- C 端用户要的是"改 AI 初稿"，不是"从零剪片"（准则 P6/P10）。
- OTIO 天然对接达芬奇/Premiere/MLT，给专业用户留出口。
- ffmpeg 成熟、可脚本化、可集群，适合服务端定稿。

## 后果

**正面**
- 数周内可交付可用的时间线。
- 与外部工具互通，降低锁定。
- 预览与渲染解耦，成本可控。

**负面 / 代价**
- 浏览器对高码率/多轨的支持有上限，需要代理与降级。
- 复杂特效能力弱于专业 NLE（可接受）。
- OTIO 与 IR 需要双向映射（单向导出即可）。

**跟进**
- 明确预览分辨率/帧率上限与降级策略（开放问题）。
- 评估 WebCodecs 在目标浏览器的兼容性。

## 替代方案

- **A 自研 NLE**：否决，投入产出比不成立。
- **B 嵌入 MLT/Shotcut**：桌面端绑定重、Web 化困难、定制受限，作为后备。
- **纯云端渲染、无实时预览**：体验差，否决。
