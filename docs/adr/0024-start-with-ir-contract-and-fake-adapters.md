# ADR-0024 S0 从 IR 契约与假适配器起步

- 状态：已接受
- 日期：2026-11-09
- 决策者：用户 + Claude
- 关联：P2、P8、P12、ADR-0001、ADR-0011、KICKOFF.md

## 背景

讨论已经覆盖了故事、分镜、表演、声音、成本、发布、界面。现在要决定"第一行代码写什么"。

常见起手式是 `npm create next-app`，先搭界面。但对这个项目，那是高风险选择：

- IR 是唯一事实来源，改一次会波及全部下游；
- 单人开发，重写前端的成本无法承受；
- 真模型接入受资质、单价、限流影响，早期不该成为阻塞；
- 团队（一个人）最缺的是"可验证的反馈"，而不是"好看的界面"。

## 决策

**S0 只做三件事：IR 契约、假适配器、事件日志。**

1. 建立 pnpm monorepo，依赖方向单向：`ir ← gateway ← pipeline`。
2. `packages/ir` 用 zod 定义 schema，先做 5 个实体：Project / Scene / Shot / DialogueLine / Character。
3. 先实现 10 条最关键的不变量，每条配正反测试。
4. `packages/gateway` 先写 `FakeImageAdapter` / `FakeVideoAdapter`，返回本地样片。
5. 事件日志第一版：append-only `events.jsonl` + `rebuild` + 快照。
6. S0 验收：`pnpm test` 全绿；Fake 链路能产出 2 图 + 2 视频并写回 IR；rebuild 与快照一致。
7. 第一周明确不做：UI、登录、支付、真模型、Postgres、3D、OTIO、部署。

## 理由

1. **契约错了，后面全错。** 先把它写成可编译、可测试的代码，成本最低。
2. **假适配器让链路先跑通。** 没有 API key、没有网络、没有费用，测试稳定，还能提前暴露"契约不够用"。
3. **接口先行（P8）。** 今天 Fake，明天真模型，业务代码不动。
4. **事件日志是撤销/审计/并发的地基**（ADR-0011），越早做对越省事。
5. **每一层由真实需求拉出来，而不是提前推进去。** 避免过度设计。

## 后果

**正面**
- 第一周就有可验证产物，不依赖外部服务。
- 数据模型在写 UI 之前被真实链路检验过。
- 换模型、加 UI、上数据库都不会推翻地基。

**负面**
- 没有可视界面，前期"看起来没进展"。
- Fake 适配器可能掩盖真实模型的边界，必须在 S1 用真模型重测。

**跟进**
- S1 接入真实模型后，回填能力矩阵与真实单价。
- S1 再引入 Postgres + Drizzle（项目数 > 1 或需要并发时）。
- S1.5 引入 3D 灰盒；S4 引入 Web 前端；S5 引入 OTIO。

## 替代方案

- **先做 UI 原型**：好看但数据模型未验证，返工风险高，放弃。
- **先接真模型跑通生成**：受资质/单价/限流影响，且没有契约约束会写出一次性代码，放弃。
- **先做 3D**：依赖分镜契约，顺序反了，放弃。
