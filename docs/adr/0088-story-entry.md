# ADR-0088 故事入口：一次生成故事骨架，确认后才换项目

- 状态：已接受
- 日期：2026-11-11
- 决策人：用户 + Claude
- 关联：ADR-0017（故事层）、A1 / A3 / A4、STORY.md、STORYBOARD.md、准则 P5 / P7 / P14

## 背景

A1（一句话 / 大纲 → 故事梗概）、A3（场次与分镜自动拆解）、A4（Story Bible 自动抽取）一直停在「待设计」。项目从示例项目启动，用户没有一条「从想法开始」的路：要先在剧本页手建场次，再去定妆页建人物，故事层本身没有入口。

三个功能共享同一份输入与同一份输出，拆成三个独立对话框只会让用户把同一个想法贴三遍：

- 输入是「一句话前提 / 一段大纲」；
- 输出必须同时包含 logline、人物（含弧光）、地点、道具、场次、镜头与初稿台词；
- A1 只要梗概，A3 要把场次与镜头写进 IR，A4 要把人物弧光留给下游引用。它们是一条流水线上的三段，不是三件事。

技术上还有一个此前未验证的前提：供应商的文本模型能不能用。2026-11-11 探测 `GET /v1/models`：74 个模型里 46 个 `chat`；`qwen3.8-max` 返回 403 `No authorized bound group supports this request`，`claude-sonnet-5-5` / `claude-haiku-5-5` 正常返回。文本生成这条路是通的，但必须显式配置 `TEXT_MODEL`，不能猜一个默认值。

## 决策

1. **一个入口、一次生成、三段产物。** 新页面 `/story`：用户写一句话或一段大纲，服务端一次调用文本模型，返回一份 `StoryDraft`（标题、logline、梗概、题材、受众、基调、人物与弧光、关系、地点、道具、场次、镜头、初稿台词、结尾钩子）。A1 / A3 / A4 共用这一次调用，避免同一想法贴三遍、三次计费。
2. **生成结果只是草稿，不自动写 IR。** `StoryDraft` 留在页面内存里，刷新即丢；页面逐段展示人物、关系、场次与镜头。用户点「用它开工」并确认后，才用草稿构造一个**新项目**，写一条新的 `project.created`。不自动覆盖、不逐条追加到现有项目——故事入口的语义是「开一个新项目」，不是「往当前项目里塞东西」。
3. **Story Bible 进 IR 的第一刀只收能被下游引用的字段。** `Project.story` 新增：`logline` / `synopsis` / `genre` / `audience` / `tone` / `hooks { opening, ending }` / `arcs[]`（按 `characterId` 引用 want / need / wound / flaw / secret / agency / arc）/ `relationships[]`（from / to / tension）/ `provenance`（文本模型与原始输入）。Beat、ScriptDoctorReport、OriginalityReport 不在这一刀里；它们是 A11 / A2 / A8，需要各自的评分标定，先不造空壳。
4. **草稿到项目的映射是确定性的，且必须过现有不变量。** 人物 / 地点 / 道具 / 场次 / 镜头 / 台词按固定前缀生成 id；台词时长沿用 0.3 秒 / 字的估算（P5 的临时口径），镜头时长 = 本镜所有台词时长 + 1000ms 表演余量，正好落在 `SHOT_DURATION_VS_DIALOGUE` 的允许范围内（最短一句 800ms 时偏差 500ms 仍不超过容忍下限）；没有台词的镜头给 5 秒。1 秒而非 500ms 是实测口径：500ms 余量让一份 12 镜 18 句的草稿只有 55 秒，成片会短于 60 秒。场次地点按名字匹配，匹配不上退回第一个地点；人物 / 道具名字匹配不上就不挂引用，不编造 id。构造完成后调用 `assertValidProject`，不合法就拒绝开工并如实报错。
5. **文本模型走网关的 OpenAI 兼容接口。** 新增 `TreecloudChatAdapter`：`POST /v1/chat/completions`，请求只带 `model / messages / max_tokens`。**不传 `temperature`**：实测 `claude-sonnet-5-5` / `claude-haiku-5-5` 在代理上只接受默认值，传 0.7 直接 400。模型取 `TEXT_MODEL`；没配就抛 `text_not_configured`（500），一个请求都不发。这与 TTS / ASR 的「没配就说没配」是同一套。`max_tokens` 用 16000：一份草稿约 8–11k completion tokens，其中一半是推理；8000 时实测 JSON 在 72 秒后被截断。
6. **服务端路由 `/api/story`。** GET 只回「有没有配文本模型 + 模型名」；POST 收 `{ idea, genre? }`，长度上限 2000 字，返回 `{ draft, model }`。模型输出先剥 Markdown 代码围栏、取第一个 `{` 到最后一个 `}`，再用 zod 校验；校验失败回 502 并带第一个字段错误，不把半截 JSON 写进项目。供应商失败按 502 透传，参数问题回 400。
7. **提示词写死短剧约束，而不是让模型自由发挥。** 系统提示要求：竖屏 60–90 秒、1–2 场、主要人物 3–5 个、总镜头 10–14 个、除最多 2 个空镜外每镜都有人说话、台词总量 12–18 句、每镜 ≤ 2 句台词、单句 ≤ 15 字、前 3 秒必须有钩子、结尾留钩、只写能拍出来的动作；输出字段与枚举值在提示词里逐项列出，只允许 JSON。枚举（景别 / 机位 / 运镜）与 IR 的 `CameraSchema` 对齐，模型不给中文自由词。
8. **故事页如实标状态。** 没配 `TEXT_MODEL` 时生成按钮禁用并写「还没配文本模型：服务端加上 TEXT_MODEL 之后才能生成」；生成中显示进行中；失败显示原因；生成成功标「由 <model> 生成」。不把 403 伪装成「生成失败」。

## 理由

- **一次生成而非三次**：三段产物共享人物、地点与场次，分开生成必然出现「梗概里的名字和分镜里的名字对不上」。一次生成、一次校验，至少保证这一份草稿内部自洽。
- **草稿不落 IR**：模型输出会有错名字、错时长、多余人物。直接写事件等于把一次未经确认的生成当成事实，回放与撤销都会变重。草稿只是屏幕上的候选，确认才产生项目。
- **新项目而不是合并**：故事入口回答的是「从零开始」。往现有项目里塞人物与场次，会和已有场号、地点、台词冲突，还要处理「保留哪些」。开新项目语义清楚，旧日志留在本地不被物理删除。
- **Story Bible 只收可引用字段**：`arcs` 按 `characterId` 引用，下游拿得到「这个人想要什么」；Beat / 评分还没有可靠的标定与界面，先存只会变成没人读的字段。
- **不传 temperature**：代理对 Anthropic 模型的参数限制是硬的，传了就是 400。少一个可调参数，换来一次就能调通。
- **确定性映射 + 不变量**：模型给的是内容，id、时长、双向引用由代码定。这样草稿再离谱，写进项目的也是一份能通过 `validateProject` 的结构。

## 后果

**正面**

- 从一句话到可编辑的场次 / 镜头 / 台词，只要一次生成 + 一次确认；生成后能直接在剧本页、定稿页继续改。
- 实测一份 12 镜 18 句的草稿估时 59.8 秒，贴近 60–90 秒目标；时长在页面上与落项目后一致。
- A1 / A3 / A4 一次落地，三者共享同一份草稿，名字、地点、人物关系不会各说各话。
- Story Bible 的 logline、人物弧光、关系张力进了 IR，后续 A11 Beat / A2 剧本医生 / A18 改写有地方挂。
- 文本模型不可用时界面说清楚缺哪个配置，不产生「按钮点了没反应」。
- 不自动改 IR：生成结果错了，最坏是重生成一次，不会污染事件日志。

**负面**

- **一次调用生成全部内容，质量上限受单次输出限制**：60–90 秒的体量够用，长片或系列会需要分步生成与人工闸门。
- **没有重试修复**：JSON 不合格直接报错，用户要重新生成；不自动再问模型一次（多一次计费与更长等待）。
- **没有逐段重生成**：不能只重写人物或只重写第三场，只能整份重来。
- **草稿刷新即丢**：没有本地暂存；生成一次的成本无法在刷新后复用。
- **开场钩子只从第一镜描述推断**：`hooks.opening` 用第一镜描述填入，不是模型单独评分过的 hook；Hook 评分（A15 / A19）仍未做。
- **旧项目日志仍在本地**：开新项目后，旧事件从回放起点之后不再生效，但物理上仍占 IndexedDB；回收策略未做。
- **文本模型单价未知**：`/v1/models` 没有 chat 计价，生成成本暂时只能看账单；没有写进预算 / 已花。

**跟进**

- 文本模型配额与计费确认后，把单次故事生成的估价接进预算（与 ADR-0033 的价目表分开，按 token 计）。
- 逐段重生成：先做「只重写人物」与「只重写某一镜」，仍走草稿、仍不自动写 IR。
- 把 `StoryDraft` 暂存到 IndexedDB 草稿区，刷新后能接着看（明确标「草稿」，不进事件日志）。
- Beat 分析与 Logline 评分（A11 / A15）在草稿结构稳定后再做。
- 导入剧本 txt（F6）复用同一份 `StoryDraft` 与落项目映射。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| A1 / A3 / A4 各做一次模型调用 | 同一想法贴三遍、三次计费；名字与地点容易对不上 |
| 生成后直接写 IR | 未确认的模型输出成为事实，错误要逐条删；回放与撤销变重 |
| 往当前项目追加人物与场次 | 与已有场号、地点、台词冲突；「保留哪些」说不清 |
| 硬编码一个默认文本模型 | 供应商模型可用性会变（qwen3.8-max 已 403），猜默认值会把 403 说成生成失败 |
| 传 `temperature` 提高多样性 | 代理对 Anthropic 模型只接受默认值，传了直接 400 |
| 让模型直接输出中文景别 / 机位词 | 下游要枚举，中文自由词还得再做一层映射，错一个词就整份失败 |
| 把 Beat / ScriptDoctor 一起塞进 IR | 评分标定与界面都没有，先存只会变成没人读的字段 |
