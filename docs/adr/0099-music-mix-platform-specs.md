# ADR-0099：配乐床、确定性 ducking、两遍响度归一与版本化平台规格

- 状态：已采纳
- 日期：2026-11-11
- 关联：C4、C12、G7、C7、G1、G8、R35、R36、ADR-0086、ADR-0091、ADR-0093、ADR-0095、ADR-0098

## 背景

`SOUND.md` 定的混音口径是：台词期间音乐压低 12–18 dB，整片 ≈ −14 LUFS、真峰值 ≤ −1 dBTP，并检查单声道兼容；不变量 26 / 27 / 28 要求「未经 ducking 的音乐不得进入混音」「成片必须通过响度与真峰值检查」「音乐资产必须有授权引用」。

`PUBLISHING.md` 要求平台规格不写死在代码里，维护成 `PlatformSpec` 表并定期校验。`FEATURES.md` 里 C4、C12、G7 都还是「待设计」，但成片页已经有完整的渲染链路（ADR-0091 / ADR-0093）与导出闸门（ADR-0095），缺的正是音乐、响度与平台校验这三段。

现实约束：

- 当前没有音乐生成接口，也没有平台开放平台资质。不能假装「按情绪生成配乐」或「已按平台官方规格校验」。
- 本机 ffmpeg 可用，`loudnorm`、`aphasemeter`、`alimiter` 都能跑；渲染队列已存在，可以在编码前多跑一遍混音与测量。
- 用户要求每个功能都能在 UI 上操作验证，所以这一轮必须给出可点、可听、可量、可拦截的完整路径。

## 决策

### 1. 配乐先做「导入有授权的音乐」，不做生成

`Timeline` 增加 `music: MusicCue[]`：

```ts
interface MusicCue {
  id: string;
  assetId: string;        // 必须是 kind === "audio" 的资产
  title: string;
  mood: string;           // 作者标的情绪，不参与自动选曲
  startMs: number;
  durationMs: number;
  gainDb: number;         // -40–0，默认 -18
  duckDb: number;         // 12–18，默认 15
  ducking: boolean;       // 默认 true
  loop: boolean;          // 默认 true：4 秒的音乐可以铺满 60 秒的片子
  licenseRef: string;     // 必填，空串直接拒绝写入
}
```

写入只走一条新事件 `timeline.music.updated { music }`，整条替换；与 `timeline.updated` 分开，因为换 take 不该顺手重写音乐。`applyEvent` 当场校验：id 唯一、资产存在且是音频、授权备注非空、起点 / 时长为整数、起点在成片之内、增益与 ducking 深度在范围内。`timeline.updated` 与 `shot.removed` 都保留现有 `music`，不会因为改画面把配乐清掉。

成片页的配乐区：读入本地文件（`audio/*`，≤ 18 MB，用 `<audio>` 元数据量时长，< 500ms 拒绝），选情绪，填授权来源（必填），加入后显示时长与「循环铺满 · 全片 n 秒」，两个滑杆调基准增益与 duck depth，一个勾选控制 ducking，可试听、可移除。文件以 data URI 存在资产里，和配音轨同一条本地路径；对象存储仍缓（H3）。

**不做**：音乐生成、按情绪曲线自动选段（C10）、BPM 卡点（C5）、音效层（C6）、逐段多 cue 混排。当前只允许一条配乐床，数据模型允许将来多条。

### 2. Ducking 用已知台词窗，不用 sidechain 压缩

混音时把这一版时间线里所有有音轨的台词窗（`startMs` → `startMs + durationMs`）合并（间隔 ≤ 500ms 视为一口气），生成 ffmpeg `volume` 表达式：

```
base * if(lt(t,start-0.2),1,
         if(lt(t,start),1-(1-duck)*(t-(start-0.2))/0.2,
           if(lt(t,end),duck,
             if(lt(t,end+0.3),duck+(1-duck)*(t-end)/0.3,1))))
```

- 压深是写死的：界面说 15 dB，表达式里的因子就是 `10^(-15/20)`，不随对白电平漂。
- 台词前 200ms 起坡、结束后 300ms 抬回，避免咔哒声。
- 音乐先 `aresample=48000`，按 `endMs - startMs` 截取，再 `adelay` 到起点；`loop: true` 的输入加 `-stream_loop -1`，由 `atrim` 截到成片长度。
- 对白与音乐各自 `amix` 成一条总线，再用 `normalize=0` 合成，避免 ffmpeg 自动把两条都压小一半。
- 混音单独输出 PCM s16le 48k 立体声 wav，不塞进最终编码命令：先拿到可量的混音文件，视频失败重试时也不用重新混音。

### 3. 两遍 loudnorm + 输出后复测

1. 第一遍只量：对混音 wav 跑 `loudnorm=print_format=json`，从 stderr 取最后一个 JSON 块（`input_i / input_tp / input_lra / input_thresh / target_offset`）。量不到（`-inf`、没有 JSON）就记为未测。
2. 编码时用第二遍：`loudnorm=I=-14:TP=-1.5:LRA=11:measured_I=…:measured_TP=…:measured_LRA=…:measured_thresh=…:offset=…:linear=true`。TP 取 −1.5 而不是 −1，给 AAC 编码抬升留 0.5 dB 余量，保证成片仍 ≤ −1 dBTP。
3. 没有测量值时不编 `measured_*`，退回动态 loudnorm（`I=-14:TP=-1.5:LRA=11`），并在报告里标「未测」。
4. 编码完成后再量一次成片：集成响度、真峰值，另跑 `aphasemeter` 取 `out_phase_duration` 与 `mono_duration`。
5. 判定：集成响度偏离 −14 ± 1 LU 或真峰值 > −1 dBTP（容差 0.05）→ `fail`，**不交付文件**，错误写「响度检查没通过，没有交付：…」；反相时长 > 500ms → `review`，照常交付但写明「单声道折叠可能抵消」；没有可测音频 → `unmeasured`；其余 `pass`。

结果 `LoudnessReport` 随任务状态回到成片页，配乐区显示「上次成片响度实测 · 达标 / 需复核 / 未达标 / 未测」与数值；导出结果那句话也带上 `loudness.detail`。

### 4. 平台规格：版本化表，硬项少而确定，参考项如实标注

新增 `apps/web/lib/platforms.ts`：

- `PLATFORM_SPEC_VERSION = "2026-11"`，发布包记录 `specVersion`。
- 9 份规格：抖音、快手、小红书、B 站、视频号、TikTok、YouTube Shorts、X、通用（不按平台卡）。
- 每份包含画幅、主分辨率参考、时长上下限、文件上限、编码（H.264）、帧率、封面比例、标题字数、话题数量、码率区间、字幕模式、发布方式、`reference` 字段列表与一句备注。
- **硬校验只有四项**：画幅、时长上下限、编码、帧率（帧率不符是 review，不 block），另加分辨率短边 ≥ 720 与文件大小（若有公开上限）。标题字数、话题数量、码率、封面只标 `reference: true`，超了只提示，不拦导出。
- 各规格的 `durationMs` 只写有公开依据的值：抖音 15s–15min、快手 ≥15s、YouTube Shorts ≤180s、X ≤140s（普通账号）；其余不设硬性时长。所有平台都没有可引用的公开文件上限，所以文件大小恒为参考项。
- 「通用」不冒充任何平台：画幅 9:16、1080×1920、无时长上下限，`reference` 写「所有平台字段」，发布方式为 `export-only`。

`preflightProject` 的平台规格检查改用 `validatePlatform`，并保留产品自己的 180 秒上限（G2 的产品口径）。成片页导出区新增目标平台下拉与「平台规格」逐项列表，改平台立即重算预检与按钮状态；标题 / 话题改了也立即重算。

`buildPublishPackage` 增加 `platform`、`platformName`、`specVersion`、`platformChecks`，并在有硬阻断时写进 `warnings`；音乐元数据（标题、情绪、增益、duck、授权来源）也进发布包，便于事后追溯用了什么音乐。

### 5. 这一轮明确不做的部分

- 不接平台开放平台 API，不做自动发布（G4）、分享扩展（G3）、多平台版本渲染（G9）。
- 不在服务端按平台码率转码：成片固定 1080×1920 / 30fps / H.264 + AAC，码率由 ffmpeg 默认质量决定；平台码率区间只展示。
- 不做封面生成（G6）与标题 / 话题的自动适配。
- 不做音乐版权核验：只要求作者写授权来源，发布包带着它。授权台账（H7）仍未做。
- 不做多 cue 音乐编排、淡入淡出曲线、音效层；C4 的「生成」与 C10 的情绪曲线仍在队列里。

## 理由

- 用导入 + 授权备注替代假生成，是当前唯一能诚实交付的 C4：作者拿得到能听的音乐，也知道自己声明了什么。
- 用已知台词窗而不是 sidechain，是为了让「15 dB」可核对：表达式里的因子固定，测试能直接断言；sidechain 的压缩量会随对白电平变化，无法承诺具体数字。
- 两遍 loudnorm 是 ffmpeg 官方推荐路径；先量后归一比单遍动态归一稳定，成片再测一次则避免「参数写了但输出没达标」。
- 平台规格把「能确定的结构」与「会变的参考值」分开，硬拦不会因为平台改标题字数而误伤，参考值也不会被冒充成官方规则。
- 所有校验都放在共享纯函数里，页面、预检、发布包、服务端清单用同一口径，测试可以逐条断言。

## 后果

**正面**

- 成片页可完整操作验证：读入 4 秒 mp3 → 填入授权 → 加入配乐 → 调增益 −22、压深 18 → 试听 → 切平台 → 预检 → 渲染。实测输出 5.5 秒、1080×1920、H.264 + AAC，独立复测 −14.05 LUFS / −12.61 dBTP，页面报告 −14.1 LUFS / −12.6 dBTP。
- 抖音默认规格会如实挡住 5.5 秒的测试片（下限 15 秒），五个导出按钮全灰；切到「通用」后平台规格通过，再勾选素材授权确认，导出恢复。这是本轮可复现的拦截路径。
- 发布包可追溯：`platform: "generic"`、`specVersion: "2026-11"`、六项 `platformChecks`、音乐元数据（−22 dB / duck 18 / 授权备注）都在 JSON 里。
- 旧项目不受影响：`TimelineSchema.music` 默认 `[]`，旧事件日志照常解析，日志版本不必升。

**负面**

- 音乐是本地 data URI，18 MB 上限意味着长曲子要么压缩要么截短；对象存储（H3）到位前，大文件会顶到浏览器存储与清单体积上限。
- 一条配乐床铺满全片，无法按段落换曲；C10 的情绪曲线与多 cue 混排要等下一轮。
- ducking 窗来自「这一版时间线里有音轨的台词」，没有音轨的台词不压低音乐；这是有意的（没有声音就没有遮挡），但作者可能期待「有台词就压」。
- 输出响度不合格时整条片子不交付，作者只能调增益 / 压深后重渲；没有自动二次归一。
- 平台规格中的标题字数、话题数、码率、封面都未逐条复核，随时可能过时；硬校验也只覆盖画幅 / 时长 / 编码 / 帧率，不等于平台一定接受。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 先做音乐生成 | 没有可用接口；假装生成会让作者拿到不可控、无授权的音频 |
| 用 sidechain 压缩做 ducking | 实际压深随对白电平漂，无法承诺 12–18 dB；表达式方案可测可断言 |
| 单遍动态 loudnorm | 输出响度波动更大，且无法提前知道要归一到多少；两遍先量后线性归一更稳 |
| 渲染后不复查响度 | 参数写了不等于输出达标，AAC 编码还会抬真峰值；必须测成片本身 |
| 所有平台字段都硬拦 | 标题字数、话题数、码率会随平台调整，硬拦会误伤正常导出 |
| 只做「通用」不列平台 | 作者不知道目标平台的结构差异；列出来但标清参考值更有用 |
| 把平台规格写死在预检里 | `PUBLISHING.md` 明确要求版本化；发布包需要记下按哪版校验 |
| 音乐与画面共用 `timeline.updated` | 换 take 会顺手重写音乐，事件语义混乱，回放与审计都更难 |
