# ADR-0101：双档渲染与重试上限 / 超预算降级

- 状态：已采纳
- 日期：2026-11-11
- 关联：H13、H10、E6、F9、ADR-0022、ADR-0035、ADR-0100、R28、R39

## 背景

`ADR-0022` 定了成片规格「1080×1920 / 30fps」，`E6` 把渲染做成「浏览器排版 → 服务端 ffmpeg」。问题出在节奏上：草稿阶段每改一次都要按定稿规格重渲一遍，5–30 秒的片子也要几十秒，作者不敢频繁看片；而真正交付前又必须有一份高质量文件。`FEATURES` 里 H13 一直是「待设计」。

H10 只做到了金额上限（ADR-0035 / ADR-0100）：项目与单镜都能拦超预算，但重试次数写死 3 次，超预算只有「阻断」一种处置。反复重抽一镜既可能超预算，又可能只是供应商不稳定，作者需要能选「就停在这，别再花钱」。

约束：

- 单人开发，ffmpeg 在本机跑，编码耗时直接占掉作者的操作节奏。
- 草稿要快，定稿要稳；两档必须有明确边界，不能出现「标着草稿却按定稿编码」的清单。
- 定稿只在成片阶段确认之后才允许导出，避免把未确认版本当交付物。
- 预算拦截仍在客户端，服务端渲染只按清单执行（ADR-0100 的边界不变）。

## 决策

### 1. 两档渲染：`draft` / `final`

`apps/web/lib/render-manifest.ts` 增加 `RenderQuality` 与 `RENDER_PROFILES`：

| 档位 | 尺寸 | 帧率 | CRF | preset | 音频 |
| --- | --- | --- | --- | --- | --- |
| 草稿 `draft` | 540×960 | 24fps | 30 | ultrafast | 96k |
| 定稿 `final` | 1080×1920 | 30fps | 20 | veryfast | 128k |

清单新增 `quality` 字段，服务端按档位校验尺寸与帧率：对不上直接 400，不静默改成另一档。不带 `quality` 的旧清单按定稿处理，兼容既有调用方。

浏览器端 `buildRenderManifest(view, style, compliance, quality)` 按档位画占位图、字幕与角标（字号与位置按宽度比例缩放），`exportMp4` 把档位一路带到 `/api/render`；服务端 `buildCommand` 从 `RENDER_PROFILES[manifest.quality]` 取 preset / CRF / 音频码率。

成片页新增「渲染档位」切换：默认草稿，定稿按钮在 edit 闸门确认（`stageStateOf(project, "edit").gate === "confirmed"`）之前禁用；导出按钮文案带档位（`导出草稿 MP4` / `导出定稿 MP4`），成功提示写清档位、尺寸与帧率。

### 2. 重试上限进 IR：`Project.maxAttemptsPerShot`

```ts
interface Project {
  maxAttemptsPerShot: number;              // 1–5 的整数，含第一次，默认 3
  onBudgetExceed: "block" | "keep";        // 默认 "block"
}
```

- 走 `project.updated { maxAttemptsPerShot?, onBudgetExceed? }`，与其他预算字段同一条事件、同一套回放。
- applyEvent 校验：重试上限必须是 1–5 的整数；处置只能是 `block` / `keep`；一条事件什么都没改就抛错。
- 老快照没有这两个字段时 zod 补默认值（3 / `block`），`LOG_VERSION` 不变。
- 视频生成的自动重试循环改为 `attempt <= project.maxAttemptsPerShot`，重试提示与最终失败文案都读当前设置；每次之间的等待仍是 `[1200, 3000]` 毫秒，超出部分按 3000 毫秒。

### 3. 超预算的两种处置

- `block`（默认）：维持 ADR-0100 的行为——发请求前拦下，提示提高预算或单镜上限，一次请求都不发。
- `keep`：同样不发请求，但文案改为「按『超预算保留现有结果』，这次不重新生成，这一镜沿用手上已有的画面」。语义是**降级为不重抽**，不是换一个更便宜的模型：没有可靠的廉价档时不编造价格，也不假装生成成功。

图像（定妆 / 关键帧 / 道具等）与视频两条生成路径都走同一判断；项目预算与单镜上限先到先拦。

顶栏预算面板新增两个下拉：`单镜最多试 1–5 次` 与 `超预算时：停下，等我处理 / 保留现有结果`，下方一句说明当前模式的效果。

### 4. 明确不做的部分

- 不新增第三档「社交平台低码率」；G7 的码率 / 文件大小目标留给收尾项。
- 不做并发渲染；队列仍是并发 1（H2 的持久化也未做）。
- 不做服务端预算复核；`keep` 只是客户端决定不调用生成。
- 不做按模态的重试上限（图像生成没有自动重试循环），也不做文本 / 语音的金额拦截（单价未知，R28）。

## 理由

- 草稿档的意义是「让作者敢频繁看片」：540×960 / 24fps / ultrafast 在 5–30 秒片长上通常几秒出片，明显快于定稿；定稿仍是平台规格要求的 1080×1920 / 30fps。
- 档位写进清单而不是服务端猜：渲染任务可能排队、可能重放，服务端只能按提交时的意图执行，不能根据尺寸临时换档。
- 尺寸 / 帧率与档位绑定校验，避免「标草稿、按定稿编码」的清单造成耗时与预期不符。
- 定稿要求 edit 闸门已确认：确认记录是「这一版成片就是这样」的明确表态，未表态的版本不该产出交付物。
- `keep` 用「不重抽」而不是「降级模型」：手上有结果时，保底比再赌一次更符合预算护栏的目的；没有可靠的廉价模型时，编一个降级档只会制造假精确。
- 重试上限进 IR 而不是 localStorage：换浏览器、导出项目、回放日志都要还原同一个上限；这也是 H10 所有数字的统一落点。

## 后果

**正面**

- 成片页可切换草稿 / 定稿；未确认时定稿灰掉并写明原因，确认后立即可选，导出按钮与成功提示都带档位。
- 实测两档都能出片：同一份 1 秒清单，草稿与定稿都返回 `done` 并下载到 MP4。
- 顶栏可把「单镜最多试」改成 4 次、「超预算时」改成保留现有结果；刷新后仍是 4 / keep，IndexedDB 里是两条 `project.updated`。
- 把预算临时改到 ¥1 后点首帧生成：一次请求都没发，提示「按『超预算保留现有结果』，这次不重新生成，这一镜沿用手上已有的画面」。
- 测试：IR 129 + gateway 28 + pipeline 30 + web 416 = 603 全过；`pnpm typecheck` 与 `next build` 全过。

**负面**

- 草稿文件名与定稿相同（只有「成片」后缀），作者下载后要靠文件大小 / 内容区分；后续可在 `renderFileName` 带档位，但会改变既有命名，先不动。
- 重试等待时间表只覆盖前两次；上限设到 5 时，第 4、5 次之间统一等 3 秒，没有指数退避。
- `keep` 只在客户端生效：绕过 UI 直接调接口仍会发起生成；与 ADR-0100 的边界一致。
- 定稿解锁只认 edit 闸门确认，不重新校验合规预检；预检在导出时仍独立执行（G8）。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 只做草稿档，交付时再手动改分辨率 | 每次都要改代码或参数，且容易忘记改回来；两档写成配置才能稳定验证 |
| 服务端按文件大小自动选档 | 作者无法预期耗时；同一清单在不同机器上可能出不同档位 |
| 草稿用 480×854 | 与 540×960 的编码耗时差别很小，但字幕与画面细节更差；540 已足够看节奏 |
| 定稿用 CRF 18 / slower | 本机编码时间显著变长，收益在短剧场景不明显；CRF 20 / veryfast 是当前交付基线 |
| 超预算时自动换更便宜的模型 | 没有可靠的廉价档与价目，换模型还会改变画面一致性；假降级比不生成更糟 |
| 超预算时静默跳过 | 作者不知道哪一镜没出；必须写清「沿用手上已有的画面」 |
| 重试上限存 localStorage | 换浏览器 / 导出项目丢失，且与其他预算数字的存储方式不一致 |
| 定稿在预检通过时就解锁 | 预检通过不等于作者确认了这一版成片；确认是明确的交付表态 |
