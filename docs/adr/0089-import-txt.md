# ADR-0089 导入剧本 txt：改写成单集草稿，确认后才换项目

- 状态：已接受
- 日期：2026-11-11
- 决策人：用户 + Claude
- 关联：F6、ADR-0088、A1 / A3 / A4、STORY.md 八（IP 来源与权利）

## 背景

故事入口解决了「从一句话开始」，但用户手里往往已经有一段小说、短篇或剧本 txt。F6 要求能把这类文本带进来。难点不在读文件，而在两件事：

1. **原文通常不是一条 60–90 秒单集**：小说有大量旁白与内心描写，剧本可能有三五场、几十句台词。直接逐字落进 IR 会超出当前单集体量，也会把不能拍的内容带进分镜。
2. **权利来源必须说清楚**：用户可能上传别人的小说。平台不做授权核验，但必须让用户明确声明，并且不把原文留在服务端。

现有 `StoryDraft` 已经有标题、logline、人物弧光、关系、地点、道具、场次、镜头与台词，草稿到项目的映射也已验证（ADR-0088）。F6 应该复用这条流水线，而不是另造一套导入格式。

## 决策

1. **在 `/story` 加第二个入口，而不是新页面。** 页面上方两个标签：「从想法开始」/「导入剧本 txt」。两者共用同一份 `StoryDraft` 展示、同一套确认开工与落项目映射；切换标签清掉上一份草稿，避免把两种来源的结果混在一起。
2. **文件只在浏览器里读，原文不落服务端磁盘。** `input[type=file]` 接受 `.txt` / `text/plain`，上限 2 MB；用 `File.arrayBuffer()` 读成文本。也允许直接把文字粘进文本框。文本随后作为一次模型请求的 user message 发给已配置的文本供应商；服务端不写文件、不建上传记录。
3. **编码按 UTF-8 优先、GB18030 兜底。** 先 `new TextDecoder("utf-8", { fatal: true })`；解不出来再按 `gb18030` 解。去掉 BOM。国内 txt 常见 GBK，直接按 UTF-8 解会变乱码，这一步比多一个依赖便宜。
4. **一次最多 2 万字。** `SOURCE_MAX_CHARS = 20_000` 由 pipeline 导出，界面与服务端共用。超过时不偷偷截断，明说「先截一段，或拆成几集分别导入」。文件本身超过 2 MB 直接拒绝。
5. **权利声明是硬门槛，但不假装是核验。** 导入模式下必须勾选「我确认有权使用这段文字（原创或已获授权）」，否则按钮禁用。勾选状态只在内存，不写日志；它是一句用户声明，不是版权审查。
6. **一次模型调用完成改编，复用同一份结构。** 新增 `importStoryMessages(source, genre?)`：与一句话生成共用系统提示里的体量与枚举约束，额外要求「保留原文的人物关系、核心冲突与结局意思；可以合并次要人物与场次；不新增原文没有的主要人物；删除旁白与无法拍摄的内心描写；不照抄大段原文」。输出仍是 `StoryDraft`，仍过 `parseStoryDraft` 与 `assertValidProject`。
7. **成片目标仍是 60–90 秒，所以台词量写死 20–24 句。** 实测 12 句只有 44 秒、18 句 55 秒，够不到 60。提示词收紧后，同一段 199 字原文生成 13 镜 / 21 句 / 62.6 秒。代价是模型会补一些反应与短句，界面必须标「改编稿」，不能说「原样导入」。
8. **确认开工才写 IR，且 provenance 只留摘要。** 与想法入口一致：草稿留在页面内存，「用它开工」→「确认开工」才构造新项目、写一条新的 `project.created`。`Project.story.provenance.prompt` 写「导入剧本（文件名）（N 字）：正文前 300 字」，不把两万字原文塞进事件日志。
9. **界面如实说是改编。** 结果标题旁标「由 <model> 改编」与「改编稿 · 原文 N 字」；输入区写「目标是 60–90 秒单集：会压缩与合并，原文不会原样保存」；生成中写 40–100 秒。读文件失败、超过上限、没勾权利、没配模型都分开说。

## 理由

- **复用而不是另起一套**：导入的真正价值是「把已有文本变成可编辑的场次 / 镜头 / 台词」，不是保留原文件。复用 `StoryDraft` 让后续的剧本页、分镜页、定妆页立即可用。
- **改编而不是逐字导入**：当前产品只做单集 60–90 秒。逐字导入会得到一条五分钟的「项目」，时间线、预算与镜头模型都没准备好。先明确改编，比偷偷截断诚实。
- **浏览器读文件**：不需要对象存储（H3 未接），也不产生上传垃圾；用户刷新就没了，与草稿的语义一致。
- **GB18030 兜底**：中文 txt 的现实格式，不处理就会把「乱码」误报成模型读不懂。
- **权利声明而非审核**：平台没有能力核验版权；能做的是让用户明确声明、保留来源摘要、提供投诉下架路径。把它写成「已审核」反而是假安全。
- **台词下限继续抬高**：体量是产品承诺，不是模型建议；用提示词与实测把 60 秒守住，比在界面上把 44 秒说成「约 60 秒」诚实。

## 后果

**正面**

- 用户手里的 txt 可以直接变成可编辑项目，仍然只需一次生成 + 一次确认。
- 原文不落盘，provenance 只留文件名、字数与前 300 字，事件日志不会被整本小说撑大。
- UTF-8 / GBK 都能读；粘贴与选文件两条路，无头环境也能测。
- 生成失败、超限、没勾权利时按钮与文案说清原因，不产生「点了没反应」。
- 导入与想法入口共享不变量与映射；导入稿同样要过 `assertValidProject`。

**负面**

- **不是逐字导入**：会删旁白、合并场次、补反应；原文的文学性会损失。这是明确的改编，不是迁移。
- **2 万字上限**：长篇需要手动截取或拆集；没有章节识别与批量导入。
- **没有保真校验**：不检查人物是否漏掉、结局是否被改；只靠提示词约束与用户自己看草稿。
- **会补原文没有的台词**：为凑 60 秒，模型可能加短句；人物立场应不变，但细节可能被发明。
- **权利声明不是核验**：用户勾选后仍可能上传无权文本；平台只有声明、来源摘要与后续投诉机制。
- **一次调用仍有质量上限**：JSON 不合格直接报错，不自动重试；不能只重写某一场。
- **原文不进日志，也不可追溯**：之后想核对「哪句来自原文」只能看用户本地文件；provenance 只有前 300 字。
- **原文会发给文本供应商**：用户需要知道导入的文字会作为一次模型请求的输入离开浏览器；隐私说明与供应商条款要在上线前补齐。
- **原文可能包含提示注入**：例如「忽略以上指令」。输出仍要过 zod 与不变量，草稿也只展示、不自动写 IR，最坏是生成失败或内容跑偏。

**跟进**

- 章节拆分与多集导入：先识别「第一章 / 第 1 集 / 场次」标题，再按集分别生成；仍走草稿与确认。
- 保真检查：人物名单、关键道具、结局句是否出现在草稿里；不通过时提示而不是静默接受。
- 原文摘要更结构化：存文件名、字数、前 300 字与一个内容哈希；不存全文。
- 导入稿的「原文对照」视图：逐场看哪些是原文、哪些是模型补的；需要先有来源标注。
- 权利与投诉流程：用户协议、下架入口与来源记录（合规层 H7 / G2 之后）。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 新开 `/import` 页面 | 与 `/story` 共用草稿、展示与确认逻辑；两个页面会让代码与文案分叉 |
| 逐字解析剧本格式，不调模型 | txt 格式没有标准，场次 / 人物写法千差万别；解析失败率高，且不解决 60 秒体量 |
| 把原文整段写进 `provenance.prompt` | 事件日志会被几万字撑大，回放与存储都变重 |
| 上传到服务端再处理 | H3 对象存储未接；没有必要的落盘与清理成本 |
| 仅支持 UTF-8 | 国内 GBK txt 很常见，乱码会被误判成模型失败 |
| 不设权利声明 | 用户可能上传无权文本；一句明确声明是最低成本的边界 |
| 保留原文全部场次与台词 | 超出单集 60–90 秒与镜头模型，时间线与预算都接不住 |
| 把 44–55 秒说成「约 60 秒」 | 与产品承诺不符；宁可收紧提示词并标「改编稿」 |
