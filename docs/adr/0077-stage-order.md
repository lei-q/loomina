# ADR-0077 出场顺序可调（人物与道具）

- 状态：已接受
- 日期：2026-11-11
- 决策者：用户 + Claude
- 关联：ADR-0065（点名即出场）、ADR-0066（道具签）、ADR-0030（道具引用即必锁）、FEATURES B1 / B8

## 背景

出场顺序就是点名顺序，也是提示词里的顺序（ADR-0065 / ADR-0066）。但顺序一旦定下就改不了：想让「周」排到「林」前面，只能先点掉再重新点一遍——两个人还好，三四个人就得全部重来，而点掉还有"这一镜有台词不能点掉"的限制（ADR-0070）。道具同理。

另外界面上的签一直按**人物库的顺序**排，与实际的出场顺序不一定一致：明明是「周，林」，签却按库里「林，周」显示，用户看不出提示词里谁在前。

## 决策

1. **挪一位，不做拖拽**：每个已出场的人物 / 道具签里嵌一对 `‹` / `›`，点一下与相邻的一位互换；到头的那一侧置灰。不用 HTML5 拖拽或指针拖动：
   - 触屏与键盘都能用，不需要额外的拖拽手柄与落点提示；
   - 一次点击写一条 `shot.updated { characterIds }`，不会产生一串中间状态；
   - 签很小、会换行，拖拽在半行处没有稳定的落点。
2. **签按出场顺序排**：已出场的人 / 道具按 `shot.characterIds` / `shot.propIds` 排在前面，未出场的按库存顺序排在后面。视觉顺序与提示词顺序从此一致。
3. **store 两个动作**：`moveShotCharacter(shotId, characterId, delta)`、`moveShotProp(shotId, propId, delta)`，`delta` 只取 `-1 | 1`。
   - 只读 / 镜头已锁定 → 拒绝，写页头：「这一镜已锁定，先解锁再改出场顺序。」
   - 不在出场里、已经在头 / 尾 → 返回 `false`，不写事件（按钮本来就置灰）。
   - 互换后整份写回 `shot.updated`，与点名、换人同一个事件形状。
4. **只显示在能改的时候**：只读标签页、锁定的镜头、只有一个人 / 一件道具的镜头，都不显示这对箭头——没有可挪的，箭头只会占地方。
5. **不做跨镜头搬移**：顺序只在同一镜内调；把人物从这一镜挪到下一镜仍然是点灭再点亮点。

## 理由

- **顺序有意义**：提示词按出场顺序写人，先出场的人权重更前；「谁先谁后」是导演的表达，不能只由点击的先后决定。
- **一对小箭头最省**：签本来就是一行行按钮，箭头嵌在同一枚签里，不引入新控件类型；用户已经会在场头用 `↑` / `↓` 挪场次（ADR-0060），同一套心智。
- **写一条事件**：互换是原子的；拖动如果每一帧都写，日志会多出十几条无意义的时间点。
- **显示顺序对齐提示词**：不这么排，箭头挪的是看不见的东西，用户无法验证。

## 后果

**正面**
- 分镜页 SH-01 同时点亮「林」「周」→ 签按点名顺序显示「林 ‹ ›」「周 ‹ ›」；点「周」的 `‹`，两个签互换，提示词里的顺序同步变。
- 道具「台灯」「搪瓷杯」同一套：点 `‹` 换到前面，必锁的参考图顺序跟着变。
- 单人 / 单道具时没有箭头；锁定后箭头消失，解锁回来。
- 测试：web 208（新增 3）、IR 94、gateway 17、pipeline 22，合计 341。`pnpm typecheck`、`pnpm build` 通过。
- 真实链路：分镜页点亮「林」「周」「试撤销」→ 点「周」的 `‹` → 顺序变「周，林，试撤销」；道具「台灯」「搪瓷杯」→ 点「搪瓷杯」的 `‹` → 顺序变「搪瓷杯，台灯」；均无报错。

**负面**
- **一次只挪一位**：四个人要挪到最前得点三次；长名单没有"拖到某个位置"。
- **箭头很小**：9–10px，缩略视图下不好点（未来可以考虑长按连续挪）。
- **顺序变化不标过期**：改了出场顺序，已出的关键帧不会挂 `过期`——人物集合没变，画面输入其实也没变，但提示词变了。这一点留给"提示词改动是否影响帧"统一判断。
- **道具顺序目前只影响提示词**：锚点标签按库存顺序还是按出场顺序，还要另看（现在锚点标签顺序未改）。

**跟进**
- 长按 `‹` / `›` 连续挪。
- 拖拽落点（如果箭头在真实使用中不够快）。
- 道具锚点标签是否跟随出场顺序。
- 顺序改动与帧过期的关系。

## 替代方案

| 方案 | 未采用的原因 |
| --- | --- |
| HTML5 拖拽 | 触屏与键盘不可用；签会换行，落点不稳定 |
| 指针拖动（自定义 ghost） | 实现与命中测试都重，一次点击就能完成的事不值得 |
| 数字输入顺序 | 用户得先知道"谁是第几"，还要处理重复与空缺 |
| 只按点击先后、不提供调整 | 现在的状况：想改只能全部点掉重来，还会被台词限制挡住 |
| 每次拖动都写事件 | 日志灌满中间状态，撤销与历史都变难读 |
