# ADR-0104：题材矩阵、logline 本地评分与节拍表模板

- 状态：已采纳
- 日期：2026-11-11
- 关联：A14、A15、A17、ADR-0017、ADR-0088、ADR-0089、ADR-0103

## 背景

STORY.md 把"从一句话到剧本"拆成 8 步，其中前三步一直没有界面：

- **前提**只给了四个题材按钮（都市逆袭 / 甜宠 / 悬疑 / 家庭伦理），矩阵里的受众、可行性、竞争与首发建议没有出现，用户看不到"为什么古装先不做"；
- **logline** 由模型一次给出，没有评分；STORY.md 说"10 选 1、6 维打分、总分 < 18 淘汰"，实际是一稿定生死；
- **Beat Sheet** 只写在文档里，生成提示词让模型自己排 hook → setup → …，没有可选的模板与时间窗。

这三步都是**策划工具**：不写 IR、不写事件，也不该额外花钱。因此这一轮全部做成确定性的本地数据与规则，只在生成提示词里把用户选中的题材与节拍表带上。

## 决策

### 1. 题材矩阵进 pipeline，12 条

`packages/pipeline/src/story-kit.ts` 的 `GENRE_MATRIX` 与 STORY.md §三 逐条对齐：

```ts
interface GenreProfile {
  id: string;
  name: string;
  aliases: string[];                       // 旧界面的叫法
  audience: "大" | "中" | "小";
  feasibility: "高" | "中高" | "中" | "低";
  competition: "高" | "中" | "低";
  priority: "P0" | "P1" | "P2" | "P3";
  advice: string;
  tags: string[];                          // 受众匹配打分与关键词
}
```

- `genreById` 同时认 id、名字与旧叫法（都市逆袭 → 逆袭打脸、甜宠 → 甜宠霸总、悬疑 → 悬疑复仇）；
- `genreReadiness` 把优先级翻译成推荐 / 可做 / 慎重 / 暂缓 + tone（P2 / P3 用 `pick` 色）；
- **不拦生成**：慎重与暂缓只是提示。单人 MVP 的闸门一直是"提示而不锁死"，且用户可能就是要拍古装。

故事页用 12 个按钮 + 可展开的完整矩阵表；选中的题材名随请求发给文本模型，写进 `题材偏好：…`。

### 2. logline 评分是本地启发式，不是模型评审

```ts
interface LoglineScore {
  text: string;
  total: number;                  // 6–30
  verdict: "淘汰" | "保留" | "优先";
  dims: { key; label; question; score; reason }[];
  weak: { … }[];                  // 低于 3 分
}
```

- 六个维度就是 STORY.md 的六问：高概念 / 冲突 / 代价 / 反差 / 可视化 / 受众匹配；
- 每维按可解释的词法规则给 1–5 分，并给出一句**具体理由**（"没有代价：补一句失败会失去什么"）；
- 阈值沿用文档：< 18 淘汰，18–23 保留，≥ 24 优先；
- `scoreLoglines` 一行一个候选、最多 10 条，按总分排序，对应"10 选 1"；
- 分数与理由都在本机算，不发请求、不写日志。

诚实边界写在界面上：这是筛子，不是审美判断；最终仍由人拍板。选择本地规则而不是让模型再打一次分，是因为：多一次调用多一份钱与 40–100 秒等待；模型打分不可复现；而这一步真正需要的是"把说不清的候选先挑出来"。

### 3. 节拍表是三套时间窗 + 任务

```ts
interface BeatSheet {
  id: "60s" | "3min" | "series";
  name: string;
  nominalSeconds: number;
  note: string;
  beats: { beat: BeatKind; label: string; task: string; startSec: number; endSec: number }[];
}
```

- **60 秒单集**：6 拍，与 STORY.md 的时间窗逐秒一致（0–3 / 3–10 / 10–25 / 25–40 / 40–55 / 55–60）；
- **3 分钟单集**：8 拍，两段升级 + 收束；
- **系列**：每集 60 秒的 5 拍（钩子 / 小闭环 / 中反转 / 爽点 / 大钩子），note 写"前 10 集决定留存"；
- `beatWindows(sheet, totalMs)` 按实际草稿时长等比换算，没草稿时用名义时长；
- `beatSheetPrompt(sheet)` 把模板名、时间窗与任务写成一行规则，加进文本模型的系统提示。

**不改变生成规模**：提示词末尾明确"当前仍按 60–90 秒、10–14 镜生成"。3 分钟模板这一轮只作为拆长版本的参考；真按 3 分钟生成要改镜头数与时长约束，留到后面的分集能力。

### 4. UI

- 题材：12 个按钮（带 P0–P3 小签），选中后一行 `「逆袭打脸」· 推荐 · 受众 大 · 可行性 高 · 竞争 高。…`；折叠的完整矩阵表。
- 节拍表：三个按钮 + 模板说明；折叠的时间窗表（时间 / Beat / 任务），有草稿时按草稿时长换算并注明。
- `logline 工坊`：折叠文本域（一行一个，最多 10 条）+ `打分`，按总分列出名次、淘汰 / 保留 / 优先与最弱维度。
- 生成结果下方自动给草稿 logline 出 `logline 体检`：总分 / 30、结论、六行刻度与理由、`先改：…`。

## 理由

- 三件事都是**策划判断**，不是项目数据：不进 IR、不写事件，刷新与回放都不受影响。
- 数据放在 pipeline 而不是组件里：生成提示词与界面共用一份，避免两处定义漂移（与 ADR-0103 的场景模板同一原则）。
- 本地规则可复现、可测试、零成本；界面上不把它包装成"AI 评分"。
- 节拍表进提示词而不只是展示：用户选了就该影响生成，否则只是一个装饰性的表格。
- 题材矩阵给出"为什么"：受众、可行性、竞争与首发建议比一个题材按钮更能帮用户避开一致性与群演坑。

## 后果

**正面**

- 故事页能选 12 个题材并看到推荐等级；古装宫斗显示「慎重 · 可行性 低」。
- 60 秒 / 3 分钟 / 系列三套节拍表可查看时间窗；所选模板写进生成提示。
- 一条 `27 分 · 优先` 的 logline 与一条 `15 分 · 淘汰` 的候选能在工坊里同屏比较，弱项与理由都在。
- 生成结果下方自动出 logline 体检；实测草稿 logline 39 字得 5/5 高概念、代价 2/5 并给出改写方向。
- 测试 643 全过（IR 137 + gateway 28 + pipeline 50 + web 428），`pnpm typecheck` 与 `next build` 全过。

**负面**

- logline 评分是词法启发式：不含关键词但写得很好的句子会被低估；反过来堆词也能拿高分。界面已写明，但仍可能误导。
- 节拍表不改生成规模，3 分钟模板目前只是参考。
- 题材矩阵的"竞争 / 可行性"是人工判断，没有数据来源与更新时间。
- 选中的题材只以名字进提示词；模型输出的 `draft.genre` 可能与所选不一致，目前不校验、不回写。
- logline 工坊的候选不持久化，刷新即丢。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 让文本模型给 logline 打分 | 多一次调用与等待、不可复现；本地规则足以筛掉说不清的候选 |
| 一次生成 10 条 logline 再打分 | 生成成本 ×10，且模型常给同质候选；工坊允许用户手写或分批 |
| 把评分做成不可解释的总分 | 用户不知道改哪里；每维理由才是这一步的价值 |
| 题材矩阵只做展示、不参与生成 | 选了不使用等于骗人；至少题材名与节拍表要进提示词 |
| 节拍表直接改变 10–14 镜约束以支持 3 分钟 | 会影响下游时长、成本与分镜闸门，超出这一轮范围 |
| 把题材 / logline 评分写进 IR | 它们是开工前的策划黑板，不属于成片数据；写进去还要迁移与回放兼容 |
| 矩阵数据放在故事页组件里 | 提示词侧也要题材关键词，两份数据会漂移 |
