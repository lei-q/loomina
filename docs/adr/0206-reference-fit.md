# ADR-0206：参考图出图前压缩与裁剪（B2 收尾）

- 状态：已采纳
- 日期：2026-11-14
- 决策者：用户 + Claude
- 关联：B2、B1、B8、C16、C25、ADR-0031、ADR-0128、ADR-0162、ADR-0200

## 背景

B2 收尾清单里还剩三项：参考图权重、自动挑图、**压缩与裁剪**。前两项依赖供应商字段
或另一套挑选策略（见「未做」），压缩与裁剪是本地就能做、且现在有真实痛点的一项：

- 网关 `MAX_REFERENCE_BYTES = 8 MB`，超了的参考图会被网关直接过滤掉，
  但没有一处告诉作者「为什么这张没吃到」——只有 `missing` 名单，原因说不清；
- 手机直出 / 截图往往是 4K 长边，`images/edits` 的 multipart 上传又慢又容易被拒；
- 定妆图、场景主镜、废片旧帧都会被当参考图复用（C16 / C25），
  一张几百 KB 压到 100 KB 级对画面约束几乎没有损失。

## 决定

1. **纯函数 `apps/web/lib/reference-fit.ts`**
   - `REFERENCE_MAX_EDGE = 1536`：长边上限（与出图尺寸 `1024x1536` 同一量级）；
   - `REFERENCE_SOFT_BYTES = 1_500_000`：超过就先压，低于它原样发；
   - `shouldFitReference(estimate)`：字节估算超过软阈值就压；
   - `estimateBytesOf(uri)`：`data:` 按 base64 长度 × 0.75 估，资产库地址按保守估算
     （不知道真实大小，只有出图时读到字节才能确认）；
   - `fitArgsOf(quality)`：`ffmpeg -i pipe:0 -vf scale='min(1536,iw)':'min(1536,ih)':
     force_original_aspect_ratio=decrease -q:v <quality> -f image2pipe -vcodec mjpeg pipe:1`。
     等比缩到长边 1536，**不裁剪**：参考图是身份锚点，裁掉边角等于把「不许变」的部分裁掉。
2. **服务端在读到字节之后压**
   - `generate-image.ts` 的 `referencesOf`：`readAssetBytes` 拿到的字节若超过软阈值，
     交给 `fitReferenceBytes`（ffmpeg 管道：stdin → stdout）；
   - 压缩结果仍然超过 8 MB 才记为 `missing`，并如实写「压过还是太大」；
   - 压缩失败（机器上没有 ffmpeg、ffmpeg 报错）**不阻塞生成**：退回原字节，
     按原样发；发不出去就由网关过滤并计入 `missing`，界面说明原因；
   - 返回 `references` 里多一个 `fitted: number`：这次压过几张。
3. **界面说清楚**
   - 出图回执（`referenceNotice`）多一句：「其中 N 张太大，出图前压到长边 1536（等比，不裁剪）」。
   - **不做参考图格子上的「大图」小签**：贴地址那条路本身有 400 KB 的地址上限
     （base64 约 300 KB 字节），永远到不了 1.5 MB 软阈值；资产库 / 对象存储地址
     又算不出真实大小，标上去会让每一张都像大图。真实的压缩只发生在**服务端读到字节之后**，
     所以提示也只在出图回执里说，不在挂图那一刻猜。
4. **不做裁剪**：等比缩放已经解决「太大」，裁剪会改变构图与边角信息（与 P3 一致性冲突）。
   行里的 `fitArgsOf` 只留等比缩放；真有裁剪需求的走 B10 局部重绘，不在这一档。

## 理由

- **压在前、说在前**：网关 8 MB 的硬上限不是秘密，但作者看不到「这张到底多大」；
  把阈值前移到客户端（估算）+ 服务端（真实字节），两层都能提示。
- **不裁剪**：参考图约束的是「同一个人 / 同一个地方」，裁边角会把 `mustNotChange`
  里写的东西切掉；等比缩放只丢细节、不丢构图。
- **失败不拦生成**：没有 ffmpeg 的机器仍能出图（原字节直发），只是可能被网关过滤；
  这与 preview 路由「没有 ffmpeg 就退回 E7.1」同一条口径（准则 P15：如实降级，不假装成功）。

## 后果

**正面**

- 大图不再因为超过 8 MB 被静默过滤；常见手机照片压到几百 KB，上传更快。
- 界面能看出「这张是大图」「压过几张」，不再只有一句 `missing`。
- 不新增依赖：ffmpeg 已是 preview / render 的既有外部依赖。

**负面 / 代价**

- 依赖本机 ffmpeg：没有它时压缩不发生，行为退回到「原字节直发」。
- 客户端估算只能看 `data:` 地址的长度；资产库 / 对象存储地址要到出图时才知道大小。
  所以「这张会不会被压」只在出图之后才知道，挂图那一刻不预告。
- 压缩是有损的（MJPEG q=4）：定妆图细节略降，但参考图本身只是约束，不参与最终画质。
- 只缩不裁：极端长图（1:5）缩完长边 1536 后短边很小，可能丢失细节。
- 每次出图多一次 ffmpeg 进程（只在超过阈值时），与 render / preview 抢 CPU 的口径一致。

## 替代方案

- **浏览器端 canvas 压缩**：能省一次服务端往返，但定妆页、关键帧页、剧本页都要各接一遍，
  而且服务端仍要防「客户端没压」的情况；本档只在服务端做，客户端只做估算与小签。
- **引入 sharp / jimp**：sharp 是 Next 的传递依赖但未在本仓库直接声明与固定版本，
  引入等于新增一个重依赖（违背「未经确认不引入重型依赖」）；ffmpeg 已经在用。
