# ADR-0129：三条被推迟的依赖，全部不引：用平台 API 与已有 ffmpeg

- 日期：2026-11-12
- 状态：已采纳
- 关联：E7.2、B13.3、H3、ADR-0126、ADR-0127、ADR-0128、R48、R19

## 背景

零依赖的 P0 条目已经全部落地。剩下三条功能各自卡在一个依赖决定上，ADR-0126 / 0127 / 0128 都写着「单独确认」：

| 功能 | 原计划的依赖 | 卡在哪 |
| --- | --- | --- |
| E7.2 帧级预览 | mp4box.js（约 100 KB）+ WebCodecs | 浏览器没有原生 MP4 解封装 API |
| B13.3 depth / edge 导出 | WebGL / Three.js（约 600 KB） | 平面 SVG 画不出 depth |
| H3 S3 适配器 | `@aws-sdk/client-s3`（约 1 MB）或 `aws4`（3 KB） | 需要 SigV4 预签名 |

CLAUDE.md：「未经确认，不引入重型依赖或自建基础设施」。现在是确认的时候。

## 决策

### 1. E7.2：不引 mp4box.js，改用服务端 ffmpeg 切帧 + 浏览器 Canvas

原设计的链路是「浏览器解封装 → WebCodecs 解码 → 画布」，mp4box.js 是解封装那一环。但项目已经有一条更强的路：**本机装了 ffmpeg，渲染路由已经在用它**（ADR-0091）。

改成的链路：

```
GET /api/preview/frame?asset=<uri>&at=<ms>  →  ffmpeg -ss <at> -i <src> -frames:v 1 → JPEG
```

- 浏览器只拿一张 JPEG，`<img>` 就能显示，**不需要 WebCodecs**。
- 帧级精度由 ffmpeg 的 `-ss` 保证（精确 seek，不是关键帧近似）。
- 单帧 60–120 KB，本地服务，一次往返约 20–60 ms；连续拖动时由前端做 60ms 节流 + 请求去重。
- 没有新依赖：ffmpeg 是运行环境的前提（渲染已经要求它），`spawn` 是 Node 自带。

**代价**：这是「服务端出图」，不是「浏览器本地解码」。断网、或者把页面部署到没有 ffmpeg 的机器上，帧级预览就不可用。所以保留能力探测：拿不到就用 E7.1 的近似（ADR-0127 §6 的降级口径不变）。

### 2. B13.3：不引 WebGL / Three.js，用 ffmpeg 的 `zscale` / `depth` 思路换成 2D 深度图

原设计要 WebGL 是因为「必须真实渲染几何体」。但 depth 导出的产品目的不是「好看的结构图」，而是**给关键帧当结构参考**：作者要看的是「人在画面的哪个位置、离机头多远、前后景怎么叠」。

用 Canvas 2D 就能画出来，而且更可控：

- 俯视 / 立面已有的坐标 → 透视投影（一个 4×4 矩阵，纯数学）；
- 人物画成按深度着色的简笔柱子（近亮远暗），家具画成按深度着色的矩形；
- 输出一张**深度色图**（近处暖、远处冷）叠一张线框，喂给图像模型当参考图。

这不是「渲染」，是「结构示意」。ADR-0126 已经定过口径：灰盒与成片差距要让人理解，不假装它是 previs 渲染。同理，这张图在界面上叫「结构参考图」，不叫「depth 渲染」。

**不引入 GPU 的另一个理由**：E7.3（合成加速）也推迟了。两条都吃 GPU，一起等 E1 支持转场时再评估渲染层——现在引入，是为一个还不存在的需求固化渲染抽象层。

### 3. H3 S3：自写 SigV4，不引 SDK 也不引 `aws4`

ADR-0128 §3 给的两个选项是「自写 80–120 行」与「引 `aws4`（3 KB）」。选**自写**：

- `aws4` 已经多年不更新，而 SigV4 的规范化规则是冻结的（AWS 公开文档 + 官方测试向量），不存在「跟着上游升级」的维护成本；
- 自写可以用 AWS 官方的测试向量做单测，正确性是可验证的，不是「相信库」；
- 3 KB 的库也要进依赖树、要审 license、要跟着 Node 版本走——对一段一年改不了一次的纯函数，不划算。

实现范围限定在**预签名 PUT / GET**，不做 SDK 的对象模型、分片上传、重试。这一点 ADR-0128 已经定过。

### 4. 三条的共同口径

- **能力探测照旧**：拿不到就降级，界面写清当前在哪一级（ADR-0127 §6）。
- **都不是导出路径**：预览帧、结构图、S3 都只是「看一眼」与「存一份」，成片仍以 ffmpeg 导出为准（ADR-0127 §5 / P20）。
- **依赖清单不变**：`package.json` 一个包都不加。这是本次确认最重要的结果。

## 理由

- **能用已有的就不引新的**：ffmpeg 已经在跑、Canvas 已经在画、`node:crypto` 已经在用。三条功能都能靠这三样完成，引依赖只是换一种写法。
- **正确性可验证**：SigV4 有官方测试向量；ffmpeg seek 有确定行为；Canvas 投影是纯数学。都能写单测，而「相信一个库」不能。
- **推迟 GPU 是克制的**：只有硬切的时间线用不上 GPU 合成，depth 也用不上真 3D。等 E1 支持转场时，两条需求一起评估。

## 后果

**正面**

- 三条功能都能开工，且 `package.json` 不动。
- E7.2 的精度比原设计更好：ffmpeg 精确 seek，不受 GOP 限制。
- 结构参考图走 Canvas，可以在浏览器里实时跟着拖动重画，不需要服务端往返。

**负面**

- **E7.2 依赖服务端**：没有 ffmpeg 的环境降级到 E7.1；这是新的运行环境要求（渲染本来就有，不算新增）。
- **B13.3 不是真 depth**：没有逐像素深度，只有按深度着色的示意。喂给图像模型时是「构图参考」，不是「几何约束」。
- **SigV4 要自己写对**：规范化请求的坑不少（URI 编码、头排序、空 payload 的哈希）。用官方测试向量锁住，但边界情况（中文 key、特殊字符）要单独测。

**跟进**

- E7.2 落地后补一次真实设备的拖动性能标定（R19）。
- B13.3 的图要在真实关键帧生成里验证「有没有用」——不是「好不好看」。
- S3 用 MinIO 做一次端到端（ADR-0128 已列）。
