# ADR-0133：整场锁定

- 日期：2026-11-12
- 状态：已采纳
- 关联：H20、ADR-0041、ADR-0080

## 背景

ADR-0041 把**单镜**锁定做完了：留用过的镜头才能锁，锁后生成、一句话指令、补充划掉全部只读，只留「解锁」。H20 还剩最后一段：

> 整段锁定、锁定历史未做。

真实用法是「这一场定下来了，别再动它」。一场 3–6 镜，逐镜点一遍锁，是把一个决定拆成六次点击；而且锁到一半停下来，状态既不是「开着」也不是「锁着」，比不锁更难判断。

## 决策

### 1. 一场一个动作，不是逐镜的快捷键

`setSceneLock(sceneId, locked)` 一次写 N 条 `shot.updated`，每条只带 `{ locked }`。

不发明 `scene.updated{locked}`：锁是**镜头**的属性（ADR-0041 的语义、下游生成与一句话指令的判断都读 `shot.locked`），加一个场景级的锁字段会立刻出现「场锁着但镜头没锁」这种要额外解释的状态。N 条镜头事件是对已有事实的如实记录，历史抽屉也逐条看得懂。

### 2. 与单镜锁定共用同一条规则

「留用过的镜头才能锁」不在整段路径上放宽。因此整段锁定是**部分成功**的操作：

- 有 approved take 的镜头锁上；
- 没有的跳过；
- 回执写明「锁了 2 镜，跳过 1 镜（还没留用 take）」。

跳过而不是报错回滚，是因为「这一场大部分能锁」是有价值的中间结果；全有或全无会逼作者先去逐镜留用，反而更慢。

### 3. 一条事件都没写成，也要说话

三种空结果各有自己的话：

| 情况 | 话 |
| --- | --- |
| 想锁，但一镜都没留用 | 这一场有 N 镜还没留用 take：先留用，再整段锁定。 |
| 想锁，但已经全锁了 | 这一场都已经锁上了。 |
| 想解锁，但没有锁着的 | 这一场没有锁着的镜头。 |

第一版把这段话写进 `castError` 却挂在一个**场头不渲染**的 `note` 上——按钮点了，store 也改了，页面上什么都没发生。浏览器实测才看出来：点击确实到达了按钮，`onClick` 也执行了，只是回执没地方显示。现在锁定回执有自己的 `lockNote`，挂在那一场标题下面。

### 4. 「有锁着的」就显示「整段解锁」

按钮文案与点击方向只看一件事：这一场有没有锁着的镜头。

```
sceneLocked === 0  →  「整段锁定」，点了锁
sceneLocked  > 0   →  「整段解锁」，点了解
```

**不能按「全锁才算解锁」**。一场里只要有一镜没留用 take，它就永远到不了「全锁」，按钮就永远是「整段锁定」——作者锁了之后**再也解不开**。这是实现时浏览器里撞出来的：一场 2 镜、锁上 1 镜、另一镜没 take，标题写着「锁 1」，按钮却还是「整段锁定」。改成「有锁着的就能解」之后，锁 / 解都能一键完成。

### 5. 读模型上只多一个计数

场头统计行在「N 镜」后面加 ` · 锁 M`（M > 0 时才显示）。计数在组件里从 `project.shots` 现算，不进 read-model：它只影响这一个标题行，没有第二个消费者。

## 为什么不做的部分

- **锁定历史**：`shot.updated` 的每条 `{locked}` 已经在事件日志里，历史抽屉能逐条回放。专门做一个「锁定时间线」页，是在已有数据上再包一层，没有新问题要回答。
- **场锁与镜锁的继承**：不做。ADR-0041 已经把「锁」定义在镜头上，加继承就要回答「场解锁后，原本自己锁着的镜头怎么办」，那是另一套模型。
- **整段锁定时自动留用最新 take**：不做。留用是一次审美决定（「这条能用」），批量替作者做决定是错的；跳过并告知更诚实。
- **跨场批量锁定**：不做。当前最多 5 场 12 镜，逐场点已经够快；跨场批量需要先有「选中多场」的交互，收益不抵复杂度。

## 后果

- 无新事件、无 IR 变化、`LOG_VERSION` 不变。整段锁定就是 N 条已有的 `shot.updated`。
- store 新增 `setSceneLock(sceneId, locked) => { locked, skipped }`。
- 场头多一个按钮与一行回执；统计行多一个 `锁 M`。
- 只读标签页下按钮不渲染（与单镜锁定一致）。
