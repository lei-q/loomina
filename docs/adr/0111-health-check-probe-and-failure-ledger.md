# ADR-0111：健康检查——供应商探测、失败率小账本与「没有调度器」的边界

- 日期：2026-11-11
- 状态：已采纳
- 关联：H11、B12 / ADR-0098、H2 / ADR-0106

## 背景

H11 一直只剩「健康检查 / 定时探测 / 失败率告警」没做。设置页的能力矩阵（B12）回答的是「这个模型理论上能做什么、多少钱」，S1 测绘回答的是「上次实测怎么样」，两者都不回答「现在通不通、最近这一路是不是在连续失败」。

单人、本机、无服务的部署形态决定了做法：没有 Prometheus、没有常驻 worker、没有告警通道。健康检查只能是「打开设置页时能看到的一份现状」，而不能假装成一个 24 小时值守的监控。

## 决策

### 1. 探测：只读 `GET /v1/models`，5 分钟缓存

- 复用配置页已有的 `probeProvider`：一条只读请求，不触发生成、不花钱、不返回密钥。
- 结果按「供应商」聚合：状态（正常 / 不稳定 / 不可用）、耗时、模型数、原始一句话说明。
- 状态口径：`401 / 403 / 404` 是配置或权限不对，记「不可用」；其余失败（超时、限流、5xx）记「不稳定」；成功记「正常」。
- 进程内缓存 5 分钟（`PROBE_TTL_MS`）。`GET /api/health` 用缓存，`?probe=1` 强制重新探测。

### 2. 失败率：每次生成调用记一笔，只记成败

- 落盘 `.loomina/health-events.json`（0600，目录 0700，可用 `LOOMINA_HEALTH_STATE` 改位置），只留最近 400 条。
- 一笔只有五个字段：时间、模态、模型 id（请求指定的才有）、成没成、失败短码。**不记提示词、不记素材、不记密钥、不记 Base URL。**
- 五个生成入口（故事 / 资产 / 视频 / 配音 / 识别）在成败处各记一笔，写完不等（`void`）：记账失败只影响趋势，不该影响生成。
- 同进程内串行写（模块级 Promise 队列），避免几个请求同时结束时后写覆盖先写；写临时文件再 `rename`，读到的一直是完整 JSON。
- 读不到、文件坏了都当空账本：健康检查不能因为自己的记录坏了就打不开。

### 3. 归组与阈值

按「模态 + 模型」归组，只看最近 24 小时（`FAILURE_WINDOW_MS`），未来时间戳与坏时间戳跳过。

| 条件 | 状态 |
| --- | --- |
| 少于 3 次（`MIN_SAMPLES`） | 正常（不下结论） |
| 失败率 ≥ 20% | 留意 |
| 失败率 ≥ 50% | 告警 |

告警按「先告警、再留意、最后正常，同状态按样本数」排序。**4xx 参数问题不进账本**：提示词被审核拦下、空输入、不认识的资产类型是这次请求写错了，不是供应商的账，记进去只会让失败率说谎。

### 4. 界面：设置页一块「健康检查」

- 打开时拉一次，之后每 60 秒拉一次（只在页面开着时）；「立即检查」走 `?probe=1` 强制探测。
- 三块内容：供应商一行一个（状态签、耗时、模型数、说明）；最近 24 小时失败率按组列出（样本 / 失败数 / 百分比 / 状态签 / 最后一次失败码）；渲染队列四个计数（读 H2 的落盘队列）。
- 有任一供应商非正常或任一组告警时，顶部出一条「现在有问题」的红框，把人和事写清楚。页面本身不做弹窗、不做声音。

### 5. 边界写进文案

「定时」就是「这一块开着时每分钟问一次、服务端 5 分钟内复用」——页面上明说没有常驻定时任务。这是有意的不做：加一个调度器就要加进程常驻、失败通知和状态恢复，超出单人项目的维护预算；而健康检查真正被需要的时刻，正是人坐在电脑前准备开工的时刻。

## 后果

- 开工前一眼能看到：供应商通不通、最近哪一路在连续失败、渲染队列有没有卡住的。
- 失败率是**本机视角**：只统计这个浏览器 / 这个进程发起过的调用，别人机器上的失败看不到；也没有跨天留存的历史曲线（只保留最近 400 条）。
- 重启进程后探测缓存清空，第一次打开设置页会真探一次；账本不受影响。
- 失败码来自供应商返回的分类，不是质量评分：`429` 与 `timeout` 都只是「这次没成」。
- 与 B12 的分工：能力矩阵说「能做什么、多贵」，S1 测绘说「上次实测」，健康检查说「现在通不通、最近稳不稳」。

## 验证

- 单测 728 全过（IR 142 + gateway 28 + pipeline 51 + web 507）：`health-events.test.ts` 12 条（分组与样本、不同模型分开、样本不足不下结论、20% / 50% 两档、24 小时窗口、坏时间戳、空账本、读写往返、并发写不互相覆盖、坏文件自愈、400 条上限与 0600），`health.test.ts` 5 条（状态口径 401/403/404、供应商告警、5 分钟缓存与强制探测、报告不含 Base URL 与密钥、渲染计数）。
- `pnpm typecheck`、`pnpm --filter @loomina/web build` 全过。
- 浏览器（生产 3100 / 3102，后者挂一份临时账本）：设置页健康检查块显示「最近一次探测 · 缓存」、供应商正常 74 个模型；点「立即检查」后缓存标记消失、耗时刷新；临时账本下出现「现在有问题」红框、视频 3/4（75%）告警、文本 1/5（20%）留意、配音 0/3 正常、渲染队列与最近失败码 429；3100 空账本下显示「还没有调用记录」，无红框。真实调一次识别（无效音频）后账本多出 `asr · 1/1 · 404`，确认入口接线生效。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 常驻定时探测 + 桌面通知 | 要引入常驻进程、通知权限与状态恢复；单人项目维护不起，而且「没人看的时候告警」本身就用不上 |
| 记录完整报错文本 | 可能带提示词与素材信息；失败率只需要「哪一类、成没成、什么码」 |
| 用 S1 测绘代替健康检查 | 测绘要真的生成、要花钱，只能偶尔跑；健康检查要的是随时能点、零成本 |
| 把 4xx 也计入失败率 | 参数写错和供应商挂了是两件事，混在一起会让「连续失败」失去意义 |
| 失败率存在 IndexedDB | 账本是服务端的视角（多条路由共用），且要跨浏览器一致；放浏览器会一人一份 |
| 无限保留历史 | 400 条足够回答「最近这一路稳不稳」，也避免账本长成第二个数据库 |
