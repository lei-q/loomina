# ADR-0010 工作流引擎：分阶段引入，先用 pg-boss + 状态机

- 状态：已接受
- 日期：2026-11-09
- 决策者：工程
- 关联：P8、H2、H10、R18

## 背景

生成管线是长任务、多步骤、易失败、需要重试与预算控制的：`关键帧 → 视频 → QA → 重试 → 入库`。

候选方案：

- **Temporal**：能力最强（持久化工作流、重试、版本化），但自托管组件多、运维重；Cloud 在国内的可用性不确定。
- **Restate**：单二进制、持久化执行，较新。
- **Inngest**：托管、开发体验好，但数据出境与合规存疑。
- **BullMQ**：Redis 队列，成熟，但流程语义要自己写。
- **pg-boss**：Postgres 队列，可在业务事务内原子入队。
- **自研状态机**：完全可控，但要自己实现重试/幂等。

单人开发 + 国内部署，是这两个约束的交点。

## 决策

分两阶段：

**Phase 1（MVP）**
- 用 **pg-boss** 做任务队列；
- 镜头生命周期用**显式状态机**存在 Postgres（`draft → keyframe → video → qa → review → approved`）；
- 幂等键 = `hash(shotId + 参数)`；
- 预算与重试次数写入任务记录，超限即失败/降级；
- 所有任务通过统一的 `JobRunner` 接口提交。

**Phase 2**
- 若状态机难以维护或需要复杂补偿，再评估 **Restate / Temporal**；
- 迁移只改 `JobRunner` 实现，不改业务。

## 理由

- pg-boss 与 Postgres 同库，**创建实体 + 派发任务可在一个事务里完成**，避免"记录建了、任务没发"。
- 少一个中间件，单人运维成本最低。
- 显式状态机虽然朴素，但可读、可查、可调试；对 MVP 足够。
- 用接口隔离，保留升级路径（准则 P8 的同一思路）。

## 后果

**正面**
- 运维面小，问题可在一张表里查清。
- 成本护栏、重试上限、幂等都能直接建模。

**负面 / 代价**
- 复杂流程（并行分支、补偿、长时间等待）要自己写，容易长出"隐性状态机"。
- 迁移到 Temporal/Restate 需要一次重构（但边界清楚）。

**跟进**
- 状态机必须有**单一入口**与状态转移表，禁止散落在各处。
- 任务表与业务表同库，便于对账。
- 若出现三个以上并行分支，触发重新评估。

## 替代方案

- **直接上 Temporal**：能力过剩、运维过重，否决为 Phase 1。
- **BullMQ**：可以，但失去事务内入队；若已有 Redis 且需要复杂限流，可替换。
- **纯自研队列**：重复造轮子，否决。
