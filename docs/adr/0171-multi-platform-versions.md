# ADR-0171：多平台版本渲染（G9）

- 状态：已采纳
- 日期：2026-11-13
- 决策者：用户 + Claude
- 关联：G9、E5、G7、G10、H5、准则 P5 / P20

## 背景

E5（ADR-0170）之后，一条片子能按 9:16 / 16:9 / 1:1 三种形状导出，但一次只能出一种：
改画幅 → 导出 → 改回来 → 再导出。发三个平台就要走三遍，中途还要记得把画幅改回去；
角标位置（H5）也跟着平台走，改一次平台就得重导一次。

平台规格表（`platforms.ts`）早就知道每个平台收什么形状、时长上下限多少，
预检也一直在用。缺的只是「把这条片子按每个平台的规格各出一版」这一步。

## 决定

1. **版本是「同一条剪辑、不同导出参数」，不是新的数据模型**
   ```ts
   VersionPlan = { platform, spec, frame, size, changesFrame, blocker? }
   ```
   - 由 `versionPlans(frame, durationMs, platforms, quality)` 纯函数算出，不落库。
   - 每一版仍然走同一个 `POST /api/render`、同一条 `buildCommand`，只是清单里的
     `frame` / `platform` 不同。不新增渲染路径、不新增服务端状态。
   - 每一版导出后各记一条 `publish.recorded`（G10），平台字段写它自己的平台。

2. **形状优先沿用项目当前画幅，平台不收时退到它收的第一个**
   - `frameForPlatform`：当前 `aspect` 在平台的 `aspectRatios` 里就原样用（作者已经
     挑过焦点、看过预览）；不在就退到平台接受、我们也做得出来的第一个形状。
   - 适配方式（`fit`）永远沿用项目设置：换形状只换宽高比，不擅自把 `crop` 改成 `pad`。
   - 一个形状都做不出来时如实报 `blocker`，不偷偷换。小红书要 3:4、我们只做
     9:16 / 16:9 / 1:1，这时退到 9:16；平台只收我们做不了的比例时才拦。

3. **时长也按平台单独判，与形状分开**
   - 抖音 / 快手下限 15 秒、YouTube Shorts 上限 180 秒、X 上限 140 秒。
   - 形状对了、时长超了同样发不出去，所以 `versionPlans` 两个都查，`blocker` 写清是哪一条。

4. **依次渲，不并发**
   - 本机渲染队列（E6 / H2）同一时间只跑一条；并发只会把几版都排进队列、
     进度互相盖住，还看不出是哪一版在跑。
   - 一版失败不中断后面几版：失败的那版报出来，别的照出。
   - 进度用 `versionLine`：`第 1 / 2 版：B 站 · 16:9 · 1920×1080`。

5. **文件名带平台后缀，加在扩展名之前**
   - `夜班-成片-B站.mp4` / `夜班-成片-X.mp4`；后缀只留平台名，去掉
     `\ / : * ? " < > |`、空白与括号（`versionSuffix`），避免各系统不认。
   - 无字幕版仍然在最后加 `-无字幕`，两个后缀不打架。

6. **闸门要分开看：内容侧与平台规格**
   - 多平台版本的「能不能导」只取内容侧结论（文案硬阻断 / 待确认没勾），
     **不取当前选中平台的规格结论**——项目是 16:9 却选着抖音时，B 站 / X 那几版照样能出。
   - 规格由面板里每个平台各自判，卡片上写明「出不了」和原因。
   - 定稿档的闸门（先在页面底部确认这一版成片）与单版导出一致，几版一起导也要求确认。
   - 由此顺带修掉一个既有问题：资产复核的「勾选确认」以前挂在 `report.ok` 上，
     当前平台规格不过就勾不了，等于把人锁死。现在挂在「内容侧没有硬阻断」上。

7. **界面：导出按钮旁的「多平台版本」抽屉**
   - 九个平台各一张卡片：形状 · 尺寸（按当前档位算，草稿 960×540 / 定稿 1920×1080）、
     平台收哪些比例、这一版会不会换形状、出不了的原因。
   - 汇总区写「这一次会导出 X / Y」，并提示有 N 版画幅与项目设置不同、文件名带平台名。
   - 导出结果列在面板里（平台 / 体积 / 文件名），并提示每版都记进了发布记录。

## 理由

- **不另开渲染路径**：多平台版本是「同一份清单换个画幅」，复用 E5 的 `frameChain`
  与既有队列，出错面最小，也自动继承了角标、字幕、调色、混音的全部既有行为。
- **沿用当前画幅**：作者已经为当前形状挑过焦点；没有理由为了「平台第一个」而
  换掉一个平台也接受、作者也已经看过的形状。
- **不偷偷换形状**：发上去被平台二次裁切，比一次失败更难发现。
- **依次渲**：并发在本机只增加排队与混乱，不增加吞吐。
- **文件名带平台**：几版下到同一个文件夹里，靠文件名分得清是哪一版。

## 后果

**正面**

- 一条片子勾几个平台、点一次导出，几版依次渲完、依次下载，不用来回改画幅。
- 每版自动记进发布台账，平台字段正确，回执能按平台贴回去。
- 卡片上直接看到「抖音要至少 15 秒，这一版只有 5.5 秒」这类原因，不用导出后才发现。
- 闸门修好后，当前平台规格不过不再锁死其它平台与确认勾选。

**负面 / 代价**

- 几版是串行的：三版就是一版时间的三倍（本机队列本来就是单条，不算额外损失）。
- 浏览器可能拦截连续多次下载，面板里已提示「选允许」。
- 画幅不同的版本，字幕 / 角标排版是按同一套 cqw 规则缩放的，不做横竖两套版式
  （与 E5 的边界一致）。
- 版本计划不落库：关掉页面再打开，勾选会回到默认（抖音 + B 站）。

**不做**

- 一次请求渲多版（服务端批量任务）。
- 每个平台单独设画幅 / 适配方式（用项目设置，平台只决定收不收）。
- 按平台自动改写标题 / 简介 / 话题。
- 小红书 3:4 这类我们还不做的比例。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 服务端一次收多个 manifest、批量渲 | 队列仍是单条，只是把排队藏到服务端；进度与失败定位都更难 |
| 并发渲几版 | 本机队列并发固定为 1，并发只会互相排队并把进度盖住 |
| 换形状时把 `fit` 也换成 `pad` | 作者选的适配方式是有意的；换形状不该顺带改它 |
| 每版文件名加画幅 | 名字太长；画幅已经写在清单与发布记录里 |
| 用当前选中平台的规格拦整个导出 | 项目 16:9 选着抖音时，B 站 / X 那几版本来能出，会被一票否决 |
