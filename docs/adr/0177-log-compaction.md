# ADR-0177：日志压缩（H3 收尾）

- 状态：已采纳
- 日期：2026-11-13
- 决策者：用户 + Claude
- 关联：H3、F4、F2、H9、ADR-0011、ADR-0034、ADR-0109、ADR-0128、ADR-0136、ADR-0158、ADR-0175、P7、R49

## 背景

素材搬进资产库之后日志并没有变小：迁移（ADR-0128）只**追加**一条新的
`asset.updated { uri: "loomina://assets/…" }`，旧事件里那份 base64 原样留着。
一个改过几版定妆图的项目，日志能到几十兆；设置页一直写着「旧事件里那份 base64
还在，要等日志压缩」，而日志压缩一直挂在「未做」。

这一版把它做掉，并且守住一条底线：**不能把图换成另一张图**。
自动化最容易犯的错，是按资产 id 去找「这个位置现在的地址」再回填历史——
可同一个资产位换过图，旧事件里的那张与现在的这张根本不是一张。

## 决定

1. **按内容指纹认，不按资产 id 认**
   - 每段 base64 先解出原始字节，算 SHA-256，扩展名按 mime 推（与资产库同一张
     mime ↔ 扩展名表），得到内容文件名 `<sha256>.<ext>`。
   - 拿这个文件名去**库清单**里查：查得到才换地址，查不到就留原样。
   - 库清单就是 `/api/asset/store`（本机）或 `/api/asset/remote`（桶）已经给界面那一份。
     两种库的前缀不同（`loomina://assets/` 与 `s3://桶/assets/<前两位>/`），
     但最后一段都是内容文件名——**按最后一段建索引**，不猜桶名与前缀。

2. **只动两个位置的地址**
   - `asset.updated.asset.uri`
   - `project.created.project.assets[].uri`
   - 事件条数、顺序、`at`、其他字段一律不动；没有匹配的事件**原样返回同一个对象**
     （不复制，界面上也不会因为压缩而整体重渲染）。
   - 项目里没有别的地方带字节：take、台词、配乐都只引用 `assetId`。

3. **压缩不写新事件**
   - 它不改变项目，只改变同一段字节在日志里的写法。写一条「我压缩了」的事件
     反而会让日志变大，也让「怎么变成这样的」多出一条与创作无关的记录。
   - 内存里那份项目跟着把 `uri` 换掉，保证 `rebuild(events)` 与当前项目逐字一致；
     不这样做，界面会显示旧地址，刷新后又变成新地址。

4. **只换地址，不删事件**
   - 撤销、回滚、历史上限、发布台账全都按「事件前缀」工作（ADR-0109）：
     条数与顺序不变，这些一个都不用改。
   - 换完之后历史里那一版仍然指得回同一张图——只是从「日志里的一份副本」
     变成「库里的那一份」。

5. **界面在设置页「本机资产库」区的「日志瘦身」块**
   - 一行账：日志里还有几处 base64、约多少字节。
   - 一个按钮：压缩日志。没有可压的、读不到库清单、只读模式时禁用并写明原因。
   - 回执写清真实数字：`改写 3 处素材地址（3 条事件），日志 1.5 MB → 11 KB`；
     库里找不到同一段字节时如实说「另有 n 段在库里找不到，留着没动」。

6. **算不了指纹就不压**
   - 需要 `crypto.subtle`（安全上下文）。拿不到时返回空计划，
     界面回执是「没有能压缩的 base64」而不是假装压缩过。

## 与 ADR-0011 的关系

ADR-0011 写的是「日志只追加、从不删改」，这条在**事件语义**上仍然成立：
压缩不增、不删、不改任何一条事件表达的事实，回放出来的项目与压缩前
只在 `uri` 这个字符串上不同，而两个地址指向**同一段字节**。

这是 ADR-0011 唯一放宽的地方，也是它第一次被放宽，所以写在这里：
**只有「同一段字节换一个等价地址」这一种改写被允许，而且必须由作者显式触发。**
任何其他对历史事件的修改仍然禁止；要作废一段历史，用 `project.restored`
指向前缀，不要改字节。

## 理由

- **内容指纹是唯一不会认错的办法**：资产 id 是「位置」，不是「图」。
  按位置回填，一次换图就会把历史改成另一张，而这种错误在界面上看不出来
  （都是同一张缩略图的位置，只是内容不对了）。
- **库清单是现成的**：设置页为了孤儿检查已经取过一份完整清单，
  压缩直接复用，不新增接口、不多一次往返。
- **只换地址的压缩最保守**：不需要判断「哪条事件还可以丢」，
  也就不需要处理「丢了之后撤销怎么办」。
- **不写事件**：日志是创作记录；压缩是存储维护，和迁移只写「地址变了」不同——
  迁移确实改变了项目里的 `uri`，压缩改的是历史里的写法，项目本身没动。
- **零新依赖**：`crypto.subtle` 是浏览器自带的；`atob` / `TextEncoder` 也是。

## 后果

**正面**

- 日志第一次真的会变小。实测：三条 400 KB 素材从 `1.5 MB` 压到 `11 KB`。
- 迁移之后，库里那些「看起来没人引用」的文件变成被引用了：
  孤儿数从 1 降到 0。压缩顺手把「搬完就被当成孤儿」这个坑填了。
- 撤销、回滚、历史上限、发布台账都不用改——条数与顺序没变。
- 库里找不到同一段字节的绝不会被换掉；宁可日志不缩，也不换错图。

**负面 / 代价**

- **压缩之后那份原始 base64 没有了**：如果库里的文件被清掉（手动删盘、
  清理孤儿、换机器），历史里那一版就只剩一个指向空气的地址。这是压缩的固有代价，
  也是为什么它必须是显式动作。
- 算指纹要把日志里所有 base64 解一遍、哈希一遍：几十兆的项目在设置页点一下
  会卡住一两秒；没有进度条，也不可中断。
- 一次只按当前库清单压：桶换过、文件没搬过来、库清单读不到时，那部分留着不动。
- 只认这两种事件：以后若出现别的事件自己带字节（而不是引用 `assetId`），
  压缩不会去动它，需要在新事件的设计里一并考虑。
- 压缩后写回的是整份日志（`replace`），不是追加：一次几十兆的 IndexedDB 重写。

**不做**

- 快照式压缩（把整条日志折叠成一条 `project.created`）：会丢掉「怎么变成这样的」，
  与 P7 / ADR-0011 冲突。
- 丢弃事件、按时间或条数裁剪、压缩历史里的文字字段。
- 自动压缩、定时压缩、按体积触发。
- 压缩前检查库文件是否真读得出来（只按清单里的地址认；文件内容一致由内容寻址保证）。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 按资产 id 回填「现在的地址」 | 同一个位换过图就会换成另一张，界面上看不出来 |
| 折叠成一条快照事件 | 丢掉历史与撤销；P7 与 ADR-0011 都不允许 |
| 压缩时删掉更早的 `asset.updated` | 撤销、历史回退、四格旧版回看全都会断 |
| 服务端做压缩 | 日志在浏览器 IndexedDB，服务端看不到；上传日志违背数据边界 |
| 迁移时顺手改旧事件 | 迁移是增量动作（中途失败可停在半个项目上）；改历史要单独确认 |
| 按体积自动压 | 压缩会丢弃原始副本，不能替作者做这个决定 |
| 给压缩写一条事件 | 多一条与创作无关的记录，日志反而变大 |
