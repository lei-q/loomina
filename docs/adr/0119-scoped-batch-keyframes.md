# ADR-0119：关键帧批量补缺按筛选范围执行

- 日期：2026-11-11
- 状态：已采纳
- 关联：H21、ADR-0042、ADR-0083

## 背景

`/keyframes` 有两种操作叠在一起：

- **筛选**：「全部 / 缺首帧 / 缺尾帧 / 两帧齐」，帮作者找到要补的那几格。
- **批量补缺**：「补缺首帧 / 补缺尾帧」，按镜号顺序一张张生成。

批量一直作用于**全量**。于是「筛到缺首帧，点补缺首帧」这个最自然的动作，会把不在这档里的镜头也补了——筛选在这里没有产生任何作用，只是让人多看了一眼。多补的每一张都是真花的钱。

## 决策

### 1. 批量接受一个可选的镜头范围

```ts
generateMissingFrames(frame?: Frame, only?: string[]): Promise<void>
```

给了 `only` 就只补这些镜头，与既有语义组合：跳过锁定、按镜号顺序、失败即停、可中途停下。没给就是原来的全量行为，调用方不必都改。

### 2. 不新增按钮，让现有按钮跟着筛选走

界面上不加「挑张补」这样一个新按钮——那会让同一件事有两个入口。改成：

- 筛选不是「全部」时，补缺按钮的**报价按这一档算**（`11 张 · ¥1.32` 是这一档的数量）。
- 按钮 title 从「按镜号顺序补首帧」改成「只补当前这一档里缺首帧的镜头」。
- 按钮左边多一句「只补这一档（n 格）」，让范围在点之前就看得见。
- 这一档都齐了时提示写「这一档里没有缺首帧的镜头」，而不是「首帧都齐了」——后者只在全量语义下成立。

### 3. 后台队列仍不做

批量补帧是浏览器发请求、拿到结果就写事件，进程在页面里。搬进后台队列需要把生成任务从页面生命周期里剥出来（服务端任务表 + 重连恢复），是另一套架构，而 H21 的痛点是「补错范围」，不是「关掉页面就断」。当前批量能中途停下，已经够用。

## 后果

- 「筛到哪一档、补哪一档」成为默认行为，报价与范围在点之前都能看到。
- 全量补缺仍然可用：筛选回到「全部」即可。
- 锁定镜头在任何范围下都跳过：批量不是绕过闸门的理由，这条不变。

## 验证

- 单测 782 全过（IR 155 + gateway 28 + pipeline 51 + web 548）。
  - `workbench-store.test.ts` 新增 2 条：点名只补那几镜（且锁定的 s-08 仍被跳过）、点名都齐时不写事件并给「这一档里没有缺首帧」。
- `pnpm typecheck`、`next build` 全过。
- 浏览器（生产 3100，关键帧页）：筛选条「全部 12 / 缺首帧 12 / 缺尾帧 12 / 两帧齐 0」；全量时「补缺首帧 11 张 · ¥1.32」（s-08 锁定）；点「缺首帧」后出现「只补这一档（12 格）」，title 变为「只补当前这一档里缺首帧的镜头」，报价仍是 11 张。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 加一个独立的「挑张补」按钮 | 同一件事两个入口；筛选已经表达了范围，按钮再选一次是重复 |
| 每张卡片加复选框，勾选后补 | 十二格手点一遍比筛选慢；筛选已经覆盖「按缺帧类型挑」这个主要场景 |
| 把批量搬进后台队列 | 需要服务端任务表与重连恢复，是另一套架构；H21 的痛点是补错范围 |
