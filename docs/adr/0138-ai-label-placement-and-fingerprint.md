# ADR-0138 AI 标识补全：角标按平台摆，标识带内容指纹

- 状态：已接受
- 日期：2026-11-12
- 决策人：用户 + Claude
- 关联：ADR-0008（AI 标识内建）、ADR-0090（导出与预览都带显式角标）、ADR-0091（mp4 烧录）、ADR-0095（导出前预检）、G7 / H5

## 背景

ADR-0090 把「显式 + 隐式标识、不可关闭」落了地，但它的「跟进」里留了两条没做：

1. **平台规格库（G7）落地后按平台安全区调整角标位置**——当时角标固定写死在右下角。
2. **强隐式标识：内容哈希 / 签名 / 不可见水印**——当时只有一句 `{explicit, implicit, standard:"AI生成"}`。

第一条不是洁癖：右下角恰恰是抖音、快手、小红书、TikTok 这些竖屏平台摆点赞 / 评论 / 分享按钮的地方。角标被压在按钮下面，画面上就等于没有——合规要求的是「看得见」。

第二条的漏洞更直接：隐式标识只有一句固定文案，把它抄到另一条视频的元数据里，没有任何东西能说明它对不上。

## 决策

1. **角标位置进平台规格表，不让用户选。** `PlatformSpec.badge` 记 `{ corner, insetPct }`。竖屏信息流平台（抖音、快手、小红书、B 站竖屏、视频号、TikTok、YouTube Shorts）统一放**左上角**，`insetPct: 8`：右侧是互动栏，底部是文案与进度条，左上相对最空。X 放右上角，通用规格回右下角（A 类导出没有平台 UI，保持 ADR-0090 的原样）。没写位置的平台退回 `DEFAULT_BADGE`（右下 4%），不抛错。
2. **三处渲染共用同一张表。** 预览 HTML 的 `.ai-badge`、成片页播放器的角标、成片 MP4 的 canvas 叠加层都读 `badgePlacementOf(platform)`。三处各写各的，迟早会漂移成三个位置。
3. **角标落在安全区之内。** `insetPct: 8` 与 `SAFE_AREA.topPct = 8` 对齐：角标至少离平台界面 8%，不会因为手机状态栏、平台顶栏或底部手势条被吃掉。
4. **隐式标识加一枚内容指纹。** `aiLabel` 增加 `version: 1` 与 `contentHash`（8 位十六进制）。指纹取材只取决定「这份产物长什么样」的字段：标题（按清单落盘的 80 字裁切）、总长、每段的时长与素材地址的短摘要（地址本身的 FNV-1a，不是长度——长度相同分不出换没换 take）。换 take、改时长、增删一镜都会变；只改字幕文案或配乐不变，因为那两项不改变「这是哪一版画面」。
5. **指纹跟着产物走，四处各写一份。** 预览 HTML 写进 `<meta name="ai-label-content-hash">`；OTIO 写进 `metadata.loom.aiLabel`；发布包写进 `aiLabelRecord`；MP4 写进容器元数据 `description=AI生成 · 内容指纹 <hash>`。每份产物的素材地址（内嵌 data URI 与否）不同，所以各自的指纹也不同——比对只对「同一份产物重算」有意义，这写进了代码注释。
6. **渲染路由重算指纹并拒绝不一致。** `validateRenderManifest` 收到清单后按同一函数重算，和清单声明的 `contentHash` 比对；改过素材或时长却没更新指纹的清单回 400「AI 标注的内容指纹与清单对不上」。这是第一条真正带强制力的隐式标识检查：客户端不能自己编一个指纹糊弄过去。
7. **IR 的发布记录也记指纹。** `AILabelSchema` 增加可选 `contentHash`，`publish.recorded` 校验它是 8 位十六进制；历史发布包缺它照样合法（可选字段，`LOG_VERSION` 不变）。`recordPublish` 从刚打的发布包带过来，项目发布记录因此能回答「这条发布对应哪一版剪辑」。

## 理由

- **不把角标位置做成用户选项**：挪一次就可能挪进平台 UI 里，而作者在成片页看不出那是什么。平台事实由表决定，改版就改表，改表是留痕的。
- **用地址摘要而不是字节哈希**：素材可能是几百 KB 的内嵌 data URI，逐字哈希整份素材既慢又没必要；地址换了素材就换了。指纹不是防篡改，是「把标识绑到这份产物」。
- **服务端重算**：客户端算指纹、服务端只信任声明，等于没检查。重算的成本只有几次字符串拼接与一次 FNV。
- **FNV-1a 32 位**：与阶段闸门、导出预检同一套（`fnv.ts` 里写明它不是安全哈希）。它要防的是误配与顺手篡改，不是有资源的对手；真正的防伪要密钥与验签，那是另一件事。
- **指纹进 IR 但不进事件语义**：标识仍是导出层常量，指纹只是把「这一版」记在发布记录上；不新增事件类型，也不要求历史日志迁移。

## 后果

**正面**

- 抖音等平台的成片角标不再压在点赞栏下；成片页切平台时角标当场换角，作者看得见。
- 清单、预览、OTIO、发布包、MP4 五处标识互相可核对，且服务端能拦住指纹对不上的渲染请求。
- 发布记录能回答「这条发布对应哪一版剪辑」，为后续追溯与申诉留了抓手。
- 可选字段：历史项目、历史发布包、旧清单读出来都合法，`LOG_VERSION` 不变。

**负面**

- **不是签名，也不防水印**：能改元数据的人也能改指纹；它证明「这份标识属于这份产物」，不证明「谁生成的」。要防伪得有密钥分发与验签，要扛转码得有像素级水印，两条都没做。
- **角标位置是参考值**：按各平台常见布局定的，平台改版就会失效，所以每份规格都把「AI 角标位置」列进 `reference`，界面只提示、不硬校验。
- **指纹包含标题**：改发布标题会让指纹变。这是有意的（标题是这一份产物的一部分），但发布前改标题会需要重新导出，界面上只说「回成片页重新导出」，没有单独解释这一点。
- **内嵌与否会改指纹**：预览 HTML 把素材内嵌成 data URI，和成片清单的地址不同，两者指纹不同。比对只对同一份产物有意义；跨产物的核对要靠时长与镜头结构。
- **竖屏平台一律左上**：没有按每个平台逐角实测，真实遮挡仍可能要按具体版本微调；表里改了才算数。

## 未做

- 数字水印（能扛转码的像素级标记）。
- 签名与验签（服务端密钥、公钥分发、离线校验工具）。
- 标识分级（全生成 / 辅助生成、服务提供者名称）。
- 按平台逐角实测角标位置（现在按公开布局推断）。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 角标继续固定右下角 | 竖屏平台的互动栏就在那儿，显式标识等于被盖住 |
| 让作者自己拖角标 | 作者看不出平台 UI 的遮挡范围，拖一次就可能拖进按钮底下 |
| 隐式标识只写固定文案 | 标识可以被抄到任意视频上，没有任何东西能说明它对不上 |
| 指纹用 SHA-256 等安全哈希 | 32 位 FNV 与项目其它指纹一致，够用于防误配；安全哈希不解决防伪（没有密钥） |
| 指纹放进项目事件、每次编辑都写一条 | 标识是导出层的事，不是项目状态；会多一堆永远相同的字段 |
| 只在客户端比对指纹 | 客户端自己算自己核，等于没检查；必须服务端重算 |

## 附记（2026-11-12）：验证记录

- 浏览器：`/edit` 默认抖音时角标在左上角（偏移 9px，落在 8% 安全区）；切到通用规格回到右下角；合规预检那一行显示「左上角「AI 生成」角标（离边 8%）…（含内容指纹）」。
- 预览 HTML：`<meta name="ai-label-version" content="1">`、`ai-label-content-hash`、`ai-label-badge` 三处都在，`.ai-badge` 定位随平台变。
- 渲染路由：指纹写成 `deadbeef` 的清单回 400；按同一规则算对的清单 202 → done，`ffprobe` 读到 `comment=AI生成`、`description=AI生成 · 内容指纹 2b2da29a`。
