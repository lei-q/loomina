# ADR-0178：预演代理缓存的上限、清理与预生成（E7 收口）

- 状态：已采纳
- 日期：2026-11-13
- 决策者：用户 + Claude
- 关联：E7、E7.1、E7.2、E7.3、H3、ADR-0127、ADR-0129、ADR-0153、R19、R57

## 背景

540p 代理（ADR-0153）是按需转的：某条片子第一次进预演时用 ffmpeg 转一份，
落 `.loomina/assets/proxies/`，之后命中缓存。它把「拖动时解码器排队」压下去了，
但留了三个口子：

- 缓存只增不减，也没有上限——一个换过很多 take 的项目，代理目录能悄悄吃掉几 GB；
- 没有地方看见它占了多少，也没有清掉它的入口；
- 每次都是「第一次播到这一镜才开始转」，作者第一次拖到那里要等一两秒。

E7 一直挂着的「未做：代理预生成与容量上限」就是这三件。

## 决定

1. **上限 2 GB，超了按最久没用先删**
   - `planProxyEviction(files, keep, cap)` 纯函数：按 `mtime` 从旧到新删，
     删到总量不超上限为止；**刚写好的那份 `keep` 永远不删**（刚转完就被自己清掉，
     下一次播放又要转一遍）。
   - `LOOMINA_PROXY_CACHE_MB` 可以改上限（磁盘紧张的机器）；不合法或没设就走 2 GB，
     清理缓存不该因为一个环境变量写错而失效。
   - 每写完一份新代理就压一次。清缓存失败不报错：缓存清不掉不该让这次播放失败。

2. **`GET /api/preview/proxy?stats=1` 报清点，`DELETE` 清空**
   - 清点回 `{ count, bytes, over, cap, files: [{ name, bytes }] }`；只有文件名与大小，
     没有素材内容。
   - `DELETE` 逐个删 `.mp4`，回 `{ removed, bytes }`。代理是派生物，原片还在，
     下一次开预演按需重建——**所以这里不要确认词**，也不碰素材本体。

3. **`POST /api/preview/proxy { assets }` 预生成**
   - 浏览器送「这条片子里用到的、在资产库里的素材地址」（去重、最多 24 条，
     路由时限 120 秒；一条 3 秒的片子本地转 1–3 秒）。
   - 已经转好的直接跳过、记 `cached`，不算失败；转不出来的记 `failed` 并带回前三条原因。
   - 预生成失败**不是致命错误**：预演会自动回原片，界面上说得清。

4. **界面在设置页「本机资产库」区的「预演代理缓存」块**
   - 一行账：`n 份 · X / 2.0 GB`。
   - 两个按钮：「预生成代理（n 条）」（按当前项目的 take 去重算 n）、「清掉代理缓存」。
   - 回执写真实数字：`转好 1 份代理`、`清掉 2 份代理（约 298 KB）；下次开预演会按需重建`。

5. **预演里的开关不动**
   - 540p 开关仍然只影响「这一镜播代理还是播原片」；预生成只是提前把缓存填好，
     开不开它都能命中缓存。

## 理由

- **代理是可删的缓存，不该需要确认词**：它重建得出来，成本是 CPU 不是数据。
  需要确认词的只有「删了就没了」的东西（本机素材、桶里的对象）。
- **上限必须自动执行**：开关默认是关的，作者不会记得去清；一个默认关掉的开关
  不应该在半年后变成几 GB 的垃圾。
- **`keep` 不删**：LRU 最常见的事故是刚写进来的新文件因为 mtime 排序被第一个删掉
  （某些文件系统 mtime 精度粗），转了个寂寞。
- **预生成是有界动作**：一次最多 24 条、逐条转、跳过已缓存，不会把磁盘一次写满，
  也不会让一个请求跑上十分钟。分不清「转好」与「本来就有」会让作者以为白等了。
- **界面上说清「原片才是唯一事实」**：代理删掉、转不出来都不影响导出，
  这条边界从 ADR-0153 起就没变过，这里只是把它写进按钮旁边。

## 后果

**正面**

- 代理缓存第一次有上限、有清点、有清理入口；E7 的「未做」清空。
- 第一次拖到某一镜不用再等转码：预生成把这条片子的代理先填好。
- 实测：同一地址再点预生成回 `{ done: 0, cached: 1 }`；把上限调到 10 KB 时，
  第二份代理写完后第一份被清掉，刚转好的那份留着。

**负面 / 代价**

- **预生成会占 CPU**：24 条一次要几十秒，期间这条请求占着一个服务端任务；
  没有进度条，也停不下来。
- 上限是全局的，不按项目分：项目 A 的代理可能把项目 B 的挤掉（下次再转）。
- 只按 `.mp4` 认缓存文件：别的格式（将来换编码）不会被统计到，也删不掉。
- 清空是一次性全删，没有「只删某几条」。
- 没有命中率统计：不知道预生成到底省了多少等待。

**不做**

- E7.3 WebGPU 合成（ADR-0127 已定暂缓：时间线只有硬切，Canvas 2D 够用）。
- 预生成的进度推送、可中断、后台排队（要走 H2 的队列，不是这一版）。
- 代理分辨率可选、按屏幕密度自适应。
- 代理目录与素材库共用一套清理（两件事：代理可删可重建，素材删了就没了）。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 不设上限，只在设置页给个清理按钮 | 开关默认关着，没人会想起来清；半年后就是几 GB |
| 超上限时连刚写好的那份一起删 | 转了个寂寞，下一次播放又要重转 |
| 按项目分目录、各算各的上限 | 换项目就要重转；总量控制不住 |
| 清缓存要两步确认 | 代理重建得出来，确认只会让人以为它很重要 |
| 预生成放六成进度条、长轮询 | 要走队列与状态通道，是 H2 的活；这一版一键到底 |
| 预生成返回视频字节 | 预生成的目的就是「不要传输」，回字节等于把整条片子拉一遍 |
| 上限写死在配置里 | 磁盘大小因机器而异；环境变量够用，不新增配置面 |
