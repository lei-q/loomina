# ADR-0093：渲染任务队列与进度

- 状态：已采纳
- 日期：2026-11-11
- 关联：ADR-0091、ADR-0092、H2、R15

## 背景

E6 的成片渲染是一次同步请求：浏览器 POST 清单，等 ffmpeg 跑完才拿到 MP4。问题：

- 没有进度，只能写「通常 20–90 秒」；长片像卡死。
- 没有并发控制，两个标签页同时导出会并行跑两个 ffmpeg 抢 CPU。
- 失败只能整次重来，客户端连任务号都没有。

H2 要求长任务可观察、可重试、幂等。当前是单人本地部署（`next start`），没有 Redis / 任务系统。

## 决策

在渲染路由内做单进程内存队列：

- `POST /api/render` 校验清单后立即返回 `202`，带 `jobId` 与初始状态；渲染在后台继续。
- `GET /api/render?job=<id>` 返回 `status`（`queued` / `running` / `done` / `error`）、`stage`、`progress`、排队位置、尝试次数、错误与计数。
- `GET /api/render?job=<id>&download=1` 在完成时返回 MP4，响应头带跳过 / 占位计数。
- 并发固定为 1；等待队列上限 8，满了回 `429`。
- 进度来自 ffmpeg 的 `-progress pipe:1`：读 `out_time_us` 除以清单总时长，封顶 99%，完成时写 100。
- 每个任务独立临时目录；失败自动重试 1 次（共 2 次），仍失败则把 ffmpeg 最后几行作为错误返回并删除目录。
- 成功的任务保留 30 分钟供下载，之后删除文件与内存记录（`setTimeout` + `unref`，不阻止进程退出）。
- 任务号用 `randomUUID()`，不可枚举。

## 理由

- 不改部署形态：不需要 Redis、数据库或额外 worker；单人本地够用。
- ffmpeg 自带进度输出，比按时间估算准确；不需要解析日志猜。
- 并发 1 让「一次只渲一条」成为硬约束，避免风扇狂转与内存峰值叠加。
- 重试放在任务内部，客户端不用理解失败发生在哪一层。
- 临时目录按任务隔离，失败不会留下半份文件，成功也不会互相覆盖。

## 后果

**正面**

- 20 秒测试片实测进度 14% → 38% → 63% → 82% → 100%，第二条任务排队位置正确，前一条完成后自动开始。
- 两个任务顺序执行，CPU 不再被并发抢占。
- 坏素材会重试 2 次后报出 ffmpeg 原文；队列继续处理后面的任务。
- 客户端轮询逻辑简单，页面刷新后任务仍在（只要服务没重启）。

**负面**

- **不持久**：`next start` 重启后内存任务全部丢失，进行中的 ffmpeg 会被杀；客户端收到 404，需要重新导出。
- 只适合单实例；多实例部署时两个进程各有队列，并发不是全局的。
- 30 分钟 TTL 由内存定时器维护，进程退出不会清理临时目录（操作系统会回收 `/tmp`）。
- 同一任务被重复 `download` 会重复读文件；当前没有一次性下载限制。
- 队列没有优先级与取消；先提交的先跑。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 同步请求保持原样 | 没有进度、没有并发控制，长片体验差 |
| 引入 BullMQ + Redis | 单人为本机部署增加一个必须常驻的服务，违反「不轻易自建基础设施」 |
| 任务写 SQLite / 文件 | 需要迁移、锁与恢复语义；当前重启丢任务可以接受 |
| 用 Server-Sent Events 推进度 | 需要维持长连接与断线重连；1 秒轮询在这个体量下足够 |
| 并发按 CPU 核数自适应 | 1080×1920 编码内存峰值高，单人机器上并发 1 更稳 |
| 把成品存回项目或对象存储 | 导出语义是下载，不是发布；H3 暂缓 |
