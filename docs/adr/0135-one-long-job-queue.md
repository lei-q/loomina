# ADR-0135：出图与出视频接入同一条长任务队列

- 日期：2026-11-12
- 状态：已采纳
- 关联：H2、ADR-0093、ADR-0106、ADR-0116、H11

## 背景

H2 一直挂着这一句：

> **未做**：……其它长任务（出图 / 视频）接入同一队列

渲染有一条自己的队列（ADR-0093）：并发 1、排队位置、进度、取消、落盘（ADR-0106）。出图（`POST /api/asset`，实测 48 秒–2 分钟）与出视频（`POST /api/video`，几十秒轮询）都是**同步请求**，没有任何排队。

于是真实的操作顺序会出问题：

- 定妆页连点四个角度 → 四个出图请求并行跑，一起打供应商的限流（实测一次 `429`）；
- 出完图顺手点视频，再回成片页点导出 → 出图、出视频、ffmpeg 三条一起抢 CPU；
- 机器卡住时，界面上**没有任何地方说得清「现在到底在忙什么」**。

## 决策

### 1. 一条队列，三个使用者

新增 `apps/web/lib/long-job.ts`：

```ts
withLongJobSlot(kind, label, task, onWait?)  // kind: "render" | "image" | "video"
longJobSnapshot()                             // 在跑什么、后面排着谁、各等了多久
```

渲染、出图、出视频都从这里过一遍。**并发固定为 1**——与 ADR-0093 同一个理由：1080×1920 的 ffmpeg 与一次出图同时跑，内存峰值叠加，单人机器上会卡到没法用。

这不是把出图改造成异步任务（要任务号、轮询、断线重连），只是**加一道闸**：请求还是同步的，只是排队等待。改动面最小，也最不容易在供应商配额不通时把错误语义搅乱。

### 2. 挂在 `globalThis` 上，不是模块变量

`next start` 下每个 route 是独立的 bundle，模块级变量不共享。渲染队列之所以能用模块变量，只是因为它的整条逻辑都在 `app/api/render/route.ts` 一个文件里。三个 route 要共享一份状态，只能挂到进程的全局对象：

```ts
const KEY = Symbol.for("loomina.long-job-queue");
```

用 `Symbol.for`（全局注册表）而不是字符串键，避免与别的库撞名。

### 3. 先来后到，不插队

「没人占」和「排在最前」必须同时满足才放行。只看「没人占」会让后到的插队——第一个任务结束时，所有等待者同时被叫醒，谁先跑到谁抢到，那就不叫队列了。

放行时叫醒所有等待者、各自再判一次：这样不需要记录「下一个是谁」，一个监听集合就够。

### 4. 排队要能看见，也要能说清在等谁

- `GET /api/health` 多一个 `longJobs`：`active`（谁在跑、跑了多久）+ `waiting`（排着谁、等了多久）。健康面板多一行「长任务」。
- 渲染的 `publicJob` 多一个 `busyWith`：渲染在等别的长任务时，按钮下方写「等前面的长任务跑完（出图 · 夜班走廊 · 24.8s）…」，而不是一句空泛的「排队中」。
- 出图 / 出视频的请求在排队时**不做界面提示**：它们的按钮本来就在转，多一行只会让人以为卡住了。真正需要解释的是「为什么我的渲染还没开始」。

### 5. `onWait` 只在真的排上队时回调一次

第一版把「等前面的长任务跑完」先写进渲染阶段，再调 `withLongJobSlot`——`runJob` 一进来就把阶段改成「准备素材」，那句提示根本没被人看见。改成入队前先判断能不能立刻开跑，只有不能时才回调。

## 为什么不做的部分

- **出图 / 出视频改成异步任务**：要任务号、轮询、断线恢复、任务落盘，一整套 ADR-0093 的机制。当前的问题是「同时跑太多」，不是「等不到结果」；加一道闸就解决了。
- **按类型分队列**（出图一队、渲染一队）：那等于没有闸——它们本来就互相抢资源。
- **优先级**：作者点「导出」与点「出一张图」在机器看来一样重。真要做优先级，得先回答「谁该等谁」，而当前所有等待都是秒级到分钟级，收益不抵复杂度。
- **多实例共享队列**：`globalThis` 只在一个进程内。多实例部署时每个进程各有一条，与 ADR-0093 的边界相同。
- **排队超时**：一个任务无限期地占着位置会把整条队列卡死。当前没有自动超时——渲染有 240 秒的 ffmpeg 超时、出图有 170 秒的客户端超时、出视频有各自的轮询上限，都靠调用方自己退出；`withLongJobSlot` 的 `finally` 保证退出时一定让位。

## 后果

- 渲染、出图、出视频不再同时跑；一次只跑一个，其余排队。
- `GET /api/health` 的 `longJobs` 是「机器现在在忙什么」的唯一答案；健康面板多一行。
- 渲染的进度文案在等待时点名在等谁。
- 无新事件、无 IR 变化、无新依赖。
- 新增 `apps/web/lib/long-job.ts` 与 5 条单测（同时只跑一个、先来后到、`onWait` 只在真排队时回调、抛错也让位、快照说清在跑什么）。
