# ADR-0179：H3 的两件不做（多项目分桶、分片上传）

- 状态：已采纳
- 日期：2026-11-13
- 决策者：用户 + Claude
- 关联：H3、H4、H9、ADR-0128、ADR-0129、ADR-0158、ADR-0176、ADR-0177、ADR-0178、R49、R59、P21

## 背景

H3 的「未做」只剩两条：**多项目分桶**与**分片上传**。它们是 ADR-0129 留下的
一句话，没有设计，也没有证据说明现在需要。在这一版收口之前，先把「为什么不做」
写清楚——留着一条永远不做的「未做」，下次读文档的人还得重新想一遍。

## 决定

### 1. 不做多项目分桶

对象存储里所有项目的素材共用同一个 `assets/<前两位>/<sha256>.<ext>` 命名空间，
不按项目再分一层前缀。

**理由**

- **内容寻址的前提就是共享**：同一段字节只存一份。按项目分前缀，
  同一张定妆图在两个项目里就是两个对象、两份钱，而且清理时两边各判各的孤儿。
- **分桶解决不了「这个项目占多少」这个真问题**。真问题是看清用量，
  那是读模型的事：日志按 `project.created` 切段（ADR-0088），
  每段的资产引用与库里的文件大小都在手上，算得出来。在这台机器上多存一层目录不解决它。
- **白名单已经按「所有能回放项目」的并集算**（ADR-0158）：清理从来不需要按项目划线。
- **迁移成本不对称**：已经写进桶里的对象不搬；分了前缀之后，
  旧对象既在新规则之外、又还在被引用，清理界面会永远看见一批「不属于任何项目」的对象。

**什么时候会改主意**：出现「一台机器上多个互不信任的项目（多人 / 多租户）」时。
那时要的是租户隔离（独立的桶或独立的账号），不是前缀。

### 2. 不做分片上传

素材走预签名 PUT，整段一次写完；不实现 multipart 的 initiate / uploadPart / complete。

**理由**

- **尺寸在射程内**：单文件上限 200 MB（ADR-0128），S3 兼容的单次预签名 PUT 上限是 5 GB，
  MinIO / OSS / COS / 七牛都在这个量级之上。
- **分片的收益只在断点续传**：一次 200 MB 的 PUT 在慢网下失败就要重来。
  但素材的绝大多数来自供应商回传（服务端落库）或本机迁移，不是从浏览器上传；
  真正会走浏览器上传的是「贴地址」与参考图，都是小文件。
- **代价不小**：每个分片的 SigV4、分片清单、失败重试、未完成分片的生命周期清理，
  以及「上传到一半的应用」的状态机。这是自建基础设施，按 CLAUDE.md 要先确认。

**什么时候会改主意**：出现「从浏览器上传几百 MB 的视频、且网络不稳」的真实场景，
或者供应商改成让客户端直传大文件。

### 3. H3 收口

两条都记为**明确不做**（不是待办），H3 的状态改成「已完成」。
以后再有需要，按上面的触发条件重新开 ADR，不在这条上慢慢加。

## 后果

**正面**

- H3 不再挂着一个「永远在开发中」的状态；读文档的人能看到「为什么不做」与「什么时候会做」。
- 对象存储的行为只有一种：一个 `assets/` 命名空间、内容寻址、跨项目去重。
- 少一套分片上传的状态机与生命周期清理。

**负面 / 代价**

- 真出现多租户或大文件直传时，要重新设计并迁移；这两条不会自己变简单。
- 无法在桶里按项目过滤——要看项目用量得在本机算（日志在浏览器，桶不在）。

**不做**

- 按项目前缀、按用户前缀、跨桶同步、生命周期规则（这些都属于「真要做时一起设计」）。
- 分片上传、断点续传、直传 STS 临时凭据。
- 桶内用量按项目统计的界面（需要时按读模型补，不是存储层的事）。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 按项目前缀分桶 | 破坏跨项目去重；旧对象迁移不对称；真需要的是租户隔离 |
| 分桶 + 每个项目一份引用清单 | 清单要多机同步，日志在浏览器，服务端拿不到 |
| 先做分片上传留着以后用 | 一次性写完就够用；未使用的基础设施同样要维护 |
| 把两条继续挂在「未做」 | 没有触发条件、没有理由，「未做」会变成事实上的「不做」，却没人知道为什么 |
