# ADR-0105：生成前提示词审核与 G8 四检查点

- 状态：已采纳
- 日期：2026-11-11
- 关联：H6、G8、ADR-0095、ADR-0100、ADR-0103

## 背景

H6 一直只有"导出前扫文本"：17 条规则确实拦得住成片里的违规台词，却拦不住**已经花掉的钱**——分镜页照常把「制毒」这样的描述发给图像 / 视频供应商，图出来以后才在成片页被拦。G8 的四项预检也只在成片页出现，剧本、关键帧、成片与发布文案四个阶段各自的风险没有被单独回答。

这一轮补两件事，都不改 IR：

1. **生成前审核**：在服务端拼完提示词、调用供应商之前，用同一套规则扫一遍；
2. **四个检查点**：按阶段各扫各的文本，给出状态与指纹，统一展示在成片页。

## 决策

### 1. 只审"将要发出去的那句话"

`apps/web/lib/moderation.ts`：

```ts
type PromptModeration = {
  kind: "image" | "video";
  status: "pass" | "review" | "block";
  blocked: number;
  review: number;
  categories: string[];
  findings: ComplianceFinding[];
  summary: string;
};
```

- `moderatePrompt(prompt, kind)` 直接扫 `buildKeyframePrompt` / `buildVideoPrompt` 的最终输出，而不是回头扫 IR 字段：提示词里还可能拼进角色外观、场景模板、表演与调度，这些同样会被送出去；
- `assertPromptAllowed` 只在 `status === "block"` 时抛 `PromptBlockedError`；`review` 不拦生成，随结果返回，界面与调用方都能看到"有几处要自己看一眼"；
- 位置在 `generateCastImage` / `generateShotVideo` 里、**任何适配器请求之前**。硬阻断时任务不建立、不轮询、不计费；错误文案明确写"这次没有发出请求，也没有花钱"；
- 路由把 `PromptBlockedError` 映射为 HTTP 400 + `code: "prompt_blocked"` + `moderation`；其余供应商错误仍是 502 / 500，视频的 `retryable` 逻辑不变。

**明确边界**：这不是像素级审核。画面出来之后的脸、手、构图与真实内容仍需人工看；模型审核服务（H6 剩余部分）与审核结果落库仍未做。

### 2. 四个检查点按阶段切文本

`apps/web/lib/compliance.ts` 新增：

```ts
type CheckpointId = "script" | "keyframes" | "edit" | "publish";

type CheckpointReport = {
  id: CheckpointId;
  label: string;
  scope: string;
  status: "pass" | "review" | "block";
  detail: string;
  findings: ComplianceFinding[];
  units: number;
  signature: string;
  checkedAt: string;
};
```

各阶段扫的文本：

| 检查点 | 扫描范围 |
| --- | --- |
| 剧本 | 标题、故事、人物弧光 / 关系、角色外观与监工要点、场景、道具、分镜描述与补充、台词（与导出预检同一份 `collectTexts`） |
| 关键帧 | 角色外观与监工要点、场景 / 道具描述、镜头描述与补充、表演目标 / 表面情绪 / 潜台词 / 三拍 / 避讳、调度备注 |
| 成片 | 台词、配乐标题 / 情绪 / 授权来源；另附时间线时长与配乐段数 |
| 发布文案 | 发布标题、简介、话题（标题空时兜底项目标题） |

- 规则仍是同一份 `RULES`，不另起一套；`preflightCheckpoint` 只决定扫哪些文本；
- 成片检查点在时间线为空时标 `review` 并写"先把镜头放上去"；这不是安全命中，所以 `findings` 仍为空；
- `signature` 由阶段文本、命中项与备注一起算；改一句话就变，可用于以后把"确认"绑到阶段上；
- 一次算完四个：`preflightCheckpoints(project, options)`。

### 3. UI 放在成片页的导出区

`apps/web/components/compliance-checkpoints.tsx` 渲染四行：状态点、阶段名、通过 / 待确认 / 阻断、说明与扫描范围；有命中时点击展开前 6 条（位置、命中词、建议、上下文）。面板放在「导出前检查」正下方，与导出预检共用标题 / 简介 / 话题。

**不新增独立闸门**：四个检查点只回答"这一阶段现在有没有问题"，不拦页面跳转、不拦生成、不替代导出预检的确认流程。导出按钮仍只由 `preflightProject` 的 `ok + reviewAcknowledged` 决定。

## 理由

- 提示词是服务端唯一能控制的表面：在它之前拦，才能做到"不发出请求、不花钱"；
- 复用一份规则，避免"生成时一套、导出时一套"的漂移（与 ADR-0103 / ADR-0104 同一原则）；
- 每阶段只扫自己的产出，问题出现在哪一段就写在哪一段；全部塞进导出预检会让用户在小问题堆里找不到重点；
- 检查点不写入 IR：它们是当前项目的派生视图，刷新、回放、迁移都不该被它们影响。

## 后果

**正面**

- 提示词命中硬阻断时，图片 / 视频接口返回 400 与结构化 `moderation`，一次供应商请求都不发；实测「制毒」两条路径都被拦；
- 正常项目在成片页能看到四行「通过」，分别写清扫了多少段文本；把发布简介改成「加微信领福利，稳赚不赔」后，发布文案行变「待确认」并展开两条命中，导出预检同步变成 2 处待确认；
- 检查点与导出预检的命中项一致，用户不用在两个面板之间对账；
- 测试 654 全过（IR 137 + gateway 28 + pipeline 50 + web 439），`pnpm typecheck` 与 `next build` 全过。

**负面**

- 只审提示词，不审生成结果；`review` 的提示词照常出图、出片，用户仍要自己看；
- 四个检查点统一在成片页，剧本 / 关键帧页就地提示还没做，问题仍可能到成片页才看见；
- 成片检查点的时间线完整性只回答"空不空"，不检查缺画面、缺配音或片段重叠；
- 检查点指纹目前只展示在报告对象里，界面没有"确认这一阶段"的按钮。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 等图像 / 视频出来后做模型审核 | 更贵、更慢，而且钱已经花了；提示词层是最早且最便宜的拦截点 |
| 扫 IR 字段而不是最终提示词 | 会漏掉模板、表演、调度拼进去的内容，也与真正发出去的句子不一致 |
| 硬阻断 `review` 项 | 剧情里的暴力、迷信、炫富很常见，全拦会让正常创作无法进行 |
| 每个阶段页各放一个闸门并锁住下一步 | 单人 MVP 的闸门原则是提示而不锁死（ADR-0100）；且阶段页数据形态不同，统一面板先跑通 |
| 检查点结果写进 IR / 事件日志 | 派生数据会随文案变化，写进去要处理失效与迁移，收益低 |
| 另写一套"生成前规则" | 两套规则必然漂移；复用 `RULES` 才能保证导出与生成结论一致 |
