# ADR-0166：发布台账与回执（G10）

- 状态：已采纳
- 日期：2026-11-13
- 决策者：用户 + Claude
- 关联：G10、G1、G5、H5、准则 P15 / P16

## 背景

到这一刻，发布这件事只留下了**一半**：导出发布包时 `publish.recorded` 会把平台、
档位、文件名、字节数与 AI 内容指纹写进 IR 的 `publishPackages`（ADR-0102）。

这半条记录回答的是「我导出过什么」。作者真正要问的是另外三件事：

- 这一版**到底发了没有**？
- 发在**哪个链接**上、平台**回了什么**（过审 / 驳回 / 播放量）？
- 同一个平台发过三版，**哪一版是现在线上的那版**？

现在这三个问题的答案只活在作者的备忘录里。导出时间被当成了发布时间，
「导出过三版、发了零版」和「三版都发了」在台账上长得一模一样。

## 决定

1. **导出事实与发布事实分成两条事件**
   - `publish.recorded` 不变：导出那一刻的平台、档位、文件、指纹，只追加。
   - 新增 `publish.updated { packageId, patch }`：`patch` 的类型是
     `Partial<Pick<PublishPackage, "publishedAt" | "url" | "receipt" | "note">>`，
     `applyEvent` 里显式白名单校验，出现别的键直接抛错。
   - 合并后整包再过一遍 `PublishPackageSchema`：长度越界在落库前被挡掉。

2. **发布包本身不许回填改**
   - 平台、档位、文件名、字节数、渲染耗时与 `aiLabel`（含内容指纹）都是
     导出那一刻的事实。允许事后改，等于允许伪造「这一版是按新规格导的」。
   - 要换平台或改文件，就重新导出、记新的一条；两条历史并排，才说得清。

3. **`publishedAt` 与 `recordedAt` 分开存**
   - `recordedAt` 由 store 在记事件时写；`publishedAt` 是作者贴回来的字符串
     （≤40 字，格式自由，界面「现在」按钮填本机时间 `YYYY-MM-DD HH:mm`）。
   - 分开存是为了让台账能按 `publishedAt` 是否为空分出「已发 / 未发」——
     用导出时间猜发布时间，会在「导出后隔天发」的常态里全部猜错。

4. **只记作者自己贴回来的东西，不接平台数据**
   - `url` / `receipt` 都是自由文本输入框，没有任何抓取或 API 调用。
   - 官方 API 发布是 G4、数据回流是 G5，都还没做，也不该在这里假装做了。

5. **界面：成片页顶栏「台账」抽屉**
   - 每份发布包一张卡：平台名、序号、已发 / 未发、导出时间、档位、文件名、
     体积、内容指纹、渲染耗时，以及（有则显示）发布时间 / 链接 / 回执 / 备注。
   - 「贴回执」展开四项输入 + 「现在」按钮；「记进台账」写一条
     `publish.updated`，四项都没变就不写事件，界面如实说「没有改动」。
   - 顶栏按钮上的数字是**还没贴回执的份数**，贴完就消失。
   - 未发的卡用虚线边框 + 「未发布」文字，不用颜色吓人：没发不是错误。

6. **store 只写有变化的字段**
   - `recordPublishReceipt(packageId, patch)` 逐项与现值比对（去首尾空白后），
     把差异收成一个更小的 `patch`；空的就不写事件。
   - 这样「打开表单又原样保存」不会在历史里留下一条无意义的记录。

## 理由

- **事实与后补分开**是这份 IR 一以贯之的做法（`recordedAt` / `publishedAt`、
  `Provenance` 只写不改）。台账要能被审计，导出事实就不能被后补覆盖。
- **白名单而不是整包替换**：`patch` 类型上已经限死四个键，运行时再校验一次，
  是因为事件是从日志回放的——手改过的日志不该能把平台改成别的东西。
- **只记不抓**：接平台数据要资质与 API（G4 / G5），现在做只能是假的。
  作者手贴一行回执，比一个假装自动的数字有用。
- **不改 IR 结构**：四个字段全部可选，旧项目与旧发布包照常合法，
  `LOG_VERSION` 不动。

## 后果

**正面**

- 台账第一次能回答「这一版发了没有、发在哪、平台怎么说」。
- 导出事实（平台 / 文件 / 指纹）被保护起来，历史可审计。
- 未发 / 已发一眼可分，不用再翻备忘录。
- 全部本地：不调模型、不花钱、离线可用。

**负面 / 代价**

- 回执要作者手动贴，不做自动同步；忘了贴就一直是「未发布」。
- 发布时间是自由文本，没有格式校验（只限长度）——写错格式界面照存。
  这是刻意的：平台回执的时间格式五花八门，强行校验只会挡掉合法值。
- 一份发布包只能记一个链接：同一版发到多个平台要各导一次发布包
  （与 G1 的「一份包一个平台」一致）。

**不做**

- 官方 API 发布（G4）与数据回流（G5）。
- 自动抓播放量 / 完播率曲线。
- 发布包之间的对比视图（哪一版播放更好）。
- 回执附件的上传与存储。
- 把回执写进发布包 JSON 的导出（导出的仍是导出那一刻的包）。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 直接把 `publishedAt` 加进 `publish.recorded` | 导出时还不知道发布时间，只能编一个 |
| 允许 `publish.updated` 改任意字段 | 平台与指纹是导出事实，可改就等于可伪造 |
| 用导出时间当发布时间 | 「导出后隔天发」是常态，会全部猜错 |
| 单独建一张发布表（不进事件日志） | 撤销、历史、重放全部要另写一套，违背单一日志 |
| 抓平台 API 自动填回执 | 需要资质与 API（G4 / G5），现在只能造假 |
| 发布时间强制 `ISO` 格式 | 平台回执格式各异，强校验会挡掉合法值 |
