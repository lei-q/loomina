# ADR-0121：故事层单独编辑与 `story.updated`

- 日期：2026-11-11
- 状态：已采纳
- 关联：A16、A18、ADR-0017、ADR-0088、ADR-0120

## 背景

`Project.story` 存着 logline、梗概、类型、受众、调性、两个钩子、每个人的 7 项弧光与关系张力。它只在故事入口生成时落一次项目——之后界面上**没有任何入口**。

想改一个人的 `want`，唯一办法是整份重新生成。那会把已经手改过的 logline、别人已经调好的弧光一起冲掉。生成的产物不能改，等于每次修改都要重掷一次骰子。

## 决策

### 1. 新增 `story.updated`，字段白名单

```ts
{
  type: "story.updated";
  at: string;
  patch: Partial<Pick<StoryBible, "logline" | "synopsis" | "genre" | "audience" | "tone">> & {
    openingHook?: string;
    endingHook?: string;
    arcs?: StoryArc[];
    relationships?: StoryRelationship[];
  };
}
```

- **不整块替换 `story`**：`provenance` 记的是这份故事由哪个模型、根据什么输入生成。作者改字不该把这份溯源抹掉。
- 只收白名单字段：`hooks` 拆成 `openingHook` / `endingHook` 两个扁平键，改一个不影响另一个；`arcs` / `relationships` 按整组传。
- 文字字段 `trim()` 后写入，空串表示清空。`patch` 里一个字段都没有时直接报错，不写空事件。

### 2. 弧光与关系按整组替换，但入口是语义化的

事件层收整组，是为了回放简单（一次替换，不做逐项 diff）。但让界面自己算「改哪一条、整组长什么样」容易算错，所以 store 提供两个语义化方法：

```ts
editArc(characterId, patch)              // 找到那一条，合并后整组写回
editRelationship(from, to, tension)      // 有就改、没有就加、写空就删
```

两者最后都落到 `editStory({ arcs })` / `editStory({ relationships })`，事件形状不变。

### 3. 校验写在 applyEvent 里

- 弧光的 `characterId` 必须存在，且同一角色不能出现两份。
- 关系两端必须是**不同**且**存在**的角色；同一对（有向）不能写两遍。
- `tension` 为空表示删掉这条关系，由 store 过滤，事件里不带这条。

放在 applyEvent 而不是只放在 store，是因为日志可能来自别的写入方；校验必须跟着事实走，不跟着界面走。

### 4. 界面：故事页的「故事圣经」区

放在生成区下方，因为它是**已落项目**的内容，与上方「草稿」是两件事：

- 5 个文字字段各一个「改」，点开就是行内输入框 + 存 / 撤。
- 每个角色的 7 项弧光一行一项（要 / 缺 / 伤 / 缺陷 / 秘密 / 选择 / 弧光），点值即编辑，`title` 写清这一项问的是什么。
- 关系列在下面，每条可改可删；底部一行「谁 → 对谁 + 张力 + 加一对」，两端相同或重复时按钮禁用并给出原因。
- 没改动不写事件：历史里塞满「改故事：梗概」而内容没动，等于噪音。

### 5. 关系三问不拆成结构化字段

STORY.md 说每对关系要回答「想要 / 害怕 / 隐瞒」里的**至少一件**。听起来该拆成三个输入，但拆了就得回答「三个都要填吗、只填一个算不算合格」——那是剧本医生的评分模型（A18）该定的事，不是编辑器该替作者决定的。当前仍是一个自由文本 `tension`。

## 后果

- 改一个字段只写一条事件，别的字与 provenance 都不动。
- 弧光与关系可以逐步打磨，不用整份重新生成。
- 下游（提示词、合规预检）读的是同一份 `story`，改完立刻生效。
- 事件校验让「日志里出现指向不存在角色的弧光」变成不可能。

## 验证

- 单测 795 全过（IR 160 + gateway 28 + pipeline 51 + web 556）。
  - IR 新增 5 条：只改传入字段且另一个钩子不动、弧光同角色重复被拒、关系两端相同 / 不存在 / 重复被拒、空 patch 被拒且 `provenance` 保留、去空白与空串清空。
  - `workbench-store.test.ts` 新增 7 条：改一条弧光只写一条事件且其余不动、没改不写、无弧光角色拒绝、关系加改删三条路径、两端相同与不存在拒绝、文字没改不写、只读全部拒绝。
- `pnpm typecheck`、`next build` 全过。
- 浏览器（生产 3100，故事页）：面板「0 条人物弧光 · 0 对关系 · 5 项里填了 0」；改 logline 存下 v6 → v7；选「林 → 周」写张力点「加一对」→ v8，关系区出现「林 → 周 / 谁先承认灯是谁关的」，底栏从「还差一句 logline；还差一段梗概」变成「还差一段梗概」；点「删」→ v9，关系区回到「还没有关系」。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 整块替换 `story` | 会把 `provenance` 与没打算改的字段一起覆盖；作者改一个字不该丢掉这份故事的来源 |
| 每个字段一条事件（`story.arc.updated` 等） | 事件类型会膨胀到十几个，而它们都是「改故事里的某个字」，回放时没有区别 |
| 只在 store 校验，不进 applyEvent | 日志可能来自别的写入方；校验要跟着事实走 |
| 关系三问拆成三个结构化输入 | 「三个都要填吗」是剧本医生的评分模型该定的事，编辑器不替作者决定 |
| 弧光支持「重新生成这一条」 | 重新生成整份故事仍走故事入口；局部重掷要定「哪些字段跟着变」，超出编辑器职责 |
