# ADR-0239：测试统一用 resetForTests，别直接调 reset

- 状态：已采纳
- 日期：2026-11-15
- 决策者：用户 + Claude
- 关联：H18、ADR-0034、ADR-0238

## 背景

ADR-0238 拆分 store 时发现：`workbench-store.test.ts` 里有几个用例**单独用 `-t` 过滤跑会失败**，
全量跑却全过。改动前后各验一次，确认是既有问题，与拆分无关。

根因查清了，是两件事叠在一起：

1. `reset()` 在生产里有正确的保护——**只读标签页直接返回**，不覆盖别人的项目（H18）：
   ```ts
   reset: () => {
     if (get().readOnly) return;
     ...
   }
   ```
2. 测试里有 49 处 `useWorkbench.setState({ readOnly: true })`，但 97 处 `beforeEach`
   只调 `state().reset()`，其中只有 4 处先清了 `readOnly`。

于是**一个用例设了只读却没恢复，后面所有用例的 `reset()` 都静默失效**，
状态从上一个用例漏过来。全量跑时前序用例的顺序恰好掩盖了它；用 `-t` 过滤时顺序变了，就暴露了。

## 决定

1. **新增 `resetForTests()`**：先 `setState({ readOnly: false })` 再 `reset()`。
   放在 store 里而不是测试文件里，因为它是「测试怎么正确地复位」这件事的唯一出处。
2. **87 处 `beforeEach` 里的 `state().reset()` 全部换成 `resetForTests()`**。
3. **用例体内的 5 处 `reset()` 保持原样**：它们是有意验证「重置」本身的行为，
   其中一处正是「只读时 reset 不生效」——换成 `resetForTests` 就把被测行为改掉了。
4. **不改 `reset()` 的生产语义**：H18 的保护是对的，问题在测试没清理干净，不在实现。

## 理由

- **修测试而不是改实现**：`reset()` 在只读页返回是正确行为，为了测试方便去掉它，
  等于在生产里留一个「只读页也能覆盖别人项目」的洞。
- **集中在 store 里加一个函数**：49 处设置 `readOnly` 的地方逐个补 `readOnly: false`
  不可靠（漏一个就复发），而且将来新写的用例还是会忘。把「正确复位」做成一个函数，
  用的人只需要记住一件事。
- **保留用例体内的 `reset()`**：那几处测的就是 `reset` 本身，不能替换。

## 后果

**正面**

- 单独跑任何一个用例组都可靠，调试时不会再被假失败误导。
- 「怎么正确复位」只有一个出处，新用例照抄 `resetForTests()` 就不会踩这个坑。
- 生产行为零变化。

**负面 / 代价**

- 多了一个只在测试里用的导出函数（`resetForTests`）。
- 用例体内的 5 处 `reset()` 仍是裸调用——它们是对的，但读代码的人要能分辨
  「这里为什么不换」；ADR 与函数注释都写明了。
- 这类「测试之间互相污染」的问题可能还有别的形态（比如 `localStorage`、
  `setEventLog` 注入的日志），本次只修了 `readOnly` 这一条最明显的。
