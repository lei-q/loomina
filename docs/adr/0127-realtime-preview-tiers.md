# ADR-0127：实时预览分两级，WebCodecs 只做「帧级找点」，WebGPU 暂不做

- 日期：2026-11-11
- 状态：已采纳
- 关联：E7、E10、E1、E6、C5、ADR-0084、ADR-0086、ADR-0091、ADR-0120、R19

## 背景

ARCHITECTURE.md 与 TECH-SELECTION.md 都写着「预览用 WebCodecs + WebGPU」，TECH-SELECTION 还列了 mp4box.js。但这两条至今只是**选型意向**，没有设计：

- 预览到底要回答什么问题？
- 逐镜播放（E10 的 Animatic）与「实时预览」差在哪？
- WebCodecs 与 WebGPU 各自解决什么，缺了会怎样？
- 引入 mp4box.js 算不算「重型依赖」？

现状：E10 的预演已经能按镜头时长放画面、放台词音轨、放配乐、放字幕（ADR-0084 / 0085 / 0120），但它只能**从某一镜开头播**，没有时间轴、不能拖到某一秒、不能跨镜连续播放一条片子。成片页只能播**已经渲染好的 MP4**，改一个镜头就得重渲一遍。

所以 E7 要补的是：**改完之后，不渲染也能看整条片子的任意一帧。**

## 决策

### 1. 分两级，第一级不引入任何新依赖

| 级别 | 能力 | 依赖 | 精度 |
| --- | --- | --- | --- |
| **E7.1 时间轴预览** | 整条片子的连续播放、拖动找点、跨镜切换、字幕与角标叠加 | 无（`<video>` + Canvas） | 到镜准确，镜内受关键帧间隔限制 |
| **E7.2 帧级找点** | 拖到任意毫秒都出对应帧，逐帧步进 | **mp4box.js（待确认）** + WebCodecs | 帧级 |
| **E7.3 合成加速** | 转场、调色、多轨合成的实时渲染 | WebGPU | — |

第一级就能回答 90% 的问题：「这一版的节奏对不对」。第二级是「这一帧的构图对不对」，第三级是「加特效之后还跑不跑得动」。

### 2. E7.1：预演升级成一条真时间轴，不是新开一个页面

- 预演（E10）的覆盖层底部进度条改成可拖动的时间轴：按 `TimelineItem` 的 `startMs` / `durationMs` 铺格子，拖到哪一格就切到哪一镜，镜内偏移用 `video.currentTime` 精确设置。
- 同一时刻只有一个 `<video>` 在播：预载下一镜的元数据（`preload="metadata"`），切换时交换 `src`。**不并排解码多条视频**——短剧每镜 2–5 秒，切换足够快，而并行解码是 R19 的主要来源。
- 字幕、AI 角标、配乐继续沿用现有实现（字幕来自 `subtitleCues`，音乐来自 `AnimaticMusic`）。
- 拖动的粒度是**镜**，镜内是近似：`currentTime` 能精确到毫秒，但浏览器只能在最近的关键帧之后解码，所以镜内拖动会有最多一个 GOP 的误差（通常 ≤ 1 秒）。
- 界面上明确写「预演精度：到镜准确，镜内近似」，**不承诺帧级**。

这一级完全没有新依赖：`<video>` 与 Canvas 都是平台自带。

### 3. E7.2：mp4box.js 是依赖，先确认再写

帧级找点必须自己解封装（`<video>` 拿不到解码器输出的帧）：

```
mp4box.js 解封装 → EncodedVideoChunk → VideoDecoder → VideoFrame → canvas.drawImage
```

- **mp4box.js 是依赖**（MIT，约 100 KB min），按 CLAUDE.md「未经确认，不引入重型依赖」需要单独确认。它不属于「十年不变」那一类，但它是这个功能唯一可行的路——浏览器没有原生的 MP4 解封装 API。
- WebCodecs 本身是**平台 API，不是依赖**（Chrome 94+ / Edge / Safari 16.4+），这一半不需要确认。
- 前置条件：预览用的代理视频。1080p 原始 take 逐帧 seek 会让解码器排队；540p 代理（与 `RENDER_PROFILES.draft` 同规格）才是可用的输入。代理生成放在**渲染队列**里（已有队列，ADR-0093），不新开一条路径。

因此 E7.2 的启动条件是两件事都成立：**依赖确认 + 代理生成可用**。

### 4. E7.3：WebGPU 暂不做

当前需要合成的只有三层：视频帧、字幕、角标。Canvas 2D 足够。WebGPU 的收益出现在：

- 转场（交叉溶解、推拉）；
- 调色（LUT）；
- 多轨同时合成。

这三件都还没有进 MVP 的时间线能力（E1 只有硬切）。**在只有硬切的时间线上引入 WebGPU，是为了一个还不存在的需求背一个渲染抽象层。** 等 E1 支持转场时再评估，届时与 B13.3 的 depth 渲染一起做渲染层选型（两者都吃 GPU）。

### 5. 预览永远不是导出路径

预览与导出是两条路径，但**只有一条是事实**：

- 导出仍走 `POST /api/render` → ffmpeg（ADR-0091），成片是权威产物。
- 预览是**近似的**：解码器、色彩管理、字幕字体的渲染都可能与 ffmpeg 不同。
- 界面上预演/预览的摘要里固定写「这不是成片，成片以导出为准」——与 ADR-0120 同一口径。

不做「浏览器内导出」：把 WebCodecs 编码器接上就能在浏览器里出 MP4，但那会变成第二条渲染路径，改一处忘一处（ADR-0120 拒绝 540p 独立渲染的同一个理由）。

### 6. 降级与能力探测

```ts
export type PreviewCapability = {
  /** 有 WebCodecs 的 VideoDecoder */
  decode: boolean;
  /** 有 WebGPU adapter */
  gpu: boolean;
  /** 能拿到代理视频（没有代理就只能用原片，seek 会卡） */
  proxy: boolean;
};
```

- 缺 `decode` 或 `proxy` → 用 E7.1。
- 缺 `gpu` → 无所谓，E7.1 本来就用 Canvas。
- 界面在预览摘要里写当前用的是哪一级，不静默降级（R19 的缓解措施）。

## 理由

- **先解决 90% 的问题，不先背依赖**：E7.1 零依赖就能让作者改完立刻看整条片子，这是「实时预览」在产品上真正值钱的部分；帧级精度是第二层需求。
- **mp4box.js 必须确认**：它是这个功能唯一的路，但它是依赖。按项目约束，依赖决定要显式记录，而不是在设计里默认带上。
- **WebGPU 等需求**：只有硬切的时间线用不上 GPU 合成；提前引入会让渲染层在需求出现前就固化。
- **预览不导出**：两条渲染路径必然漂移，而漂移的结果是「预览对了、成片不对」。

## 后果

**正面**

- 改完一镜，不用渲染就能从任意位置看整条片子。
- E7.1 零新依赖、零新服务，纯前端改造。
- 能力探测让低端设备自动退回可用的那一级，且用户知道自己在哪一级。

**负面**

- 镜内拖动有最多一个 GOP 的误差，不能用来做帧级对齐。
- 帧级找点要等依赖确认与代理生成，可能长期停在 E7.1。
- 预览与成片可能有色彩 / 字幕渲染差异。
- 代理视频会额外占用本地空间（H3 之前仍是 data URI）。

**跟进**

- 确认 mp4box.js 后做 E7.2，并补一次真实设备的性能标定（R19）。
- E1 支持转场时评估 WebGPU，与 B13.3 的 depth 渲染合并选型。
- 代理视频进对象存储（H3），IR 里只存地址。

## 成本

| 项 | 估计 |
| --- | --- |
| 运行时 | 0 元（纯浏览器） |
| E7.1 工程 | 时间轴与跨镜切换 2 天；精度文案与降级 0.5 天 |
| E7.2 工程 | 依赖确认后 4–6 天（解封装 + 解码 + seek + 代理接线） |
| 存储 | 代理视频约为原片的 1/4–1/3；本地配额压力在 H3 之前要盯着 |

## 验证（设计阶段口径）

- E7.1：示例项目拖时间轴到第 3 镜中点 → 播的是第 3 镜、镜内偏移与时间轴一致；跨镜连续播 30 秒不跳帧、不双声；摘要写明「到镜准确，镜内近似」。
- 能力探测：无 WebCodecs 的浏览器自动落 E7.1；有 WebCodecs 但无代理时仍是 E7.1，并说明原因。
- 回归：E10 的逐镜播放、台词音轨、配乐静音开关全部不受影响。
- E7.2（依赖确认后）：逐帧步进 10 帧，画面与 ffmpeg 同帧导出对比无明显色差；seek 到任意毫秒的平均响应 < 150 ms。

## 备选方案

| 方案 | 不采用的原因 |
| --- | --- |
| 直接做 WebCodecs 帧级预览 | 需要 mp4box.js 依赖 + 代理生成，两个前置条件都不具备；E7.1 能先解决节奏判断 |
| 用 `<video>` 多轨并排播 | 并行解码是 R19 的主要来源；短剧镜头短，单轨切换足够 |
| 用 WebGPU 做合成 | 只有硬切的时间线用不上，提前引入会让渲染层在需求前固化 |
| 浏览器内编码导出 | 变成第二条渲染路径，与 ffmpeg 必然漂移；导出必须唯一 |
| 预览即最终画面 | 解码器、色彩管理、字体渲染都与 ffmpeg 不同，界面必须写明以导出为准 |
| 静默降级到 `<video>` | 用户会以为看到了帧级结果；能力与精度必须写在摘要里 |
