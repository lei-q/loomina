# ADR-0225：按场批量套用先出计划，再逐镜写事件（I7 第三档）

- 状态：已采纳
- 日期：2026-11-14
- 决策者：用户 + Claude
- 关联：I7、I1、B11、ADR-0186、ADR-0222

## 背景

I7 第一档（ADR-0186）是**改一镜**：一次一项、一条 `shot.updated`。
I7 第二档（ADR-0222）是**看全片**：摄影单把参数摊成一张表，只读。

中间缺一格：**改一整场**。一整场八到十几镜，如果都要统一成某个景别或焦段，
现在只能逐镜点。I7 的未做项里第二条就是「按场批量套用」。

批量改比单镜改危险得多：改错一次要撤十几步，而 `shot.updated` 是逐条事件。

## 决定

1. **先算计划，再执行**：`batchPlanOf(project, sceneId, patch)` 返回
   - `changes`：哪几镜会变、变成什么、人话说明变了哪几项；
   - `skipped`：哪几镜跳过、为什么（锁定 / 已经是这样）；
   - `summary`：这一场几镜、会改几镜、写几条事件。
2. **界面把计划摊给作者看**：摄影单里每场一个「整场改」，
   选一项参数后立刻显示「会改 5 镜、写 5 条事件，3 镜跳过」，
   点「确认整场改」才执行。
3. **锁定的镜一律跳过**，与单镜改同一口径。
4. **参数没变的镜不写事件**：批量不等于「全写一遍」。
5. **所有事件共用一个 `at`**：整批是一次操作，撤销一步整批退回。
6. **一次只改一项参数**：批量改多项等于「整场重设」，那不是这个入口想干的事。
7. **只处理这一场自己的镜**：跨场批量没有意义（不同地点、不同时间）。
8. **机位整份写回时保留 `placement`**：与 `setShotCamera` 同一条教训——
   走位里摆好的坐标不能被批量洗掉。
9. **中文名直接用 pipeline 的常量**（`SHOT_SIZE_CN` / `SHOT_ANGLE_CN` / `MOVE_CN`），
   不本地重写一份——那正是 M6 抓过的重复定义。

## 理由

- **计划与执行分开**：批量改的代价在于「改错了要撤很多步」。先让作者看见
  「会改哪几镜」，比事后撤销便宜得多。
- **一项参数而不是多项**：一次改景别 + 机位 + 运镜，本质是「整场重设」。
  那需要另一套确认流程（每项各自的合理性），不该塞进一个下拉里。
- **共用 `at`**：这是「整批是一次操作」的唯一表达方式。不共用的话，
  撤销要按事件一条条退，作者会退到手酸。
- **跳过而不是报错**：锁定的镜是作者有意锁的，批量时跳过比整批失败合理。

## 后果

**正面**

- 一整场的参数统一从「点十几次」变成「选一项、看一眼、确认」。
- 计划里写清跳过原因，作者知道为什么某一镜没变。
- 撤销一步整批退回。

**负面 / 代价**

- **一次只能改一项**：想同时改景别和焦段要操作两次。
- **没有「只改选中的几镜」**：要精细控制仍然逐镜点。
- 批量写事件是 `changes.length` 条，一场十几镜就是十几条事件；
  日志会变长（`log-compact` 能压，但那是另一个开关）。
- 跨场批量明确不做，作者的「整部片子统一成特写」这类需求没有入口。
