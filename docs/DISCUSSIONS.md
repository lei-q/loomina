## 2026-11-09 定位与架构首次讨论

**参与者**：用户 + Claude

**议题**
1. 产品定位：通用 AI 视频工具 vs 短剧生产线
2. 生成管线：文生视频 vs 先图后视频
3. 后期顺序：画面先行 vs 音频先行
4. 剪辑工具：自研 NLE vs 组合开源
5. 发布：一键发布 / 扫码登录是否可行
6. 故事层与摄影语言如何产品化
7. 用户与市场：C 端、国内首发
8. 文档留痕机制

**确认的结论**
- 产品是**短剧生产线**，面向 **C 端**，国内首发、竖屏 60–180 秒。
- 单人开发，模型 API 预算充足，无短剧行业与 IP 资源。
- 商业模式暂不设定，先打磨产品。
- 采用**先图后视频**、**音频先行**、**多 Take + 非破坏**、**模型无关网关**。
- 剪辑采用 **OTIO + WebCodecs/WebGPU + ffmpeg**，不自研 NLE。
- 发布采用**官方 API + 移动端分享扩展**，明确不做逆向自动化。
- 摄影语言做成**可量化参数系统**（可先做最小集），与短剧语法一起作为一等公民。
- 建立**文档先于代码**的记录机制。

**产物**
- 建立 `docs/` 全套文档与记录协议（[docs/README.md](README.md)）。
- 准则 P1–P12（[PRINCIPLES.md](PRINCIPLES.md)）。
- ADR-0001 ~ ADR-0008（[adr/](adr/)）。

**待定**
1. 首个可交付故事的题材与样例（需要具体剧本验证管线）。
2. 技术栈定稿（当前为建议，见 [ARCHITECTURE.md](ARCHITECTURE.md)）。
3. 移动端形态：PWA / 原生壳 / 独立 App。

## 2026-11-09 第二次讨论：运转、闭环、难点与选型

**参与者**：用户 + Claude

**议题**
1. 平台端到端如何运转
2. 哪些环节不闭环
3. 哪些是真正的阻塞
4. 业务难点与技术难点
5. 技术选型的标准与推荐栈
6. 如何一步一步落地

**确认的结论**
- 运转不是线性流水线，而是**带四道闸门的循环**：资产确认 → Animatic 确认 → 镜头验收 → 成片确认。
- 发现 10 个不闭环点，其中最重要的是 **L1（剧本→分镜无验收）**，用 **Animatic 闸门**解决。
- 三个硬阻塞：**一致性（技术）、成本（商业）、单人 scope（执行）**。
- 技术难点排序：一致性 > 可控性 > 叙事连贯 > 音画同步 > 自动剪辑审美 > 实时预览 > 编排/成本。
- 新增设计：短镜头/覆盖率（ADR-0012）、连续性台账（SceneState）、语义编辑（F7）、预算护栏（H10）、能力矩阵（B12）。
- 落地按**风险退休顺序**（S0 契约 → S1 能力测绘 → S2 Animatic → S3 单镜质量 → S4 前端 → S5 时间线 → S6 发布），**S0–S3 不写 UI**。
- 技术选型原则：单人可维护、托管优先、同语言、无聊技术、接口隔离、先单体。
- 工作流引擎改为**分阶段**：Phase 1 pg-boss + 状态机，Phase 2 评估 Temporal/Restate（ADR-0010）。
- IR 存储定为 **JSONB + 事件日志 + 快照**（ADR-0011）。

**产物**

- 新增 [TECH-SELECTION.md](TECH-SELECTION.md)（选型原则、栈、取舍、落地顺序）。
- ADR-0009（Animatic 闸门）、ADR-0010（工作流分阶段）、ADR-0011（IR 存储）、ADR-0012（短镜头/覆盖率）。

## 2026-11-09 第三次讨论：一致性与剧本→分镜

**参与者**：用户 + Claude

**议题**
1. 3D 场景板的形态
2. 跨镜头一致性如何解决
3. 剧本 → 分镜如何做

**确认的结论**
- **3D 场景板采用灰盒（gray-box previs）**：场景模板、胶囊人物、机位视锥、轴线检查、depth 导出；**自动优先，手动其次**。MVP 只做最小版（ADR-0013）。
- **一致性拆成 8 个维度**（身份/服化道/场景/光影/空间/表演/动作/风格），采用 **5 层防线**：资产锚定 → 结构锚定（3D+关键帧）→ 生成约束 → 量化验收 → 后期统一（ADR-0014）。
- **一致性要可度量**：人脸 embedding 余弦、VLM 清单、pHash、色温/直方图；分维度打分，阈值按景别分级。
- **明确一致性的天花板**：侧背、复杂花纹、儿童/老人、多人、长镜、极端角度；产品主动规避，不承诺"完全一致"。
- **分镜不是一次 LLM 调用，是约束求解**：LLM 负责创意选择，规则引擎负责合法性（轴线/时长/覆盖率/模型能力/预算）（ADR-0015）。
- 分镜管线定为 **7 步**：Beat 分析 → 覆盖率规划 → 3D 走位 → 机位/镜头 → 时长/节奏 → 台词分配 → 校验。
- 建立**导演语法库**（叙事意图 → 景别/机位/运镜/光 + 覆盖率模板 + 校验规则 V1–V10），作为产品 IP。

**产物**

- 新增 [STORYBOARD.md](STORYBOARD.md)（7 步管线、导演语法库、30 秒例子、失败模式）。
- ADR-0013（3D 灰盒 previs）、ADR-0014（多层一致性）、ADR-0015（分镜混合约束求解）。
- 准则新增 P15（分镜=约束求解）。

## 2026-11-09 第五次讨论：规则进化与故事层

**参与者**：用户 + Claude

**议题**
1. 导演语法库后期能否自动补充？触发机制是什么？
2. 把"故事"聊透。

**确认的结论**
- **规则采用"自动发现、受控晋升"**（P17 / ADR-0018）：四个信号源（失败挖掘、用户覆盖、参考片分析、专家/社区）；触发阈值（重复失败 ≥20/1000 镜或 ≥3 项目、一致覆盖 ≥10/100 镜、规则失效 >10%、参考片模式 p<0.05、新模型、新题材、指标漂移、周期批处理、人工提议）。
- **候选生命周期**：observed → drafted → evaluating → ab → promoted/rejected/revised → versioned。
- **晋升门槛**：must = 人工确认 + 回归零失败 + 2 名评审；should = A/B 胜率 ≥5% + 成本 ≤10% + p<0.05 + 2 周；may = 可自动进风格包。
- **防膨胀**：活跃规则 ≤60、90 天归档、冲突检测、作用域限定、风格与结构分离、回归集。
- **冷启动**：37 条专家规则作 `grammar@0.1`；前 100 项目 / 10,000 镜只收集数据不自动晋升。
- **故事是产品**（P16 / ADR-0017）：生成会商品化，故事是唯一可持续差异化；LLM 擅长"合格但平庸"，用结构保证下限、人的品味抬高上限。
- **短剧十条物理定律**：3 秒法则、15–20 秒增量、一句话前提、欲望-障碍-代价、关系即冲突、结尾留钩、低认知负荷、可视化优先、情绪 > 逻辑、具体 > 抽象。
- **题材矩阵**：首发聚焦都市情感 / 逆袭打脸 / 甜宠（室内、少人、对话驱动，落在模型强项）。
- **故事引擎 8 步**：前提选择 → Logline 评分 → 人物与关系 → Beat Sheet → 场次拆解 → 台词 → 剧本医生 → 原创性检查。
- **剧本医生 12 维 rubric + 触发条件 + 6 种改写模式**；台词单句 ≤15 字、单镜 ≤2 句；人物 ≤5、场景 ≤3。
- **原创性**：先"标记"不"阻断"；相似度 >0.8 进人工复核。

**产物**
- 新增 [RULE-EVOLUTION.md](RULE-EVOLUTION.md)。
- 新增 [STORY.md](STORY.md)。
- ADR-0017（故事层结构化）、ADR-0018（规则自动发现/受控晋升）。
- 准则新增 P16（故事一等公民）、P17（规则受控晋升）。
- 更新 DATA-MODEL（Premise/Hook/CharacterArc/ScriptDoctorReport/OriginalityReport + 4 条不变量）、FEATURES（A14–A20、I10）、README。

**待定**
1. 剧本医生 12 维权重的首批标定（需 30 个短剧样本）。

## 2026-11-09 第六次讨论：表演与镜头内调度

**参与者**：用户 + Claude

**议题**
1. 故事和分镜都定了，"人在画面里怎么演、怎么动"还是空的。
2. AI 的表演能力边界在哪，产品怎么绕开。

**确认的结论**
- **表演是镜头的目的，运镜是手段**（P18 / ADR-0019）：每镜先定"观众要看到什么变化"，再定景别/机位/运镜。
- **一镜一个 objective、一个情绪转折**；想表达两个就拆两个镜头。
- **表演拆五层**：意图 → 情绪 → 微表情 → 身体 → 动作，全部进 IR。
- **表演节拍**：起（反应）/ 转（决定）/ 落（行动）；对应台词前/中/后；**反应镜头是主战场**。
- **关键帧表演法**：首帧定情绪起点、尾帧定终点，中间只做微动作；情绪跨度大用三帧法切两段。
- **情绪越强，动作越小**；把情绪翻译成具体微动作，不写形容词。
- **视线必须显式**（`GazeTarget` 必填），视线是 AI 最易飘、最影响演技的参数。
- **竖屏调度**：少横移、多纵深；前景遮挡造层次；"脸 + 手 + 一件道具"。
- **距离即关系**：脸贴脸=亲密/威胁，隔前景=隔阂/窥视。
- **口型只特写启用**，中景用侧背/遮挡/反应镜头规避。
- **表演 QA**：情绪匹配、视线、动作完整、过火/面瘫、情绪连续；按景别分级阈值。

**产物**
- 新增 [PERFORMANCE.md](PERFORMANCE.md)。
- ADR-0019（表演以关键帧与微动作为主）。
- 准则新增 P18（表演优先于运镜）。
- 更新 DATA-MODEL（PerformanceSpec/ActionBeat/GazeTarget + 4 条不变量）、FEATURES（B16–B18、I11）、README。

**待定**
1. 表演语法库的首批条目（意图 → 微动作 → 避免项）。
2. 各景别的表演强度阈值标定。
3. 表演 QA 与一致性 QA 的管线合并方式。
4. 下一个议题候选：音频与声音设计（配音表演、音乐、音效）或发布与合规。

## 2026-11-09 第七次讨论：声音设计

**参与者**：用户 + Claude

**议题**
1. 表演有了脸，还缺"嗓子"：配音、音乐、音效怎么设计。
2. 短剧的播放环境对混音的约束。

**确认的结论**
- **声音是第二条表演线**，不是后期补丁；拆四层：对白 / 音乐 / 音效 / 环境（P19 / ADR-0020）。
- **播放环境决定混音**：手机外放、单声道近似、低频缺失、环境嘈杂、可能静音 → 信息双通道、中频为主、不依赖低频。
- **配音不是朗读**：逐句参数（语速/音高/音量/气声/停顿/重音/句尾/呼吸）+ 多 Take；一句台词的意思一半在重音落在哪个字。
- **配音节拍对齐画面表演**：台词前 0.3–0.5s 反应、台词中气口、台词后 0.5s 余韵；口型只特写。
- **音乐按 Beat 情绪曲线走**：只做进/转/出，留白，主题动机（leitmotif）；不从头铺到尾。
- **音效克制**：只给有意义动作配音；画外音扩展空间比多拍一镜便宜。
- **混音对白优先**：台词下音乐 ducking 12–18 dB；整体 ≈ −14 LUFS；真峰值 ≤ −1 dBTP；单声道兼容必检。
- **声音也要一致性**：VoiceProfile 跨集固定、场景 reverb 统一、音乐服从 StyleProfile、整片响度归一。
- **声音 QA**：清晰度、响度/削波、音画同步（±40ms）、情绪匹配、静音可懂、空间一致、版权授权。

**产物**
- 新增 [SOUND.md](SOUND.md)。
- ADR-0020（声音分层、对白优先混音）。
- 准则新增 P19（对白是声音的主角）。
- 更新 DATA-MODEL（VoiceProfile/LinePerformance/MusicCue/SfxCue/MixSpec + 5 条不变量）、FEATURES（C9–C13）、README。

**待定**
1. 配音默认参数模板（按情绪/性别/年龄）。
2. 场景混响预设与音乐情绪曲线模板。

## 2026-11-09 第八次讨论：发布与合规

**参与者**：用户 + Claude

**议题**
1. 多平台发布到底能做到什么程度。
2. AI 标识、内容安全、授权链怎么落到管线里。

**确认的结论**
- **发布的第一能力是导出合规成品，不是代发**（P20 / ADR-0021）；平台 API 是增强不是依赖。
- **三层能力**：L1 导出包（P0，永远可用、自包含）、L2 官方 API（P2，需资质）、L3 移动端分享扩展（P1，覆盖无 API 平台）。
- **明确不做**：逆向登录、模拟点击、批量养号、绕过审核、爬取数据（R10）。
- **平台规格不写死在代码**，维护 `PlatformSpec` 表并版本化；矩阵覆盖抖音/快手/小红书/B站/视频号/TikTok/YouTube Shorts/X。
- **AI 标识在渲染阶段写入**：显式（角标/片头/简介烧录）+ 隐式（文件元数据）；不得移除平台标识。
- **内容安全四个检查点**：剧本 → 关键帧 → 成片 → 发布文案；处置 pass/review/block，结果留档。
- **授权台账**：模型输出/音乐/音色/字体/肖像/文本，每项素材挂 `AuthorizationRecord`，缺授权阻断发布。
- **发布流程**：预检（规格+合规+授权）→ 多平台渲染 → 人工确认 → 导出/API/分享 → 台账 → 数据回流。
- **数据回流只做官方允许的指标**，不做爬虫。
- 资质清单（生成式 AI 备案、ICP、算法备案、公安备案等）需专业法律意见，MVP 可先小范围内测。

## 2026-11-09 第九次讨论：成本与单位经济

**参与者**：用户 + Claude

**议题**
1. 一条 60 秒短剧到底花多少钱，钱花在哪。
2. 哪些重试是浪费，定价下限在哪。

**确认的结论**
- **成本的核心是废片率，不是单价**（P21 / ADR-0022）：`C_effective = 总成本 ÷ 通过镜数`。
- **成本结构**：视频生成占 60–80%，关键帧 10–20%，其余是零头。
- **三个公式**：单镜成本、项目成本（含重试）、有效成本；重试是乘法，通过率 40%→25% 会让成本从 2.5 倍变 4 倍。
- **基准情景（待 S1 标定）**：720p/60% ≈ 100–150 元；1080p/40% ≈ 250–400 元；1080p/25% ≈ 600–900 元。
- **成本杠杆按 ROI 排序**：Animatic 闸门 > 关键帧先行 > 提高通过率 > 双档渲染 > 短镜头 > 模型路由 > 缓存 > 预算护栏。
- **短镜头的成本注意**：不减少视频总秒数、还增加关键帧；省的是"长镜漂移导致整段重来"。
- **双档渲染**：draft（540p/720p）用于一切确认前；final（1080p+）只在确认后。
- **重试停止条件**：预算上限、次数上限 3–5、质量提升 < 阈值、同维度连续两次失败（回设计层）。
- **单位经济现实**：单条 300 元 vs C 端 9.9–29.9 元 = 负毛利，必须靠降本 + 提高单用户产出 + 点数计费三条一起解。
- **点数制**：点数映射真实资源消耗；默认套餐覆盖"一条完整片"。
- **观测**：逐笔记账、提交前估算、异常告警、`ModelPrice` 版本化、双层预算护栏。

**产物**
- 新增 [COST.md](COST.md)。
- ADR-0022（有效通过率为核心、双档渲染、点数计费）。

## 2026-11-09 第十二次讨论：接入真实模型（S1 起步）

**确认的结论**
- **先测绘，再抽象**（ADR-0025）：S1 的第一个产出不是更完整的适配器，而是三份数据——真实单价、首次通过率、失败维度分布。

### 第十三次讨论（三续）：tokens.css 落地

按定稿顺序走第一步，只写 CSS 变量，不引入任何依赖。

**落地的文件**

**实现时定下的两条**
1. **不跟随系统亮暗。** 默认就是印片；亮色要显式写 `data-theme="hall"`。理由：产品 80% 时间在看暗场竖屏，系统切到亮色不等于用户想看一个亮的工作台。
2. **印片写两处。** `:root` 给默认值，`[data-theme="release"]` 再写一遍同样的值。这样亮色页面里嵌一段暗色样片时能切回去，否则 `data-theme` 只向下继承、切不回默认主题。

**顺手补的**
- `--leading-*` / `--tracking-*`：字阶表里的行高与字距变成变量，组件不重复写。
- `--font-sans` / `--font-mono`：Archivo 与 IBM Plex Mono 尚未自托管，先系统栈兜底，接入字体只改这一处。
- `[data-theme]` 自己铺底（`background: var(--bg)`），换主题的容器不必再记一遍。
- `prefers-reduced-motion` 时 `--dur` 归零；`:focus-visible` 用 1px 实线描边，不发光。

**产物**

### 第十六次讨论：重做报价接价目快照（2026-11-10）

写回接通后，重做按钮上的 ¥2.12 是一个写死的数——它正好等于"4 秒 × ¥0.50 + 首帧 ¥0.12"，但对一个 2.4 秒的镜头也是这个价，直接违反 COST.md 不变量 39（单价只能来自价目表）。

**做了什么**
- 价目表不复制：`apps/web/lib/pricing.ts` 直接读 `@loomina/gateway/pricing` 的 `VIDEO_PRICES` / `IMAGE_PRICES`，只做"这个镜头重做一次"的换算：时长 × 每秒单价 + 一张首帧。
- `StageView.requote` 从一个数字变成一个报价对象：`totalCny / videoCny / keyframeCny / basis`。`basis` 是给人看的一句话依据（"2.4s × ¥0.50/s + 首帧 ¥0.12"），挂在按钮的 `title` 上。
- 报价跟着当前格子走：2.4s 的镜头 ¥1.32，3.0s ¥1.62，4.2s ¥2.22。默认草稿档 minimax-h3 @ 768p，首帧 gpt-image-2-c。
- 拿不到价目就不报价：返回 `totalCny: undefined`，界面写"价目未知"，不拿一个想当然的数顶上。

**接线时定的**
- `@loomina/gateway` 的 `index.ts` 会连带导出读 env 文件的模块（`node:fs`），不能整包引到浏览器。加了子路径导出 `@loomina/gateway/pricing`，只把价目表那一个文件交出去，`transpilePackages` 同时加上 gateway。
- take 上的 `costCny` 是"当时记账"，不随价目表变化；报价是"现在再做一次要多少钱"。两者刻意分开，示例数据里的历史成本不重算（仍是 ¥18.96）。
- 重做按钮继续禁用：价格是真的，生成链路还没接。

**测试**
- 新增 6 条报价测试：2.4s → 1.32、4s → 2.12（对上 COST.md 实测）、换分辨率换价、未知分辨率不报价、首帧无价目只给视频部分、默认档位。
- 读模型补 1 条：报价跟着当前镜头的时长走。
- web 23 条测试通过；全仓 63 条通过，`pnpm typecheck`、`pnpm build` 通过。
- 浏览器实测：三个不同时长的镜头，按钮分别显示 ¥1.32 / ¥1.62 / ¥2.22，`title` 给出算式。

**下一步**
1. 一句话指令：解析"太暗了""换个角度"，报价直接用这次的 `requote`。
2. 报价进顶带：已花旁边显示"按当前算，全部重做一遍要多少"，让预算有前瞻，不只有回溯。
